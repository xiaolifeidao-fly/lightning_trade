### 1.2 本任务的目标复述

彻底替代「每周导出 Telegram 历史消息交给 AI 读」这个复盘流程。落到页面上是三件事：

1. **找那一次触发**：多维筛选的信号列表 + 两张分布图（拦截原因、强度分级），点开是逐账户判定抽屉，还原 TG 消息的 `[n]` / `[跳过n]` 结构。
2. **顺一笔持仓从头读到尾**：episode 列表 + 生命周期抽屉（浮盈 ROI 轨迹、事件时间轴、trail 峰值与回吐比例、出场归因）。
3. **把改参数前后摆在一起比**：按 `config_version` 与实例切片对比。

外加两条硬性护栏，它们不是装饰而是验收项：

- **全部实例视图每行标实例归属**，并提示账户重号（实例1 与实例3 的 `account1` 是不同账户）。
- **`external_close` / `manual_close` 在页面明确标注不计入策略胜率**（任务说明的「不做」项，是「不做隐藏过滤」而不是「不显示」）。

argus_event/episode.go:407:15:  undefined: ErrEpisodeNotFound
argus_event/episode.go:412:22: s.episodeEntryRepository undefined

即：r10 把 episode 读侧的**业务逻辑**写完了（`episode.go` 781 行、`compare.go` 257 行、`dto/episode.go` 391 行、`repository/episode_repository.go` 456 行），但没有把两个仓储接到 `ArgusEventService` 结构体上，也没有定义 `ErrEpisodeNotFound`。这与 r10 设计文档最后一行的自述吻合：

### 2.3 三条必须落到 UI 上的口径（来自 DTO 注释与需求大纲）

1. **`fillPriceAvailable` 恒为 false**：成交价与委托均价来自交易所下单回执，埋点未落库。前端必须显示「—」，不能显示 0——那是「没有这个观测」不是「成交在 0」。
2. **ROI 轨迹是离散观测，upl 是心跳序列，两者不换算**：ROI 只在 `gate_block` / `loss_alert` / 出场事件里被写下来；upl 单位是 U，换算成 ROI% 需要假定保证金不变，那正是需求大纲 §3.5 记录的伪影来源。
3. **窗口口径是显式入参**：同一批持仓按 `opened` / `closed` / `overlap` 数出来的条数不同（r10 实测 21 / 29 差 8 笔），服务端刻意不偷偷定一个。

### 2.4 前端可参照的同构模块

`client/manager/src/app/(console)/argus-market/`（r12，正在并行开发）已经建立了本域前端的写法：`api/*.api.ts` 用 `class` + `declare` 字段配 `instance.get` + `unwrapApiResponse`，`hooks/use*.ts` 用请求序号做并发保护，时间一律墙钟串。r13 照抄这套，不另起一路。

> 施工过程中观察到 `argus-market/` 与 `ManagerShell.tsx`、`globals.css` 尾部被并行回合改动（r12 在同一分支上跑）。r13 的所有新增都落在独立目录，对共享文件只做**追加**（`globals.css` 追加一段、`ManagerShell` 追加一个菜单项），没有覆盖任何既有内容。

## 3. 考虑过哪些方案

### 3.1 episode 读路径放在哪里

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A：补完 `service/argus_event` 的接线，在 r9 的 handler 里加路由 | 给 `ArgusEventService` 加两个仓储字段 + `ErrEpisodeNotFound`，`RegisterHandler` 追加 5 条 GET | 与 r10 设计文档的建议完全一致；信号侧与持仓侧共用 `resolveWindow`、`splitCSV`、label 字典，跨域拼装的活儿服务端已经做完（`GetSliceCompare` 同时读两张表） | **选中** |
| B：新建 `manager-api/pkg/argus_episode` + `service/argus_episode` 独立域 | 按「一个页面一个域」拆 | `compare.go` 要同时读 `strategy_event` 与 `episode`，拆域后必然出现跨域调用或仓储重复定义；label 字典也要复制一份，写侧改名不再编译报错 | 否决 |
| C：前端调 r9 现有接口，自己在浏览器里归集 episode | 不动后端 | 派生逻辑 781 行在服务端，前端重做一遍必然漂移；决策归集口径（PnL 平摊回建仓时状态）在前端做等于把统计护栏交给最容易出错的一层 | 否决 |

### 3.2 页面切成几个视角

| 方案 | 取舍 | 结论 |
|---|---|---|
| A：原型的两段式（信号 / episode），切片对比塞进 episode 页脚 | 忠于原型 | 切片对比要在两张表上各扫一遍窗口，与统计接口同量级开销。塞进 episode 视角等于每次看持仓都替它买单 | 否决 |
| B：三视角 Tabs（信号 / episode / 切片对比），切片对比按需加载 | 比原型多一个 Tab | 任务说明把「按 config_version 与实例切片对比」列为独立能力，给它独立入口反而更贴需求；开销可控 | **选中** |
| C：三个独立路由页 | 入口更清楚 | 筛选条件（实例 / 账户 / 时间窗口）三处共享，拆页后要么各填一遍，要么塞进 URL 参数同步。而且 r15 才是负责菜单重组的任务，r13 不该一口气占三个菜单位 | 否决 |

### 3.3 统计接口什么时候拉

| 方案 | 取舍 | 结论 |
|---|---|---|
| A：三个视角各拉各的统计 | 请求最少 | 顶部 KPI 条要同屏显示信号侧（触发数 / 成交率）与持仓侧（胜率 / 净盈亏），分开拉会出现两块数据窗口不一致的瞬间 | 否决 |
| B：`gate-stats` 与 `episode-stats` 并行拉、随筛选变化；`slice-compare` 只在切到对比视角时拉 | 每次改筛选两个聚合请求 | KPI 条口径一致，且最贵的那个接口不被另外两个视角连带 | **选中** |

### 3.4 相对时间窗口锚在哪

| 方案 | 取舍 | 结论 |
|---|---|---|
| A：锚在 `new Date()`（服务器/浏览器当前时间） | 直觉写法 | 本库主力数据是 6–8 月的回灌历史，「近 7 天」永远是空页 | 否决 |
| B：锚在 `/filter-options` 返回的 `dataRange.end`（已入库数据最新时刻） | 需要先拿到筛选项才能算窗口 | 「近 7 天」= 有数据的那批里最近的 7 天，符合复盘的实际语义 | **选中** |
| C：全部交给服务端（永远不传 start/end） | 最简单 | 服务端只有一个默认跨度，用户选不了「近 30 天」还是「近 90 天」 | 部分采纳：默认档 `latest` 就是不传，交给服务端按同样规则定窗口 |

### 3.5 ROI 轨迹怎么画

| 方案 | 取舍 | 结论 |
|---|---|---|
| A：ROI% 与 upl 叠在同一张图的左右两轴 | 一屏看完 | 两者单位不同、采样密度差一个量级，叠在一起会诱导人把它们当同一条曲线的两种刻度读 | 否决 |
| B：ROI 与 upl 各一张图，ROI 画虚线 + 点标记，upl 画实线 | 占两屏高度 | 视觉上直接说清「ROI 是几个离散观测、upl 才是连续心跳」，与 DTO 注释的口径一致 | **选中** |
| C：把 ROI 观测点插值成连续曲线 | 最好看 | 这正是需求大纲 §3.5 点名的伪影制造方式 | 否决 |

### 3.6 展示名（事件 / 门控 / 出场方式）从哪来

前端建一份映射表最省事，但写侧改常量时前端只会**静默显示旧名字**。服务端已经在 `catalog.go` 用写侧常量做 key，改名会编译报错。所以前端一律用返回体里的 `eventLabel` / `gateLabel` / `exitLabel` / `statusLabel` / `depthFidelityLabel`，`constants.ts` 里只留**服务端不返回**的东西：颜色、时间预设、数值格式。

## 5. 影响面与兼容性

- **后端全是追加**：service 结构体加字段、新增一个 error 哨兵、`EnsureTable` 多建两张表、handler 加 5 条 GET。既有 8 条路由与它们的行为一字未动，r9 的测试仍绿。
- **`EnsureTable` 多建两张表**的实际影响：`NewArgusEventHandler()` 在 manager-api 启动时会 `AutoMigrate(episode.Models()...)`。这两张表的所有者仍是 r10 的重建 CLI，读服务永不写入；建表只是为了让页面在「还没跑过派生」时查出空集。与 r9 对 `strategy_event` 的处理同因同写法。

## 7. 遗留项与风险

1. **episode 派生仍需手工重建**（r10 的遗留项，本轮未解决）。页面已经把滞后暴露成一条顶部 Alert（派生到哪一刻 vs 事件表最末、滞后多久），但不解决滞后本身。挂 cron 每日重建还是在读服务里做增量触发，需要单独定。
2. **`fillPriceAvailable` 恒为 false**。逐账户判定表的「均价 / 成交」两列对开仓行永远是「—」，这是埋点缺口不是页面缺陷。要真正补上得改写侧（落交易所下单回执），不在 r13 范围。
3. **聚合接口的行数上限**。`gate-stats` 单次最多扫 200k 行，命中时返回体挂 `truncated`，页面已显式提示「请缩小时间范围」。但**页面不会自动缩窗**——如果测试时选了「近 90 天 + 全部实例」，看到的分布可能是截断的，要按提示重来。
4. **切片对比的开销**。它在信号表与 episode 表上各扫一遍窗口，按需加载已经把它挡在另外两个视角之外，但单次仍然不便宜。窗口开大时会明显变慢。
5. **并发分支冲突面**。r12 在同一分支上并行改 `argus-market/`、`ManagerShell.tsx`、`globals.css` 尾部和 `SignalSliceDTO`。r13 对共享文件只做追加，本轮结束时两边的 Go 与前端构建都是绿的；但如果 r12 后续继续改 `service/argus_event`，需要在合并前再跑一次两个模块的 build + test。
6. **相对窗口锚在 `dataRange.end`**。这个锚是**全库**的最新事件时刻，不区分实例。某个实例停机很久时，锁定它再选「近 1 天」会得到空页——服务端的 `resolveWindow` 在不传时间时是按筛选条件回推的，比前端这个全局锚更准。这是为了让「近 N 天」这几档有确定语义付出的代价，`latest` 档不受影响。
7. **未做**：CSV 导出（原型里有个「导出」按钮，任务说明未列入范围，本轮不做）；从复盘页跳到行情主视图定位触发点的深链（r12 页面尚未落地，等它有了稳定的 URL 参数约定再接）。
