## 1. 需求怎么理解

任务说明给的目标一句话：**一张图看懂什么时候触发、当时行情什么样、为什么触发或没触发。**
我的复述，拆成六件必须做到的事：

1. 引入 lightweight-charts 并**封装成可复用组件**（不是在页面里 `createChart` 一把梭，
   后面 r13 / r14 / r15 还要画图）。
2. 新页面 `src/app/(console)/argus-market/`，结构按原型 `prototype/market.html`。
3. 主图 K 线：周期切换（1m/5m/1h/1d）+ DC 与币安双源对比。
4. 两个副图：偏离（gapBp，**阈值线跟随实例**）+ 净持仓阶梯（**上限线跟随实例**）。
5. 触发点四态标记 + 点击下钻 ±1min 秒级切片抽屉（三条序列 + 说明信号源口径）。
6. 行情缺口空状态与一键回填；**同一分钟内多个触发点须能分别渲染与点选**
   （1m 视图同一根最多叠 5 个）；菜单挂进 `ManagerShell.tsx` 的 Argus 管理分组。

**不做**：实时行情推送。

**我给自己额外定的两条验收线**（来自需求大纲，任务说明没写死但方向明确）：

- 阈值 5bp / 3bp 是**实例属性**，前端一个数字都不许写死——写死等于把 champion /
  challenger 的对照组画错，这是需求大纲反复强调的护栏。
- 任何"看不全"都必须显式说出来（截断、折叠、降级），不能静默。这是 r9 整份设计的
  母题，页面层如果把服务端的自曝字段吞掉，那些字段就白设计了。

## 2. 勘察到的现状事实

### 2.1 数据源已经齐了，本页是纯消费方

r9 的八个接口里，本页用到四个：

| 接口 | 本页用它做什么 |
|---|---|
| `GET /argus-event/filter-options` | 实例与币种下拉（列的是**真有事件数据**的实例） |
| `GET /argus-event/timeline` | 主图 K 线 + 对比源 K 线 + 覆盖率 + 净持仓阶梯（`buckets[].netSizeEnd`） |
| `GET /argus-event/signals?category=trigger` | 四类触发点，按事件行返回、不折叠 |
| `GET /argus-event/signals/:id/slice` | 触发瞬间 ±60s 切片 |

外加两个既有接口：`/argus-config/published`（取该实例的阈值与上限）、
`/klines/backfill-range`（回填缺口）。

**本页不新增任何后端代码。** 这一点在动手前就确认了：`timeline` 的
`ComparePlatformCode` 参数、`CompareKlines` / `CompareCoverage` 返回字段，r9 落地时
就是**为本页的双源对比预留**的（dto.go 里的注释直接写了"r12 行情主视图的双源对比"）。

### 2.2 时间口径：全程墙钟串，不做时区换算

r9 的核心决定是时间全程按**本地墙钟串**走（`2026-08-18 10:30:27`），与 JSONL、
Telegram 消息逐字一致，与数据库连接的 `loc` 无关。

lightweight-charts 的 `UTCTimestamp` 一律按 UTC 渲染坐标轴。所以前端只有一条正确做法：
**把墙钟串当作 UTC 折算**成时间戳。图上刻度显示的就是后端给的那串字，与表格、抽屉
里的时间完全对得上。这个折算全页只有一处（`chartTheme.ts` 的 `wallClockToChartTime`），
所有序列、标记、副图都走它，彼此天然对齐。

唯一的例外是 `/klines/backfill-range`：它按 RFC3339 解析，必须传 `toISOString()`。
两套口径不能互相灌——这一点在 `argus-market.api.ts` 顶部注释里钉死了。

### 2.3 三个必须正视的现实约束

**约束 A：同一分钟最多 5 次触发，且是常态不是异常。**
实测 28.7% 的信号分钟内触发 ≥2 次、承载 48.6% 的全部触发、单分钟最多 5 次、相邻触发
间隔中位 61 秒。这直接否定了"一根 K 线一个标记"的所有画法。

**约束 B：偏离只在触发那一刻被观测到。**
`strategy_event` 的 `gap_bp` 是被生产阈值**结构性截断**过的样本（实测 min = 5.01bp）——
阈值以下的偏离根本不进这张表。所以偏离副图能画的是"这一根里最极端的一次触发有多大
偏离"，**不是**"这一根里偏离的连续曲线"。

**约束 C：阈值与上限是实例属性，且三个实例都不同。**
5bp / 3bp / 3bp，上限 15 / 26+8 / 246。而且实例 2 有两个账户，`timeline` 的净持仓是
**该实例全部账户之和**，所以上限线也必须是各账户 `maxContracts` 之和。

### 2.4 一个与本任务无关、但挡住验证的既有问题

`src/app/(console)/trade-backtest-runs/page.tsx:28` `import dayjs from "dayjs"`，
而 `package.json` **从来没有声明过 dayjs**（`git show HEAD:client/manager/package.json`
里 dayjs 出现 0 次）。dayjs 只是 antd 的传递依赖，pnpm 的 isolated linker 不会把它
链到 `node_modules` 根目录——这是一个典型的 phantom dependency。

后果：`npx tsc --noEmit` 与 `pnpm build` 对**整个应用**报错，我没法验证自己的产出。
处理见 §5.3。

## 3. 考虑过哪些方案，为什么选中最终这个

### 3.1 同一分钟的多次触发怎么画（本轮最关键的决定）

这是任务说明点名的硬要求，也是最容易做错的地方。

| 方案 | 做法 | 否决 / 选中理由 |
|---|---|---|
| A. 一根一个标记，带计数角标 | 同一根聚合成一个标记，标 "×5" | **否决**。点不进去。用户看到"这一分钟触发了 5 次"之后必然要问"哪 5 次、分别什么结果"，聚合标记回答不了，等于把一半的信息挡在门外 |
| B. 自绘 Canvas 覆盖层 | 在图上盖一层自己画标记并做命中测试 | **否决**。要自己同步缩放、平移、DPR、pane 偏移，等于把 lightweight-charts 的坐标系统重写一遍；引入图表库就是为了不做这件事 |
| C. `atPriceTop` / `atPriceBottom` 手工算价格偏移 | 第 k 个标记价格 = high × (1 + k × 0.04%) | **否决**。偏移量是**价格单位**，视图价格跨度变了就散架：跨度几百 U 时看着分得开，跨度 5000 U 时 5 个全糊在一起 |
| **D. 交给 lightweight-charts 的同 bar 堆叠（选中）** | 标记挂在 K 线序列上，`position` 只用 `aboveBar` / `belowBar` | 库自己按 bar 重置堆叠偏移，偏移量是**像素单位**，与价格跨度无关；且每个标记能被单独命中 |

选 D 之前先把库的实现读了一遍确认，不是猜的：
`node_modules/lightweight-charts/dist/lightweight-charts.development.mjs` 的
`SeriesMarkersPaneView._makeValidImpl` 里有

```js
if (marker.time !== prevTimeIndex) {
    // new bar, reset stack counter
    offsets._aboveBar = shapeMargin;
    offsets._belowBar = shapeMargin;
    prevTimeIndex = marker.time;
}
```

`fillSizeAndY` 里 `offsets._aboveBar += shapeSize + shapeMargin`。也就是：**同一根上的
标记按像素向上/向下依次堆叠，换一根就归零**——正是要的行为。

命中测试同样确认过：同一份 bundle 里 `externalId: marker.id`，即 `marker.id` 会原样
透出成 `MouseEventParams.hoveredObjectId`。所以"同一根上叠的 5 个能分别点选"是库的
既有能力，不需要我做任何额外的坐标计算。

配套的三条约束（都落在 `buildMarkers()` 里）：

1. 标记时间必须**对齐到 bar 并且该 bar 真实存在**——库里 `dataByIndex(...)` 返回 null
   的标记直接 `continue` 跳过，静默消失；
2. 按时间升序（堆叠靠 `prevTimeIndex` 的顺序扫描）；
3. 每根上限 5（`MAX_MARKERS_PER_BAR`，取自实测的单分钟最大触发数），
   **超出的计数上报给页面显式提示**，不静默丢弃。

### 3.2 偏离副图：折线还是直方图

| 方案 | 否决 / 选中理由 |
|---|---|
| A. 折线连起来 | **否决**。偏离只在触发那一刻有观测（§2.3 约束 B），连成曲线会让人以为中间那段也被测过。这正是需求大纲最忌讳的那类"图能画、只是不对"的错法 |
| B. 用 `buckets[].maxAbsGapBp` | **否决**。它是**绝对值**，方向丢了。正 = UP、负 = DOWN，方向没了就没法和主图上的开仓方向对上 |
| **C. 直方图，基线 0，取自触发事件的带符号 `gapBp`（选中）** | 离散柱子在视觉上就是"离散观测"，不会被误读成连续曲线；带符号保住方向；颜色按正负分绿红，与主图涨跌同一套色 |

一根 K 线里有多次触发时取**绝对值最大**的那次的带符号值，不取均值——这条副图要回答的
是"这根里最极端的一次偏离够不够阈"，均值会把一正一负抵消掉，看上去像没触发过。
这个口径写在 `toDeviationData()` 的注释里。

另外，偏离副图的数据源刻意**不受"触发点类型"勾选影响**：勾掉"上限跳过"是想在主图上
少看几个标记，不是想改变"当时市场偏离有多大"这个事实。所以组件收两份触发点——
`triggers`（全量，喂副图）与 `visibleTriggers`（筛过，喂标记）。

### 3.3 阈值线 / 上限线：写死还是跟随实例

需求大纲 §4.3 把话说死了：参数分实例是 champion/challenger 实验体系的核心机制。
所以**一个数字都不写死**，全部从 `/argus-config/published` 的已发布快照读：

- 阈值 = 该实例当前币种的 `monitorSymbols[].signalThreshold`；
- 上限 = 该实例 `accountRisks[].maxContracts` 之**和**（因为净持仓阶梯是全账户之和）。

读不到已发布配置时**不画线**，并在筛选条上显示"读取中 / 该实例未发布配置"。宁可不画
也不给个可能是错的默认值——画错的参考线比没有参考线更危险。

**发现的一个真实缺陷（本轮修掉）**：`createPriceLine` 画的线**不参与序列的自动缩放**。
第一版截图里净持仓在 8~20 张之间波动，上限 26 张的线直接被裁到可视区外，完全看不见。
而"离上限还有多少空间"恰恰是这条阶梯唯一要回答的问题。修法是给两个副图挂
`autoscaleInfoProvider`，把阈值 / 上限强行并进取值范围（`widenRange()`）。
这个 bug 只有真跑起来截图才能发现，靠读代码看不出来——见 §5.2。

### 3.4 pane 高度：`setHeight` 还是 `setStretchFactor`

第一版用 `panes[i].setHeight(...)` 依次设 352 / 128 / 104，截图出来偏离副图只有
**约 35px**，被压成一条缝。原因是 v5 的 `setHeight` 是按当前总高换算成占比再重分配，
三个 pane 顺序调用会互相稀释，最后谁也不是设定的高度。

改用 `setStretchFactor(5.5 / 2 / 1.6)`——占比是一次性声明的，不存在互相稀释。
截图复验三个 pane 比例正确。同样是只有跑起来才看得见的问题。

### 3.5 秒级切片的第三条序列（币安）

任务说明要求"展示 DC last / DC mark / 币安 last 三条序列"。

进本轮时后端 `slice.go:103` 只给 1m K 线做参照（`NormalizeKlinePlatform("")` = 币安），
没有币安逐秒。中途上游把 r3 落地了，`SlicePoint.binLast` 出现（§0.2）。

最终实现**同时兼容两种形态**，用 `slice.binPoints`（服务端给的币安非空秒数）判别：

- `binPoints > 0`：画逐秒 `binLast`，实线 + 点标记，图例写"币安 last（参照）"；
- `binPoints === 0`：退回 `slice.klines` 的 1m 收盘，**虚线**，图例写"币安（1m 收盘参照）"，
  正文明确写"这段切片里没有币安逐秒报价……只能看大致走向，不能按秒对齐"。

用不同线型区分两种精度是刻意的：两者差一个数量级，同样画成实线会让人把 1m 折线当成
秒级观测。

顺带按新契约修了一个会**整段错位**的问题：切片的时间原点是 `sliceAnchorTs`
（偏离穿越那一秒），而事件 `ts` 会晚 `anchorLagSec` 秒（信号延迟调度 + 下单往返）。
T0 标记因此挂在 `sliceAnchorTs` 上而不是事件 ts 上，并在快照里把两个时刻和延迟都列出来。

### 3.6 缺口空态与回填：走哪个接口

`/klines/backfill` 以"DB 里最新一根"为基准算增量，窗口整段落在过去时会判成"已是最新"
而一根都不补——那正是本页要补的那种历史空洞。所以走
`/klines/backfill-range`（按窗口覆盖率补）。前一轮的 api 封装已经选对了，本轮沿用并在
页面层把结果讲清楚：

- 汇总写入根数；
- `capped` 的组单独 warning——交易所"最近 N 根"接口够不到太老的窗口，这时**补不动
  不是失败**，混在成功里报会让人反复点；
- `failed > 0` 单独 error。

分两级空态：完全没有 K 线 → 整块 `Empty` + 主按钮（不画半张图，因为触发点挂不上去）；
有 K 线但有缺口 → 顶部 warning 条 + "一键回填"，图照画。

2. **把 `MarketChart` 直接用 `useLightweightChart` 写**——那样 `LightweightChart.tsx`
   这个封装件就没人用了，等于交了一个死代码。改成两处都走 `<LightweightChart>` 的
   children-render 模式，序列层是只跑副作用、返回 `null` 的内部组件。
3. **每个标记都挂文字标签**——同一根上叠 5 个时文字会糊成一片（库的 `offsets` 还会因为
   文字额外累加）。只给选中的那个挂文字。
4. **点表格行就打开抽屉**——点行只做"选中 + 图上定位"，抽屉由"秒级切片"按钮或点图上
   标记触发。浏览触发点列表时不该每点一行就弹一次抽屉。
5. **选中后总是把图滚过去**——只在该 bar 已经**不在**可视区时才移动。否则每点一行图都
   跳一下，反而看不清上下文。
6. **`Descriptions` 用 children 写**——antd 5 已推荐 `items`，改用 `items` 避免
   fragment 子节点的兼容坑。

## 6. 被否决的想法一览（含理由）

1. **同一根聚合成一个带计数的标记** —— 点不进去，丢掉一半信息（§3.1）。
2. **自绘 Canvas 覆盖层做标记** —— 等于重写图表库的坐标系统（§3.1）。
3. **用 `atPriceTop` 手工算价格偏移堆叠** —— 偏移是价格单位，价格跨度一变就散架（§3.1）。
4. **偏离副图用折线** —— 把离散观测画成连续曲线，误导（§3.2）。
5. **偏离副图用 `buckets[].maxAbsGapBp`** —— 绝对值，方向丢了（§3.2）。
6. **一根里的多次触发取偏离均值** —— 一正一负抵消，看上去像没触发过（§3.2）。
7. **偏离副图跟着"触发点类型"勾选变** —— 勾选是想少看几个标记，不是想改变"市场偏离
   有多大"这个事实（§3.2）。
8. **阈值写死 5bp / 上限写死 26** —— 三实例本来就不同，写死等于把对照组画错（§3.3）。
9. **读不到配置时给个默认阈值** —— 画错的参考线比没有参考线更危险（§3.3）。
10. **用 `setHeight` 设 pane 高度** —— 顺序调用互相稀释，实测偏离副图被压到 35px（§3.4）。
11. **币安逐秒与 1m 参照画成同样的线** —— 精度差一个数量级，会被当成秒级观测（§3.5）。
12. **T0 标在事件 ts 上** —— 切片原点是偏离穿越时刻，差 `anchorLagSec` 秒（§3.5）。
13. **走 `/klines/backfill`** —— 以"DB 最新一根"为基准，对历史空洞一根都补不动（§3.6）。
14. **把 `capped` 混进失败里报** —— 窗口太老补不动不是失败，混报会让人反复点（§3.6）。
15. **有缺口时照常画整图不提示** —— 缺口段的触发点会挂不到 K 线上静默消失（§3.6）。
16. **加导出 CSV 按钮**（原型上有） —— 不在任务说明的范围里，不夹带（§3.7）。
17. **`MarketChart` 直接用 hook 建图** —— `LightweightChart.tsx` 会变成死代码（§3.7）。
18. **每个标记都挂文字** —— 同一根叠 5 个时糊成一片（§3.7）。
19. **点表格行就弹抽屉** —— 浏览列表时每点一行弹一次，噪音（§3.7）。
20. **选中后总是滚动图表** —— 每点一行图都跳，反而看不清上下文（§3.7）。
21. **凭空造 page 类型的权限资源** —— 本仓库菜单是硬编码、无权限过滤，r7 / r9 的
    SQL 也都只补 api 资源；造一个没人读的 page 资源只会污染授权树。
