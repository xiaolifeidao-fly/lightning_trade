## 1. 任务目标

把 BADelay500W 仓库 `argus_single` 模块在 `feature/issue#fea0523_64new_login` 分支上的最新业务能力，合并进 lightning_trade 的 `server/argus_single`，同时**完整保留** lightning_trade 已有的「配置入库 + Redis 热加载 + 心跳上报」运行时改造；并把 BADelay500W 根目录下的 `docs/` 与 `logs/` 资料迁入 lightning_trade。

### 关键结论（先看这条）

任务说明里写的「lightning_trade 的 argus_single 基于前几个版本分支开发，少了很多功能」**只对了一半**。实测两边是**双向分叉**：

- BADelay500W 侧独有：趋势闸、偏离采样等 8 月策略补丁（约 1147 行新代码 + 测试）；
- lightning_trade 侧独有：`runtimeconfig`（MySQL+Redis 配置快照与热加载）、`runtimehealth`（心跳）、`market_data`（MarketDataHub）、会话写库钩子、账户风控字段入库、脚本互斥锁重写。这批是 commit `453e52a feat: strategy gate + position monitor + MarketDataHub (P0-P3)` 的产物，且被 `server/manager-api`、`server/service/argus_config` 依赖。

因此**本任务是三方合并，不是目录覆盖**。整目录 `cp -r` 覆盖会直接摧毁 lightning_trade 平台侧的配置管理能力，导致 `server/manager-api` 的 Argus 配置发布链路失效。

**本轮新增：这个三方合并已经被真实跑通了一遍。** 在 `/tmp/argus_trial/`（`server/` 整树副本，仓库本身未动）上完整执行了合并，结果是 `go build` + `go vet` + `go test` 全绿，下游 `server/service`、`server/manager-api` 也照样构建通过。改动面被精确锁定为 **11 个新增文件 + 7 个修改文件，`go.mod`/`go.sum` 零改动**。可复现脚本见 [`design/合并落地方案-已验证.md`](design/合并落地方案-已验证.md)。动作执行阶段照着做即可，不必再摸索合并顺序。

**即「拷贝 script 下的脚本」对其中 5 个文件是空操作**，实际只涉及 `start.sh` / `stop.sh` 两个，且这两个是目标侧更新。

**关键发现 C — 实际部署走 `deploy_1.sh` / `deploy_2.sh`，它们只传二进制（用户本轮确认）**

用户明确说明：每次部署都是调 `deploy_1.sh`（实例 1）/ `deploy_2.sh`（实例 2），远程服务器上早已有 `start.sh` / `stop.sh`。通读这两个脚本，与该说法完全一致：

| 步骤 | 实际行为 |
| --- | --- |
| 1 | `bash build.sh` → `GOOS=linux GOARCH=amd64 go build -o argus_single ./cmd.go` |
| 2 | ssh 建 `REMOTE_PATH=/data/program/app/argus_single`，备份旧二进制为 `argus_single.backup.<时间戳>` |
| 3 | **只 `scp` 二进制一个文件** |
| 4 | 上传 `configs/` 的代码块 —— **整段注释掉** |
| 5 | 上传 `start.sh` / `stop.sh` 的代码块 —— **整段注释掉** |
| 6 | ssh 远程执行 `bash stop.sh` → `chmod +x` → `bash start.sh` → `ps -ef \| grep` 校验 |

两者只差环境变量名：`deploy_1.sh` 读 `argus_single_remote_server` / `argus_single_password` / `argus_single_port`；`deploy_2.sh` 读同名加 `_2` 后缀。远程路径两者相同。

由此得到三个结论，**推翻了上一轮关于 `init.sh` / `lib.sh` 的判断**：

1. **`init.sh` 不在实际部署链路上**，`deploy.sh`（无后缀）也不是在用的那个。上一轮提出的「必须修 init.sh 上传清单」**不再作为本任务的交付项**。
2. **本地的 `start.sh` / `stop.sh` / `lib.sh` / `control.sh` 只是本机开发便利**，永远不会被上传；远程用的是服务器上那套旧的自包含脚本，不 `source lib.sh`，因此**不存在 lib.sh 缺失问题**。本地保留目标新版即可，与远程各行其是，互不影响。
3. **但 configs 同样不会被上传** —— 这引出一个真正会炸的问题，见下。

**关键发现 D — 合并后的二进制直接部署到现网会启动失败（本轮新增，需在部署前处理）**

`deploy_1/2.sh` 只传二进制、不传 configs，而远程 `/data/program/app/argus_single/configs/application.properties` 是**源仓库那一版**，不含 `sqlconn` / `redis.addr` / `redis.password`。合并后的二进制在 `Init()` 里硬性要求这三项（§2.6.3 对比表：`db.Db == nil` 即 `log.Fatalf`）。

后果：`deploy_1.sh` 跑完会显示「上传成功」，随后远程 `bash start.sh` 起进程 → 进程读不到 `sqlconn` → 立刻 `log.Fatalf` 退出 → 脚本第 6 步的 `ps -ef | grep` 查不到进程 → 报「应用启动失败」。**而此时旧二进制已被改名备份，服务处于停机状态。**

处置见 §4.9。

### 2.6.3 仓库里已有的配置模板与补键来源（本轮新增调研）

`server/manager-api/configs/application_dev.properties`（9 行，**已入库**）就是本仓库既有的配置模板，键名与 argus_single 需要的完全一致：

| 键 | 模板中的值 |
| --- | --- |
| `server.port` | `8291`（manager-api 用；argus_single 用 `8855`） |
| `request.path` | `/api`（argus_single 用 `/`） |
| `log.dir` | `./logs/` |
| `sqlconn` | **留空** |
| `redis.addr` | **留空** |
| `redis.password` | **留空** |

三个关键结论：

1. **补键的键名直接照抄这份模板即可**，无需另行约定——`server/manager-api/initialization/initialization.go:55-58` 读的正是 `redis.addr` / `redis.password`，`server/common/middleware/db/db.go` 读的正是 `sqlconn`，与 argus_single 同一套 `common` 中间件。
2. **本仓库已有「模板入库、真值本地」的现成惯例**：`application_dev.properties` 敏感值留空并入库，真实的 `application.properties` 由根 `.gitignore` 的 `*/**/application.properties` 排除。实测确认 `server/argus_single/configs/application.properties` 与 `server/manager-api/configs/application.properties` 均为 IGNORED，而 `application_1.properties` 在加规则前是 TRACKED。§4.7 因此改为沿用这一惯例，模板文件命名统一为 `application_dev.properties`。
3. **模板里的敏感值本来就是空的**，也就是说 `sqlconn` / `redis.addr` / `redis.password` 的真值从来没进过这个仓库，需要用户单独提供（§7.2-3）。

另有一处写法细节已实测澄清：模板里写的是 `sqlconn =`、`redis.addr =`（等号前带空格）。用 viper v1.12.0 实跑验证，properties 解析器会自动裁掉键尾空白，`vipper.GetString("sqlconn")` 能正常取到值，`AllKeys()` 返回的也是 `sqlconn` 而非 `sqlconn `。**这不是 bug，补键时沿用同样写法即可。**

`argus_single` 对基础设施的要求比 manager-api **更严格**，动作执行阶段要注意：

| 组件 | manager-api | argus_single |
| --- | --- | --- |
| MySQL | `db.InitDB()` 失败只 `log.Printf` 并把 `Db` 置 nil，**初始化仍返回 nil**，进程继续 | `initialization.go:27-29` 显式判 `db.Db == nil` → 返回 error → `cmd.go` `log.Fatalf` **退出** |
| Redis | `InitRedisClient` 的 error 会向上抛 | 同样向上抛 → `log.Fatalf` **退出** |

结论：**argus_single 启动硬依赖 MySQL 与 Redis 双双可连**，任一不可达即进程退出，没有降级路径。这决定了 V17 端到端验证必须有真实环境。

### 4.8 script 的处理（本轮新增）

**保留目标版 `start.sh` / `stop.sh` 作为在用脚本**，源版本另存 `script/legacy/`。理由：

1. 目标版实现了 `mkdir` 原子锁（`lib.sh: argus_acquire_lock`）与 PID 归属校验（`argus_pid_is_target`），源版靠 `ps -ef | grep "$APP_PATH"` 匹配进程——后者在同机跑多实例（正是 `application_1`/`application_2` 的场景）时会误杀另一个实例。
2. `control.sh` 依赖目标版语义：它先持锁再置 `ARGUS_CONTROL_LOCK_HELD=1` 调用 start/stop，源版脚本不认这个变量，`control.sh` 的锁协调会失效。
