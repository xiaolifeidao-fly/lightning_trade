## 1. 分域的三条边界

配置从「发布」到「生效」经过三段介质，分域必须三段都做，漏一段就串实例：

| 介质 | 分域手段 | 落地位置 |
| --- | --- | --- |
| MySQL | `argus_config_version.instance_key` + 两个复合唯一索引 | `repository/model.go`、`repository/repository.go` |
| Redis | 键前缀 `argus:config:{instanceKey}:` | `common/middleware/redis/ArgusConfig.go` |
| Pub/Sub | 共用频道 + 消息内 `instanceId` 过滤 | `ConfigVersionMessage` + `runtime.go:handleVersionMessage` |

**为什么 Pub/Sub 不按实例分频道**：`handleControlMessage` 已经确立了「共用频道 + 消息内实例过滤」的范式（`runtime.go` 控制消息分支），配置版本消息照抄同一范式，订阅端不用改 `SubscribeContext` 的频道列表，也不用为新增实例改代码。

## 2. 索引迁移是本次唯一的真实风险点

GORM 的 `AutoMigrate` 只创建**缺失**的索引，对「索引名存在、但列集已经变化」的情况**什么都不做**。本次两个唯一索引都是原名改列：

- `idx_argus_single_published`：`(published_slot)` → `(instance_key, published_slot)`
- `idx_argus_config_version`：`(version)` → `(instance_key, version)`

如果只靠 AutoMigrate，历史库会保留单列唯一索引，第二个实例发布时撞唯一键，而且**代码里看不出来**。

因此 `EnsureTable()` 在 AutoMigrate 之后显式调 `EnsureInstanceScopedIndexes()`：

```
SELECT COLUMN_NAME FROM information_schema.statistics
 WHERE table_schema = DATABASE() AND table_name = ? AND index_name = ?
 ORDER BY seq_in_index
```

列集与期望不符就 `DROP INDEX` + `CREATE UNIQUE INDEX`；相符则跳过（幂等，可反复执行）。新建库走 AutoMigrate 直接建出复合索引，检查随即命中并跳过。

配套 `BackfillInstanceKey(defaultKey)` 把 `instance_key` 为空的历史行归到默认实例——**必须先补齐再建索引**吗？不必：`published_slot` 为 NULL 的行不参与 MySQL 唯一性判定，而历史库最多只有一条 `published_slot = 1` 的行，所以两者顺序无关。当前实现是「建索引 → 补齐」，因为 `EnsureTable()` 里索引迁移在 Repository 层、补齐在 Service 层（需要读 vipper）。

`published_slot` 为 NULL 时 MySQL 唯一索引不做约束，这是「只有已发布版本占槽位」这一设计能成立的前提，改造前后一致。

## 3. 实例键的格式约束

实例键会被拼进 Redis 键，所以 `NormalizeInstanceKey` 限制为 `^[A-Za-z0-9_.-]{1,64}$`：

- 禁冒号：`argus:config:a:b:snapshot` 会和命名空间层级混淆；
- 禁空白：避免键里出现不可见字符；
- 限长 64：与 `instance_key varchar(64)` 对齐。

三份现有 properties 的 `argus.instance.id`（`argus-single-1` / `argus-single-roc` / `argus-single-ives`）都满足。

## 4. 参数校验顺序的一处刻意偏离

仓库既有约定是「先查 `r.Db == nil`」。本次在带实例键的 Repository 方法里把实例键校验**提到 Db 校验之前**：缺实例键是调用方的编码错误，与数据库连通性无关，先报 `ErrInstanceKeyRequired` 能让调用方拿到可行动的错误，也让单测不需要真实 DB 就能覆盖这条路径。

## 5. 三实例导入操作序列

在 `server/manager-api` 目录下执行，每份 properties 跑一次。`--instance` 可省略，命令会读 properties 里的 `argus.instance.id`：

```
# 1. 干跑校验（不写库，不需要密钥）
go run ./cmd/argus-config-import \
  --config ../argus_single/configs/application.properties \
  --session <session.json 路径>

# 2. 正式导入（需要 ARGUS_CONFIG_ENCRYPTION_KEY）
export ARGUS_CONFIG_ENCRYPTION_KEY=<base64 32 字节密钥>
go run ./cmd/argus-config-import --apply \
  --config ../argus_single/configs/application.properties \
  --session <session.json 路径>

# 3. 换 application_1.properties（argus-single-roc）与
#    application_2.properties（argus-single-ives）各跑一次
```

每次导入依次做：读 properties → 解析实例键 → `EnsureInstance` 登记实例 → 按实例检查是否已有发布 → `SaveDraft` → `Publish`。
第二、三次导入不会再被「已有发布」挡住，因为该检查已按实例隔离。

## 6. 管理端接口变化

| 方法 | 路径 | 实例参数 |
| --- | --- | --- |
| GET | `/argus-config/instances` | `?onlyEnabled=true` 可选 |
| POST | `/argus-config/instances` | 请求体 `instanceKey` 必填 |
| GET | `/argus-config/published` | `?instanceKey=` / 请求头 `X-Argus-Instance`，省略走默认实例 |
| POST | `/argus-config/drafts` | query / 请求头 / 请求体 `instanceKey`，省略走默认实例 |
| POST | `/argus-config/versions/:id/publish` | 同上 |

响应新增字段：`ConfigVersionDTO.instanceKey`、`ConfigSnapshotDTO.instanceKey`。均为新增字段，现有前端类型不受影响。

## 7. 已知限制

1. **前端没有实例选择器**（任务范围明确不做）。三实例并存时，前端不传 `instanceKey`，只能操作 `argus.instance.default_key` 指定的那一个。要在界面上切实例，需要一个后续前端任务。
2. **`manager-api/pkg/argus_runtime`（心跳/控制）未纳入本次分域**。它仍读 `argus.instance.id`，未配置时回落 `"default"`——这是改造前就有的行为，属于运行时控制任务的范围。注意它读的键与本次新增的 `argus.instance.default_key` **不是同一个**，两者需要在部署时同时配置。
3. **Redis 旧全局键不会被清理**。`argus:config:snapshot` / `argus:config:version` 改造后无人读写，会等 TTL（24h）自然过期。如需立即清理，手动 `DEL` 这两个键。
