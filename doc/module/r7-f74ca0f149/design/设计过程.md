## 1. 需求怎么理解

任务的一句话目标是：**改参数不误伤其他实例，能确认程序真读到新参数，能看清配置面收敛进度。**

拆成可判定的条款（复述任务说明的【范围】，并标注我对每条的理解）：

| # | 条款 | 我的理解 |
| --- | --- | --- |
| 1 | 强制单实例作用域（不允许全部实例） | 页面顶部有实例选择器，且没有「全部」这个选项；所有读写请求都必须显式带 `instanceKey`，不能让服务端按默认实例兜底 |
| 2 | 参数默认值跟随实例 | 表单初值一律从当前实例的已发布快照里读，前端不得有任何写死的参数默认值 |
| 3 | 参数按域分组并标注真实参数键与需重启标记 | 参数按信号 / 仓位与风险 / 移动止盈分档 / 反向门控 / 趋势闸 / 巡检与告警六域分组；每个参数同时显示 properties 键与 DB 落点；热生效与需重启要能一眼分开 |
| 4 | 生效链路五步可视化含实例命名空间与 30 秒轮询兜底 | 五步的每一步都要有真实的判定依据（不是动画），键名要带实例命名空间；兜底轮询作为说明呈现 |
| 5 | 发布前 diff、关键参数二次确认、极端行情快速下发（含暂停新开仓=order_size 0）、一键回滚 | 四个交互，其中「暂停新开仓」必须落到真实能生效的列上，不能是摆设 |
| 6 | 生效状态以 `argus:heartbeat:<instance>` 的 version/checksum 为准 | 判定条件是 version **和** checksum 双匹配，不是「发布成功=已生效」 |
| 7 | 跨实例同步只生成草稿 | 同步动作产出的是目标实例的 draft，绝不自动发布 |
| 8 | 新增配置面覆盖度面板与账户会话只读巡检 | 两个新面板；会话只读，且不回显明文 |
| 9 | 运行控制只留立即热加载，下线 start/stop/restart 与 `Control()`，保留 `Reload()` | 前端按钮、manager-api 路由、service 方法三层一起下线 |
| 10 | 按 add-permission-resources 补权限资源 | 输出幂等 SQL |

【不做】里两条是硬约束：cookie / token / sentry 不进参数编辑表单；不做参数自动调整。需求大纲 §2.2 还补了一条更强的：**页面上不存在任何能停掉实盘进程的入口**（验收 8）。

三个具体缺陷，勘察时逐个确认过：

1. **无实例作用域**：`fetchPublishedArgusConfig()` 不带任何参数 → 服务端 `ResolveInstanceKey("")` 回落到 `argus.instance.default_key`。三实例部署下，页面上改的永远是同一个默认实例，而且改的人看不出来。
2. **`heartbeat.reloadedAt` 是个永远为空的字段**：Go 侧 DTO 是 `LastReloadAt *time.Time \`json:"lastReloadAt"\``，前端读的是 `reloadedAt`。所以「最后热加载」那一格从来没显示过真实值——一个存量 bug，本轮顺手修掉（改成 `lastReloadAt`）。
3. **生效判定只看版本号**：`drift = runningVersion !== currentVersion`。同一版本号被重新发布（回滚场景）时版本号相同但快照不同，只看版本号会把「还在跑旧快照」判成一致。

## 3. 考虑过哪些方案

### 3.1 参数编辑器怎么组织：三个方案

**方案 A：继续用 Ant Design `Form` + `Form.List`，照 ConfigEditor 的写法加一个「参数」页签。**
- 代价：参数是跨表的（`argus_config` / `argus_monitor_symbol` / `argus_account_risk` / 三个 JSON 列），`Form.Item name={[...]}` 的路径要能表达「第 2 个账户风控的 trailing JSON 里的 large_activate」——Form 的 namePath 表达不了 JSON 列内部的路径，得为每个 JSON 列写自定义 `getValueProps` / `normalize`，很快就比手写状态更绕。
- 而且 diff 需要「已发布基线 vs 当前草稿」的逐项比较，Form 只有一个 store，得再维护一份基线副本。
- **否决**：Form 在这里没有带来收益，只带来路径表达上的绕。

**方案 B（选中）：把参数抽成一张显式的「参数目录」元数据表，用受控组件渲染，草稿以 `overrides` 形式独立存放。**
- 每个参数声明 `carrier`（落到哪张表的哪一列 / 哪个 JSON 键）、`propertyKey`、`storeKey`、`hot`、`critical`、`pendingRuntime`、`scale`。
- 读：`readParam(param, snapshot, ctx)`；写：`applyParam(draft, param, value, ctx)`。
- 草稿是 `Record<overrideKey, ParamOverride>`，`overrideKey` 把账户 / 币种下标编进去，切账户不丢改动。
- 发布时 `buildDraft(snapshot, overrides, note, instanceKey)`：深拷贝已发布快照 → 套用 overrides → 提交。
- 好处：①「真实参数键」「需重启」「关键」「运行时待打通」这些标注和参数定义放在一起，不会漂；② diff 是 `overrides` 与快照读值的直接比较，天然精确；③ 增删参数只改一处数据。

**方案 C：后端出一个「参数视图」接口，前端只渲染。**
- 好处：参数目录成为服务端契约，回测页（r14）也能复用。
- 代价：要新造 DTO、新造 handler、新造服务端参数目录，且 r5 马上要改 DB 列结构，这套契约会在 r5 落地时全部重写。
- **否决**：现在做等于给一个已知要变的结构提前上锁。等 r5 定下最终列结构后再抽服务端契约更划算，此刻放在前端 `params/catalog.ts` 里，迁移成本只是搬一个文件。

### 3.2 r5 没做完，DB 没列的 9 个参数怎么办：三个方案

- **否决**：交付物残缺，且任务范围写的是「参数按域分组并标注真实参数键」，不是「只做已有列的参数」。

**方案 B：本轮顺手把 9 个 DB 列加上。**

- **否决**：越界，且制造合并冲突。

**方案 C（选中）：用 DB 里**已经存在**的三个 JSON 列作为这批参数的载体，键名沿用 properties 的真实键名；同时给每个这类参数打上「运行时待打通」标记。**
- `argus_config.extra_config_json` ← 全局级（`trade.signal.delay_seconds`、`monitor.spread.max_price_age_ms`、`position.risk.contract_face`、`trade.trend_gate.window_hours`、`trade.trend_gate.threshold_pct`）
- `argus_account_risk.extra_risk_json` ← 账户级（`reverse_gate_min_profit_pct`）
- `argus_account_risk.trailing_stop_tiers_json` ← 移动止盈 8 项（importer 已经在往这里写，键名现成）
- 好处：零 schema 变更；参数值真的进了配置版本快照（可发布、可 diff、可回滚、可审计）；r5 落地时只需要决定「读 JSON 还是读新列」，页面这层不用动。
- 代价：这批值现在写进去**不会改变策略行为**。这是必须诚实呈现的事——所以有了 `pendingRuntime` 标记：字段旁边有蓝色「运行时待打通」标签，改动预览里会单独列一段警告「会写进快照但 argus_single 还没消费，改完不会改变策略行为」。

### 3.3 「一键回滚」怎么做：两个方案

任务说明写「后端 `rollbackPublishedVersion` 已有」，但代码事实是它是 `Publish` 内部的**补偿路径**（发布后广播失败时把 published 槽位翻回去），私有、无接口、语义也不是「回滚到任意历史版本」。所以这条得自己实现。

**方案 A：回滚 = 把历史版本的内容复制成一个新草稿，再走一次发布，生成新版本号。**
- 好处：版本序列严格单调，审计上「什么时刻生效的是哪个版本号」永远唯一。
- 代价：回滚一次多一个版本号；而且要把历史快照反解成 `SaveConfigRequest`（含逐项搬运凭证），链路长、失败面大。

**方案 B（选中）：回滚 = 把那条已归档版本的不可变快照重新推上 published 槽位，不新建版本号。**
- 版本快照本来就是不可变的（`argus_config_version` + 子表按 `config_version_id` 固化），重新发布它就是回滚。
- 实现上与 `Publish` 是同一条链路：写 Redis 快照 → 翻 published 槽位（先归档当前 published）→ 广播。差别只有源版本的合法状态：发布要求 `draft`，回滚要求 `archived`。
- 于是把 `Publish` 的主体抽成 `activateVersion(ctx, instanceKey, versionID, fromStatus, releaseNote, actor)`，`Publish` 传 `draft`、`Rollback` 传 `archived`。**没有复制粘贴出第二条发布链路**——这点很重要，两条发布链路早晚会漂。
- 附带好处：`fromStatus = archived` 天然挡掉「回滚到当前正在生效的版本」（它的状态是 `published`，查不到，返回 `ErrArchivedVersionNotFound`）。
- 代价：同一个版本号会被发布两次，两次的 `snapshot_checksum` 可能相同。这正是 §3.4 要求心跳同时上报 checksum 的原因之一。

### 3.4 生效判定：只看版本号 vs 版本号 + 校验和

只看版本号在回滚场景下会误判：v36 → v37 → 回滚到 v36，中间那次 v37 若热加载失败，心跳里的 version 可能仍是 36，与回滚目标 36 相同，页面会立刻显示「已生效」，而进程其实从来没重新读过快照。

选择：给 `ArgusHeartbeat` 加 `ConfigChecksum`，判定条件是 `version 相同 && checksum 相同`。

对老构建的兼容：`configChecksum` 为空时退化成只比版本号，并在「快照校验和」瓦片下方明说「该实例心跳未上报校验和（旧构建），当前只按版本号判定」。**不静默降级**。

实现路径上还有一个小选择：`Manager.reloadObserver` 的签名是 `func(version uint64, err error)`，要带 checksum 有两条路——
- 改签名成 `func(version, checksum, err)`：要动 `notifyReload` 的 8 个调用点，还会波及 r4 已经挂在这个 observer 上的 eventstore 回调。
- **选中**：不改签名，在 `initialization.go` 的观察者里读 `runtimeManager.Current().Checksum`。`apply()` 是「先写 `m.current` 再回调」，成功时 `Current()` 已是新快照；失败时它仍是**正在运行的旧快照**——而这恰好就是心跳该上报的「程序实际读到什么」。语义上比透传更准，改动面还小得多。

### 3.5 跨实例同步：拿谁的快照做底

第一版我写成「用**源**实例的快照 + 改动 → 提交到目标实例」，写完立刻发现这是个严重错误：源快照里带着源实例的账户、UID、API Key、会话，提交过去就是**把 A 的账号覆盖到 B 上**。

改成：拉取**目标**实例自己的已发布快照，只把参数 overrides 套上去。账户、凭证、会话全部保持目标实例原样。

还有一个衍生问题：实例1 有 2 个账户，实例2/3 各 1 个。账户级改动的 `riskIndex=1` 在目标实例上不存在，`applyParam` 会静默 no-op——那会让人以为同步全量成功了。所以加了 `splitApplicableOverrides()`：落不下的参数被摘出来，前端用一条黄色提示把它们的名字列出来。**静默丢弃比报错更危险。**

### 3.6 配置面覆盖度的数据从哪来

**方案 A：后端探测接口。** 探测不出「DB 有列但代码不读」——那要静态分析 `runtimeFromSnapshot` 的赋值。**否决：做不到。**

**方案 B（选中）：前端静态审计清单 `params/coverage.ts`。** 明确标注这是人工审计结论、来源（需求大纲 §3.2）、审计时点（2026-08-31），并在面板底部写清「收敛进度由 r5 推进，变化时同步更新 `params/coverage.ts`」。宁可标注它是快照数据，也不要伪装成实时探测。

### 3.7 会话只读巡检怎么显示凭证

原型显示「950 字符」。但服务端 `sessionDTO` 把 cookie 掩码成 `"******"`，前端拿不到长度。

选择：给 `RuntimeSessionDTO` 加 `cookieLength` / `tokenLength` / `otokenLength`，服务端 `secretLength()` **只回长度不回内容**。运维要判断的是「有没有、是不是被截断了」，长度足够；回显 950 字符的 cookie 只会扩大泄露面。空值返回 0（页面显示「未回写」）。

注：凭证已改为明文入库（见需求大纲 §决策记录），所以这里不再有「解密失败」这一分支；掩码与只回长度这两条约束保留不变——库里明文是给运维手改用的，接口仍不吐真值。

### 3.8 会话从编辑表单里拿掉后，发布会不会把登录态发丢

这是个差点踩到的坑。`ArgusRuntimeSession` 行是按 `account_id` 建的，而账户行每次存草稿都是新建（版本作用域）。如果表单不再提交 `sessions`，`saveChildren` 就不会为新版本的账户 id 建会话行 → `runtimeAccount()` 拿到 `session = nil` → cookie / token 为空 → **热加载后登录态直接丢失**。

处理：会话从 UI 上拿掉，但**数据仍原样带上**——
- `buildDraft()` 深拷贝时把 `snapshot.sessions` 一起带进草稿；
- `ConfigEditor.submit()` 显式 `{ ...values, instanceKey, sessions: snapshot?.sessions ?? [] }`，不依赖 antd Form store 会不会保留未注册字段这种隐式行为。

掩码值 `"******"` 由服务端 `preserveSecret()`（`secretOrEmpty` 把 `"******"` 当空）从已发布版本还原成明文，链路与改造前一致。

## 6. 还剩什么风险与待确认项

1. **r5 未完成是本任务最大的悬空依赖。** 三处直接影响：
   - 参数目录共 25 项，其中 **17 项打了「运行时待打通」**（trail 8 + 巡检告警 3 + 信号域 2 + 趋势闸 2 + 反向门控最低盈利 1 + 合约面值 1）。这些参数改完能进快照、能 diff、能回滚，但**不会改变策略行为**。真正改完立刻生效的只有 8 项：信号阈值、价差阈值、风险预算、兜底止损、仓位上限、单次下单张数、反向门控开关（服务端口需重启）。
   - 30 秒兜底轮询不存在。页面把它作为设计说明呈现，并明确写了「轮询本身由 r5 交付；在它上线前，漏消息只能靠上方『立即热加载』手动补」。需求级验收 5 的「发布瞬间断开 Redis 订阅，30 秒内参数仍能自行补上」**本轮不成立**。
   - r5 落地时若给这 9 个参数加了独立 DB 列，`params/catalog.ts` 里对应参数的 `carrier` 要从 `configExtra` / `riskExtra` 改成 `config` / `risk`，并去掉 `pendingRuntime`。改动集中在一个文件，但**必须改**，否则会出现「新列和 JSON 里各存一份、以哪份为准不确定」。这条要写进 r5 的收尾检查。

2. **`extra_config_json` 的并发写风险。** 参数页与「完整配置」页签都能写 `extraConfigJson`：前者按键合并（`parseJsonMap` → 改键 → 序列化），后者是整段文本框覆盖。两个页签在同一次会话里各改一次，后发布的会覆盖先发布的。目前两者都走「读已发布快照 → 改 → 发布」，最后写的赢，与既有配置编辑的语义一致，没有额外恶化；但如果 r5 之后 `extra_config_json` 变成重要载体，值得考虑把完整配置页签里的 JSON 文本框改成只读。

3. **回滚复用版本号带来的审计歧义。** 同一个版本号可能有多个 `published_at`。`argus_config_version` 只保留最后一次的 `published_by` / `published_at`，历史发布次数没有留痕。当前靠 Redis 的 `argus:config:<instance>:snapshot:<version>` 与心跳 checksum 侧面还原。如果后续需要严格的发布流水，得单独加一张发布事件表——**不在本轮范围**，记在这里。

4. **`splitApplicableOverrides` 只按下标判断账户是否存在**，不校验「目标实例的第 2 个账户是不是语义上对应的那个账户」。实例1 的账户 A/B 与实例2 的单账户之间没有稳定的对应关系，跨实例同步账户级参数本身就需要人判断——所以同步结果只生成草稿、必须切到目标实例确认后再发布，这一层人工闸是有意保留的。

5. **权限 SQL 的 `role_id` 未经确认。** 文件里默认 `1`，执行前需要人确认目标角色。

6. **`trade-backtest-runs/page.tsx` 有一个存量编译错误**：`Cannot find module 'dayjs'`。`dayjs` 没有列进 `package.json`，在 pnpm 严格 node_modules 下解析不到。该文件本轮未改动（`git log` 显示最后一次改动是上一个提交 `9a59edc`），属于既有问题，与本任务无关，未处理——但它会让 `next build` 失败，需求级验收 9「既有页面无回归」要跑通得先补这个依赖。

## 补记（2026-09-09）：§3「生效判定只看版本号」的隐患已在运行侧修掉

本文档指出过：

> 生效判定只看版本号：`drift = runningVersion !== currentVersion`。同一版本号被重新
> 发布（回滚场景）时版本号相同但快照不同，只看版本号会把「还在跑旧快照」判成一致。

这个判断是对的。2026-09-09 的重构把 Argus 运行侧的变更检测从版本号换成了**派生运行
配置的内容指纹**（`sha256`），上述场景以及「运维直接改库不动 version」都能被检测到。
详见 `doc/requirements/req-1787224869197/需求大纲.md` §决策记录：配置不经 Redis 缓存。

管理端的漂移展示（`runningVersion` vs `publishedVersion`）口径未变——它反映的是
「实例上报的版本」与「已发布版本」，仍是给人看的近似指标；真正决定是否切换配置的
是实例侧的指纹比对，不再依赖这个比较。

另外本文档 §5 描述回滚「与 `Publish` 是同一条链路：写 Redis 快照 → 翻 published
槽位 → 广播」，其中**写 Redis 快照这一步已删除**。回滚链路现在是：翻 published 槽位
（先归档当前 published）→ 发布变更通知（可选加速）。发布与回滚的状态机差别不变：
发布要求源版本为 `draft`，回滚要求 `archived`。
