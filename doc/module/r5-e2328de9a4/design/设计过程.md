## 1. 需求怎么理解

任务要做三件互相咬合的事，优先级不同：

1. **修一个功能性故障（最高）**：切到 DB 配置驱动后，`runtimeAccount()` 不读
   `extra_risk_json`，`TradeLogic` 停在空串，被 `normalizeTradeLogic` 归一化成
   `spread`，`manager.go` 的 `IsSignalLogic()` 分支永远不进。**整套盘口信号策略静默
   失效，且不报任何错**——程序照常运行、心跳照常上报、日志一片正常，只是不再按
   盘口信号开仓。`variant` 同理为空，champion/challenger 归因彻底失灵。
2. **补一个静默漏洞（次高）**：`argus:config:changed` 是即发即弃的 Redis pub/sub。
   订阅断线重连窗口内发布、Redis 主从切换、客户端缓冲区溢出，任一情况都会丢消息，
   结果是「发布成功 + 程序跑旧参数 + 谁都不报错」。要一条不依赖 pub/sub 的兜底通道。
3. **把配置面补齐（主体工作量）**：properties 63 键里，4 个必须留（连库前置的
   `sqlconn`/`redis.addr`/`redis.password`/`argus.instance.id`），13 项「DB 有列但值
   到不了运行时」，9 项「DB 完全没有列」。剩下的已经通了。

边界（任务说明的【不做】+ 需求大纲 §2.2）：不做远程 start/stop/restart，不引入 agent，
不改进程启停方式；紧急刹车走 `order_size=0`；`argus.build.version` 与 `argus.heartbeat.*`
不收敛；不改任何策略判定逻辑。前端参数编辑页是 r7 的事，本轮只保证字段能进出。

      → commonRedis.ReadConfigSnapshot(instanceKey)   命中即用

热更新路径：`handleVersionMessage` →（r1 已加的实例过滤）→ `loadCurrent` → `apply` →
`applyRuntimeConfig`（`trade.ReplaceManager` + `monitor.ReloadMonitor`）→ `notifyReload`
→ 心跳上报 version+checksum。

### 2.3 顺带查出来、需求文档没写的两个事实

1. **`importer.go` `importRisk()` 只读全局 `position.risk.budget_pct` 与
   `position.monitor.catastrophe_stop_pct`**，忽略 `trade.accountN.budget_pct` /
   `trade.accountN.catastrophe_stop_pct`。`application_1.properties` 的
   champion(cap26/S400) 与 challenger(cap8/S400) 差异会在导入时被抹平——
   验收标准 6.1-3「三实例 RiskParamsView 与 properties 逐项一致」直接过不了。
2. **`argus_account.position_mode` 的 CHECK 约束只收 `net`/`hedge`**（导入把
   `bidirectional` 归一化成 `hedge`），而 `pkg/trade` 用的是 `bidirectional`。
   不做反向翻译，双向持仓账户会走进「信号逻辑强制改 net」的告警分支。

### 2.4 一个被我判定为「我的改动引入的新风险」的点

`NewTradeManager` 校验风险参数不过时是 `logrus.Fatalf`。收敛前 trail 档位只来自
properties、在进程生命周期内不变，Fatalf 只可能在启动时触发；收敛后它们变成可热更新项，
**一次误发布会在热加载瞬间打死正在扛仓的进程**——比参数不生效危险得多（停进程后持仓
仍挂在交易所，但移动止盈、兜底止损、平仓监控全失效，这正是需求大纲否决远程 stop 的理由）。

## 3. 考虑过的方案与取舍

### 3.1 参数怎么从 DB 送到运行时

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| A. 全部 `vipper.Set` | 加载快照后把每个键（含 `trade.accountN.*`）写回 viper | 改动最小，`AccFloat` 一行不用动 | ❌ 否决。① 账户被删/改名后旧的 `trade.accountN.xxx` 键留在 viper 里永不消失，下一版配置会读到幽灵值；② viper 是全局 map，无法表达「这一版没配这个键」；③ 任务明确要求改 `AccFloat` 内部 |
| B. 改 `AccFloat` 签名，显式传快照 | `AccFloat(snapshot, index, name, ...)` | 语义最清楚 | ❌ 否决。13 个调用点全要改，且 `resolveTrailParamsForAccount`、`resolveCapParams`、`trend_gate.go` 都在 leaf 位置，要把快照一路穿下去；任务也明确要求「签名不变」 |
| C. 包级覆盖层 + 保持签名 | `trade.SetParamOverrides()` 装一层 map，`AccFloat` 先查它再回退 viper | 覆盖层每次热加载整体重建，"取消一个参数"能干净退回；签名不变，调用点零改动 | ✅ 选中 |

**但 C 覆盖不了直接 `vipper.GetX` 的键**（`contract_face`、`signal.delay_seconds`、
`max_price_age_ms`、`trend_gate.window_hours`、巡检间隔与盈亏阈值——这些不走 `AccFloat`）。
所以最终是**两条通道**，按「运行时怎么读它」分：

- 走 `AccFloat` 的（账户级参数 + 两个 `AccFloat` 全局键）→ **覆盖层**，整体重建；
- 直接 `vipper.GetX` 的全局标量 → **`RuntimeTuning` + `vipper.Set`**。

`vipper.Set` 不可撤销这个问题，用「首次写回前抓一份 properties 原值」解决：
`setTuningValue(key, 0)` 写回的是抓下来的 properties 值，而不是 0。这样两条通道的
「DB 未配置 → 退回 properties」语义是一致的。

### 3.2 `order_size` 放哪张表

考虑过 `argus_account`（它是账户身份表）。最终放 `argus_account_risk`：`ValidateRiskParams`
把 `order_size` 和 `max_contracts_ceiling` 放在一条约束里校验（`1 ≤ order_size ≤ ceiling`），
两个值分居两张表会让校验要跨表取数。

### 3.3 `extra_risk_json` 解析失败怎么办

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 解析失败 → 记 Warn，按空值继续 | 与现状一致，不会拒绝快照 | ❌ 否决。空值 → `spread` → 策略静默失效，**这正是本任务要修的失效模式**，不能用同一个模式去兜它 |
| 解析失败 → 返回错误，拒绝这份快照 | 热加载路径 `apply` 失败 → 继续跑当前配置；启动路径直接启动失败 | ✅ 选中。失败方向是安全的：宁可不换配置，也不要换成一份策略被悄悄降级的配置 |

`extra_risk_json` 为**空串**不算错（手工建的行可能没有），但打 Warn 并在启动日志里
打印 `logic=`，让它可见而不是静默。

### 3.4 巡检间隔/阈值怎么热生效

`AccountMonitor` 是 `sync.Once` 单例，构造时读一次 vipper。三个选项：

- 归进 `restartRequired` → ❌ 与任务说明冲突（restartRequired 只能是三项），且重启会让持仓失去看管；
- 照 `ReloadMonitor` 的样子整体热替换 → ❌ 会丢掉 trail 峰值状态、告警冷却表、UPL 缓存、平仓连败计数，代价远大于收益；
- ✅ 就地改参数：三个字段加 `paramMu sync.RWMutex` + 访问器，`ApplyParams()` 写；持仓轮询循环每轮比对间隔，变了就 `ticker.Reset`。

字段原本是裸读裸写，持仓轮询 goroutine 一直在读，不加锁就是 data race，所以访问器不是装饰。

### 3.5 兜底轮询的判定口径

- 只比 `argus:config:version:<instance>` 的**版本号**（任务说明的口径），不比 checksum。
  同一版本号被重新发布（checksum 变）只能靠 pub/sub 感知——记在 §7 遗留项。
- Redis 读不到（`redis.Nil` / 连接失败 / 内容非法）一律**回落查库** `FindPublishedContext`。
  兜底通道自己不能依赖单点。
- 发现落后后**先 `loadCurrent` 再比对**，只有快照确实更新了才 `apply`。
  否决过「发现落后就直接 Reload」：版本键已前进但快照还没写好的窗口里，
  那样会每 30 秒空转一次 `ReplaceManager`（重建全部交易客户端 + 价格监控器）。

### 3.6 `ResolveRiskEquity` 的短路要不要拆

原代码 `if acc.RiskBudget > 0 { return acc.InitialBalance }` 是 DB 驱动下防止 properties
的 `risk_equity` 漏进来的临时补丁。`risk_equity` 有了自己的列之后，`AccFloat` 的
「DB 优先 vipper 兜底」已经表达同一件事，短路反而会把 DB 里显式配置的 `risk_equity` 挡掉。
拆掉。行为等价性由「导入把 properties 的 `risk_equity` 写进 DB」保证。

### 3.7 `order_size=0` 紧急刹车：本轮不做，说明理由

需求大纲把 `order_size=0` 当作远程 stop 的替代品。但现状 `GetOrderSize()` 把
`≤0` 当「未配置」并兜底成 1，所以**配 0 等于配 1，刹不住车**。要让它真正暂停开仓，
必须改 `manager.go` 的开仓判定分支——那属于「不改任何策略判定逻辑」的禁区，也超出本任务
【范围】。本轮只把列加上，语义保持 `0 = 未配置`，作为待确认项交回（§7）。

## 4. 方案怎么落到改动

### 4.1 数据层（`server/service/argus_config`）

- `repository/model.go`
  - `ArgusConfig` +6 列：`contract_face`、`signal_delay_second`、`spread_max_price_age_ms`、
    `trend_gate_window_hour`、`trend_gate_threshold_pct`、`reverse_gate_min_profit_pct`；
  - `ArgusAccountRisk` +4 列：`order_size`、`risk_equity`、`reverse_gate_min_profit_pct`、
    `trend_gate_threshold_pct`。
  - 迁移方式：沿用 `EnsureTable()` 的 `AutoMigrate`。全部是新增列且带 `default:0`，
    历史行不需要回填脚本——0 的语义就是「未配置，回退 properties」，与旧行为一致。
- `dto/dto.go`、`service.go` 的 `configEntity/configDTO/riskEntity/riskDTO`：同步 10 个字段。
  管理端接口不用改签名，字段跟着快照 DTO 走，r7 的编辑页直接能用。
- `importer.go`：
  - 6 个全局项 + 4 个账户级项从 properties 读入，缺省 **0（未配置）** 而不是运行时默认值——
    写默认值会把「没配」变成「显式配了默认值」，破坏兜底语义；
  - 修 §2.3-1：`RiskBudget` / `CatastrophicStopLoss` 改成「账户级优先、全局兜底」，
    与运行时 `AccFloat` 的解析顺序对齐。

### 4.2 参数覆盖层（`server/argus_single/pkg/trade`）

- 新增 `param_overrides.go`：`ParamOverrides{Global, Accounts}` + `SetGlobal/SetAccount`
  + 包级 `SetParamOverrides()`（装载时 `clone()`，避免与调用方共享 map）+ `lookupParamOverride()`。
- `account_params.go`：`AccFloat` 开头查覆盖层，命中即返回；未命中走原来的
  账户键 → 全局键 → 默认值链路。`AccInt` 不动（它调 `AccFloat`）。
- `config.go`：抽出 `NormalizeAccountConfig()`，properties 与 DB 两条路径共用；
  新增 `StopLossMode` / `Baggage` 字段与 `StopLossModeCatastrophic` 常量。
  **共用归一化是防止两条加载路径行为再次分叉的结构性措施**，比在 DB 路径里
  照抄一遍默认值可靠。
- `risk_params.go`：拆 `ResolveRiskEquity` 短路；`logStaticRiskParams` 增打
  `logic/variant/sl_mode`；新增 `ValidateAccounts()`（可返回错误的预校验，见 4.4）。
- `manager.go`：风险参数打印从「仅 trailing 账户」放开到全部账户，fail-fast 仍只对
  trailing 生效。这一行是验收标准 6.1-3 的现场证据。
- `session_store.go`：`applySessionAccountData` 回填 `Baggage`；`Save()` 在 entry 缺
  `Baggage` 时从 `AccountConfig` 补——闭合「DB → 运行时 → 再回写」的环。

### 4.3 快照转换与生效（`server/argus_single/pkg/runtimeconfig`）

- 新增 `tuning.go`：`RuntimeTuning` 结构、`setTuningValue`（带 properties 兜底快照）、
  `applyTuning`、`snapshotTuning`、`globalParamOverrides`、`accountParamOverrides`、
  `parseExtraRisk`。
- `runtime.go`：
  - `RuntimeConfig` +`Tuning`+`Overrides`；
  - `runtimeFromSnapshot` 逐账户建覆盖层；
  - `runtimeAccount` 消费 `extra_risk_json` / `stop_loss_mode` / `order_size` / `baggage`，
    `position_mode` 反向翻译，末尾调 `trade.NormalizeAccountConfig`；
  - `applyRuntimeConfig` 顺序固定为
    **覆盖层 → 全局标量 → 预校验 → ReplaceManager → ReloadMonitor → ApplyAccountMonitorParams → Telegram**。
    顺序有强约束：`NewTradeManager` 与 `NewPriceMonitor` 都在构造时把参数读走，晚一步就是「换了配置跑旧参数」；
  - 新增 `hotApplied()` 与原有 `restartRequired()` 配对，日志上把「已热生效」和「需重启」分开说；
  - 新增 `pollPublishedVersion` / `reconcilePublishedVersion` / `publishedVersion`，
    由 `Start()` 与订阅协程一起拉起，周期 `defaultVersionPollInterval = 30s`。

### 4.4 我引入的风险的兜底

`applyRuntimeConfig` 在装好覆盖层之后、`ReplaceManager` 之前插一道
`trade.ValidateAccounts(next.Trade)`：不合法就**把覆盖层与全局标量回滚回当前配置**
并返回错误，`apply` 失败 → 继续跑旧配置 → 心跳如实上报旧版本。
这样 `NewTradeManager` 的 `Fatalf` 在热加载路径上不可达，只保留在启动路径。

### 4.5 影响面与兼容性

- **旧库**：10 个新列全部 `default 0`，`AutoMigrate` 自动加列，不需要数据迁移。
  未导入新值时全部为 0 → 覆盖层为空 → `AccFloat` 与 `vipper.GetX` 全部走 properties，
  **行为与改造前逐字节一致**。
- **旧 properties 部署**：`LoadConfigFromProperties` 路径只是把内联的默认值块换成
  `NormalizeAccountConfig` 调用，逻辑等价（唯一差别是 warn 日志里的账户序号从循环变量
  `i` 改成 `account.Index`，取值相同）。
- **管理端接口**：只增字段不改签名，现有前端不传新字段时按 0 存，即「未配置」。
- **r7（参数编辑页）**：`ConfigDTO` / `AccountRiskDTO` 已带全部新字段，可直接渲染。
- **不改动**：策略判定逻辑、进程启停方式、心跳协议、Redis 键格式、实例分域口径（r1 的产出全部沿用）。

## 6. 被否决的想法（存档）

1. **把 63 个键做成通用 KV 表**（`argus_config_kv(instance, key, value)`）：省掉加列，
   但会失去类型、CHECK 约束和 DTO 校验，参数编辑页只能渲染成一张裸表格，
   与 r7 的原型（分组表单 + 二次确认）冲突。否决。
2. **让 `AccFloat` 直接查 DB**：每次解析一次查询，`resolveTrailParamsForAccount`
   在持仓轮询里每 5 秒对每个账户调 10 次。否决（且违反「写库失败不得阻断交易路径」）。
3. **轮询改成订阅 Redis keyspace notification**：要求服务端开 `notify-keyspace-events`，
   是部署侧的隐式依赖，而且它本身还是 pub/sub，同样会丢。否决。
4. **轮询周期做成可配置项**：又是一个要收敛的配置键，且它是「配置系统自己的兜底」，
   不该依赖被兜底的配置系统。用常量。
5. **热加载时整体重建 AccountMonitor**：见 §3.4，会丢 trail 峰值与冷却状态。否决。
6. **`stop_loss_mode` 支持 `off` / `tight`**：属于改策略判定逻辑，且紧止损已被实测否定
   （−150% 会杀死全部 22 个反转获利 episode）。只做「读进来 + 打印 + 非法告警回退」。

## 7. 遗留风险与待确认项

1. **`order_size=0` 刹不住车**（§3.7）。需求大纲把它当紧急刹车，但 `GetOrderSize()`
   把 0 当未配置兜成 1。要真正生效必须动开仓判定分支，超出本任务范围。
   建议在 r7 一并决策：要么改 `GetOrderSize` 语义 + 开仓前置判断，要么在参数页明确
   「暂停开仓」是独立开关而不是 `order_size=0`。
2. **同版本号重新发布（checksum 变）兜底轮询感知不到**：轮询只比版本号。发布方
   `NextVersion` 按实例递增，正常不会复用版本号；但回滚会沿用历史版本号，回滚 → 再回滚
   的场景下若 pub/sub 恰好丢消息，要等下一次发布才会纠正。
3. **`argus.build.version` 与 `argus.heartbeat.*` 未收敛**（任务明确不做），
   它们仍只能改 properties + 重启。
4. **`trailing_stop_tiers_json` 目前每个账户存的是同一份全局 trail**（导入时按
   `position.monitor.trail.*` 前缀抓，不区分账户）。列本身是账户级的，改成逐账户
   不同的档位只需要在参数页填不同值即可生效，但导入不会自动产生差异。
5. **`vipper.Set` 的 properties 兜底快照在进程内只抓一次**：如果有人在
   `ApplyInitial` 之前就 `vipper.Set` 了这些键，抓到的就不是 properties 原值。
   现有初始化顺序（`vipper.Init` → `db` → `redis` → `runtimeconfig.Initialize` →
   `ApplyInitial`）满足前提，新增初始化步骤时要留意。
6. **`server/service/argus_event/` 与 `server/manager-api/cmd/argus-*` 是并行任务的
   未跟踪工作区文件**。本轮开始时它们编译不过（`s.episodeRepository undefined`），
   期间被对方修好；本轮结束时四模块全绿。它们不属于本任务改动。

## 补记（2026-09-09）：缓存优先路径已被移除

本文档 §2 记录的加载链路

```
commonRedis.ReadConfigSnapshot(instanceKey)   命中即用
→ 未命中回落 repo.FindPublished / LoadSnapshot，再回写 Redis
```

**已不再成立**。配置改为「数据库唯一来源 + 定时内容指纹比对」，Redis 不再缓存快照，
详见 `doc/requirements/req-1787224869197/需求大纲.md` §决策记录：配置不经 Redis 缓存。

本任务当时识别的核心问题——「`argus:config:changed` 是即发即弃的 pub/sub，漏消息就
静默跑旧参数」——判断完全正确，本次重构沿用并加强了这个结论：兜底轮询保留，但比对
依据从**版本号**换成**派生运行配置的内容指纹**。原因是只比版本号覆盖不了两种真实场景：
运维直接改库（每周轮换 cookie/token）不动 `version`；回滚时同一版本号被重新发布
（后者 r7 的设计文档 §3 也已指出）。

本文档 §3.2 关于「热加载失败方向必须安全——宁可不换配置，也不要换成被悄悄降级的
配置」的论证继续有效，且在新方案里更重要：指纹比对会更频繁地触发 apply，校验失败
必须继续跑当前配置。
