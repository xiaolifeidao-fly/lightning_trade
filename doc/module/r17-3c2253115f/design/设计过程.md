## 1. 需求怎么理解

这不是再做一轮“看起来更聪明”的参数扫描，而是用 r4/r6/r10 已经补齐的事件事实，解决原始 Phase 0 的三个数据死结：

1. 原库没有兜底止损，无法判断 λ（`catastrophe_stop` 的频率）是否随状态变；本轮必须把 8/18–8/21 事故窗口中的可归集兜底纳入分层。
2. 状态收益、风险归因必须站在**建仓决策时刻**，不能站在平仓时刻；后者已经被原研究证明会制造“高波动期更赚钱”的伪影。
3. 状态必须双跑 `ρ`（过去 1h/4h 信号密度）和 `rv`（过去 1h/4h 1m 收益率标准差），阈值必须来自训练段、切换必须去抖，不能看完事故窗口再回头调阈值。

任务的最终问题是“是否打开自动按行情路由参数”。答案必须是可以关闭方向的研究结论，而不是为了把功能立项硬找显著性。范围还要求单独重跑事故窗口的 24h/±5% `trend_gate` 拦截面，但该规则是方向性 gate，不能被混同为已否定的“高波动降暴露”。明确不做自动路由、外生数据、burst throttle、紧止损、提前割肉和时间衰减退出。

### 3.2 事故窗口事实

- 合并 r6 归档的六个训练来源与两个 8/18–8/21 实例来源后，共读到 185,137 条原始事件，按账户扇出收回为 2,073 个市场信号键；同一盘口触发以 `(ts, side, gap_bp)` 去重，避免 champion/challenger 被数两遍。
- 原始 `catastrophe_stop` 有 7 条。剔除 r10 已认定的截断头后，剩 6 条可归集 stop，ROI 为 −401.92%~−448.33%；这与任务说明“6 次、−401%~−448%”一致。
- `application_1.properties` 与 `application_2.properties` 都配置了 `trade.trend_gate.window_hours=24`、`trade.trend_gate.threshold_pct=5`，但事故档案里的 `trend_skip=0`；`gate_block` 是 reverse gate 的“盈利不足”。代码注释也将趋势闸列为 8/21 事故复盘补丁，故不能把该窗口写成线上已实拦截。
- `server/argus_single/pkg/trade/manager.go:553`~`595` 的顺序是：反向减仓先走 reverse gate；非减仓才先过 trend gate、再过 cap。因此 trend 反事实只允许评估非减仓的 `open`/`cap_skip`，不得把反向减仓塞进来。

### 3.3 环境事实

本机 MySQL 进程存在，但无密码 `mysql -uroot` 返回 access denied；本轮没有获授权的事件库 DSN。需求级文档也禁止把日志、配置中的真实凭据写进资产。因此没有尝试从 properties、聊天记录或其他文件翻取密码。研究改为读取事件库回灌所用的 JSONL 真源，并把这个与直接查询 `strategy_event`/`episode_entry` 的差异写进报告限制。

## 4. 考虑过的方案与取舍

| 方案 | 取舍 | 结论 |
|---|---|---|
| 直接连本地/生产 MySQL 查询 `strategy_event`、`episode_entry` | 最贴近运行后的事件库，但当前没有获授权 DSN；猜凭据会越过安全边界 | 否决，记录为成品测试环境条件 |
| 从 JSONL 临时手抄统计 | 能快出一个数，但会绕过 r6 的归属/字段口径，很容易把两个实例或账户扇出混在一起 | 否决 |
| 选中：纯标准库 Python 读 r6 JSONL 真源 + r2 DeepCoin K 线，输出 Markdown | 与历史 `docs/argus_single/vol_state_phase0.py` 一致；事件字段与 `eventstore.Convert` 同源；可无凭据复跑 | 采用，并明确生产复跑应先过 r6 一致性巡检后读 MySQL |
| 把 7 条 `catastrophe_stop` 全部按平仓状态入 λ | 数量多一条，但其中一条在窗口前已建仓，没有真实决策状态 | 否决；这会直接违反 r10 和本任务的决策归集约束 |
| 从 JSONL 再算“按平仓状态的 PnL” | 容易做出显著表，但正是原 Phase 0 §10.3 已证实的伪影 | 否决；报告只引用 r10 已验证的决策归集事实，不伪造收益侧证据 |
| 将 24h/±5% 重跑写成实际 trend_gate 效果 | 事故文件没有一条 `trend_skip`，规则当时还未上线 | 否决；报告标为 1m close 近似的反事实可拦截面 |
| 用 λ 的单窗口差异打开自动路由 | 6 个事件且混入 cap 8/26/246、不同 order size 和人工干预；没有随机/实例内对照 | 否决；继续关闭路由 |

## 5. 选定方案怎样落到文件

### 5.1 新增可复跑脚本

新增 `docs/argus_single/vol_state_phase0_r17.py`：

1. 读取 6/28–8/16 的可用历史快照作训练段、8/18–8/21 作专项观察段，以及 `klines_1m_dc_r17.json`。
2. 在每个分钟格计算过去 W=1h/4h 的去重 `ρ` 与 1m 收益率标准差 `rv`；高/低阈值固定为训练段 p80/p50，状态切换连续 M=3 点后才生效。
3. 最小化重建“首次可见建仓 → 出场”的研究投影，只为 λ 提供 episode 分母和截断头排除；r10 的完整 `episode_entry` 仍是生产 PnL 归因的唯一权威。
4. 用条件 Poisson 的二侧 binomial 检验呈现可比较的高/低状态率；如果一组为零暴露/零事件就明确说不可检验，不制造 p 值。
5. 镜像 `manager.go` 的门控次序，以 1m close 的 24h 动量近似运行 `trend_gate`；输出候选动作数、反事实拦截数和“首次开仓即可挡住的 catastrophe episode”数。
6. 固定输出“不开自动路由”的结论；不输出任何线上参数、不会写库、不会请求外部数据。

### 5.2 新增研究报告与回归测试

- `doc/module/r17-3c2253115f/report/phase0-r17-研究报告.md` 是脚本真实生成的报告，给出双状态口径阈值/一致率、λ 分层、trend 重跑、明确结论和限制。
- `docs/argus_single/test_vol_state_phase0_r17.py` 钉住两个最容易回归的事实：7 条原始 stop 必须只留下 6 条可归集决策 stop；事故档案没有 `trend_skip`，rv W=4 的反事实中有 5 个 catastrophe episode 的首次开仓会被拦住。

## 6. 结果如何解释

报告的结论不是“λ 在某个状态更高”，而是：λ 已经从 0 次、不可观测变为可持续监测，但当前 W=1/4、ρ/rv 分层的暴露格子仍然很小，且不同实例/参数包混杂；例如 rv·W=4 的高/低条件 Poisson 双侧 p=0.2538，不能拒绝无差异。ρ/rv 观察段一致率为 39.9%（W=1h）和 63.3%（W=4h），也再次说明不能把 ρ 当成 rv 的同义词。

trend 反事实在事故流中会拦下大量逆势账户动作，且按首次开仓可直接对应 5 个可归集 catastrophe episode；但阻断首单/后续加仓会改变后续路径，不能从已发生路径外推出“必然避免了亏损”。它保留 gate 的后续研究价值，不构成上线或路由授权。

## 9. 剩余风险与待确认项

1. **数据库级复跑待环境授权**：成品测试需提供安全来源的只读事件库 DSN，先做 r6 JSONL↔MySQL 一致性巡检，再用 `strategy_event`、`dev_sample`、`episode`、`episode_entry` 复跑同表。没有这个条件时，不应假称“直接使用了已入库表”。
2. **ρ 的档案空洞**：历史快照在 8/9、8/17 等日缺失，ρ 会自然衰减；rv 连续，故不能挑 ρ 的局部读数放宽结论。
3. **trend 精度**：重跑使用 1m close；线上 `TrendTracker` 用实时 tick 和 warmup，结果只代表反事实可拦截面。
4. **λ 统计量不足且混杂**：6 条 stop 既不满足 ensemble 规则，也不是同一参数包的随机样本。只有在锁定实例/参数、预注册 rv 主口径、训练阈值、M 去抖和连续 OOS 数据下，才可研究 gate/trail 档位的状态依赖。
5. **路由仍关闭**：任何后来人不得把本报告的 trend 可拦截面改述成自动调 cap/止损/仓位的依据；那会重新落入已否定方向。
