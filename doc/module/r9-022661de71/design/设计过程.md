## 1. 需求怎么理解

任务说明给的边界很清楚，我的复述：

**要做的是一个只读服务**，为四个前端页面（总览/实例对比、行情触发点、信号复盘、
回测与寻优）提供统一数据源。七件事：

1. 信号列表，按 实例/时间/币种/账户/事件类型/结果/gapBp 强度/参数版本 多维筛选；
2. 信号详情，含逐账户判定（对应 TG 消息的 `[n]` 与 `[跳过n]` 明细）；
3. 秒级切片查询；
4. 与 K 线对齐的时间轴聚合；
5. 权益曲线；
6. 拦截原因聚合；
7. 跨实例汇总对比。

外加：按 `add-permission-resources` 补权限 SQL；按 `routers/register.go` 的 `build()`
模式注册；包放 `manager-api/pkg/argus_event`。

**两条硬约束**（任务说明点名，也是我给自己定的验收线）：

- 同一分钟内多次触发须能分别定位到秒（实测单分钟最多 5 次）；
- 按实例筛选不得串数据。

**不做**：前端页面；不写任何数据；不碰实盘链路；不生产 episode（那是 r10）。

需求大纲给这两条约束提供了量化依据：§3.3 实测 28.7% 的信号分钟内触发 ≥2 次、
承载 48.6% 的全部触发——任何"按分钟折叠"都会丢掉约一半触发；§4.3 三实例的账户
名会重号（实例1 的 `account1` 是 1394537246@qq.com，实例3 的 `account1` 是 uid
9564268），账户唯一性必须是 `(instance_key, account_label)`。

## 2. 勘察到的现状事实

### 2.1 数据源已经就位（r4 + r6 的产出）

`server/argus_single/pkg/eventstore/model.go` 定义了三张 append-only 事实表：

| 表 | 内容 | 关键列 |
|---|---|---|
| `strategy_event` | 10 类业务事件 | `ts`(datetime 秒精度)、`instance_key`、`config_version`、`uid`、`account_label`、`variant`、`event`、`instrument`、`side`/`net_side`、`size`/`order_size`、`avg_px`/`last_px`/`roi_pct`/`pnl`/`peak_pct`、`sig_last`/`sig_mark`/`gap_bp`、`trend_mom_pct`、`gate_kind`/`gate_threshold`/`gate_actual`、`reason`、`source` |
| `balance_sample` | 分钟级余额/权益心跳 | `balance`、`equity`+`equity_known`、`upl`、`net_size`+`net_size_known` |
| `dev_sample` | 无条件偏离采样窗口 | `dev_ticks`、`dev_max_bp`、`dev_mean_bp`、`dev_cross_json`、`dev_over_json` |

索引已经按查询形态建好：`idx_strategy_event_inst_ts`、`idx_strategy_event_uid_ts`、
`idx_strategy_event_inst_event_ts`、`idx_strategy_event_gate`。本任务的全部 where
组合都能命中其中之一，不需要加索引。

拦截原因已经结构化：`pkg/eventstore/gate.go` 的 `ParseGate` 把 reason 文本拆成
`gate_kind / gate_threshold / gate_actual` 三元组，枚举值有 7 个常量。这是"今天最常
被什么条件挡住"能聚合的前提，我直接引用这些常量而不是重打字符串。

### 2.2 已有的读侧先例

`server/service/trade/repository/signal_event_repository.go`（r8 的产出）已经示范了
从 `service` 模块读 `eventstore` 模型的做法：`service/go.mod` 已 `replace argus_single`，
import 零成本；事实表不嵌 `db.BaseEntity`，套不进 `db.Repository[T]` 泛型基类，
所以自定义一个只有 `Db`/`SetDb` 的 `eventReader`，并且查询里**不能带 `active = 1`**。

它的 `SignalEventFilter` 只支持 实例+账户+合约+时间+事件类型，没有分页、没有
gate_kind / 强度 / 版本维度，也不返回聚合——不够本任务用。

### 2.3 Handler / 注册 / 权限的既有模式

- `manager-api/routers/register.go` 的 `build(name, fn)`；
- `manager-api/pkg/argus_runtime/argus_runtime.go` 是最接近的样板（薄 handler +
  `commonRouter.ToJson`）；
- `manager-api/pkg/strategy/strategy.go` 里 `/strategy-positions/summary` 必须先于
  `:id` 注册的注释，提醒了同类路由冲突；
- `doc/module/r7-f74ca0f149/权限资源.sql` 给了本仓库权限 SQL 的确切写法（幂等
  `NOT EXISTS`、`SET @role_id`、api 资源 `page_url/component/...` 留空）。

### 2.4 三个必须正视的现实缺口

**缺口 A：r3 没做，没有逐秒行情切片表。** 全仓搜索无 `signal_slice` /
`tick_slice` 之类实体，`pkg/monitor/dev_sampler.go` 的采样间隔仍是 1 分钟。
r8 的设计文档第 121 行已经记过同一个结论。而任务说明明确要求"秒级切片查询"。

**缺口 B：TG 消息里的成交均价/成交价没有落库。**
`pkg/trade/manager.go:749` 那行 `[%d] ... 均价:%s 成交:%s` 的两个价格取自
`acc.WebResp.GetOrderData()`（交易所下单回执），而 `eventlog.Event` 的 `AvgPx`/
`LastPx` 在开仓路径上只有"减仓锁利"分支才赋值。所以复盘页无法还原这两个数。

**缺口 C：manager-api 的连接 loc 不确定。**
`argus_single/configs/application.properties` 里的 DSN 带 `loc=Local`，且
`eventstore.NormalizeDSN` 还会再强制一次；而 manager-api 的 `sqlconn` 由部署方提供，
仓库里根本看不到（`manager-api/configs/application_dev.properties` 只有 port/path/log）。
go-sql-driver 的默认是 `loc=UTC`。`strategy_event.ts` 是**跨进程**的列：
argus_single 按 Local 写、manager-api 按未知 loc 读。两侧不一致就整体偏 8 小时——
需求大纲反复点名的那类隐蔽错误（数据全在、图能画、只是整段错位）。

## 3. 考虑过的方案与取舍

### 3.1 放哪儿：扩 `service/trade` 还是新建 `service/argus_event`

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 扩 `service/trade` | 在 r8 已有的 `signal_event_repository.go` 上加分页与聚合 | 省一个包；但 `trade` 已经背着预测回测 + 信号回测 + K 线回填 + 持仓，`trade_service.go` 的构造函数已经很重，读服务塞进去会让"回测"和"查事件"共用一套 DTO 命名空间，后面谁改谁怕 |
| **B. 新建 `service/argus_event`（选中）** | 独立域，自带 dto/repository/service | 任务说明本身就写了"新增 manager-api/pkg/argus_event"；`backend-development` 技能的新增业务域路径也是这个；读侧口径（时间按串、实例硬隔离）与 trade 的口径不同，混在一起会互相污染 |

选 B。代价是 `strategy_event` 有两个读侧仓储（trade 的回测入参 + argus_event 的
查询），我在包注释里写清楚了两者的分工：r8 那个只服务回放，本包只服务展示，
两边都不定义实体、都从 `eventstore` 引模型，所以不会 schema 漂移。

### 3.2 时间口径：`time.Time` 还是墙钟串（本轮最关键的决定）

针对 §2.4 缺口 C，考虑了三条路：

| 方案 | 做法 | 否决/选中理由 |
|---|---|---|
| A. 照 r8 做法用 `time.Time` | 绑定参数与扫描都用 `time.Time` | **否决**。它把正确性押在"部署方在 sqlconn 里写了 `loc=Local`"这件仓库里验证不了的事情上。押错的表现不是报错，是整段数据偏 8 小时——最贵的那种错法 |
| B. 在 manager-api 启动时强制改写 `sqlconn` | 复用 `eventstore.NormalizeDSN` | **否决**。这条连接是全仓共用的（trade / coin / user / permission 全在上面），改它的 loc 会改变**所有** DATETIME 列的读写解释，既有数据的口径瞬间平移 8 小时。本任务是"新增只读接口"，没有资格做这种全局改动 |
| **C. 时间全程按串走（选中）** | 入参归一成本地墙钟串，查询用串比较（`ts >= '2026-08-18 00:00:00'`），出参用 `DATE_FORMAT(ts,'%Y-%m-%d %H:%i:%s')` 读成串 | 读出来的字符 = 存进去的字符 = JSONL 里的字符 = TG 消息里的字符，与连接的 loc 完全无关。串比较对 DATETIME 列仍然走索引 |

选 C。代价：不能直接复用 `eventstore.StrategyEvent` 作为扫描目标，得在
`service/argus_event/repository` 里定义一个 `Ts string` 的读侧投影
（`StrategyEventRow`）。这不算 schema 重复——列名与类型仍由写侧的模型定义，
投影只是 SELECT 的形状。

唯一的例外是 `trade_kline`：它的 `open_time` 由 manager-api 这条连接**自己**写、
自己读，读写同 loc，来回抵消后 `time.Time` 是正确的绝对时刻，`In(time.Local)`
再落回墙钟就与事件对齐了。这一点写在 `slice.go` 的 `listKlines` 注释里。

集成测试直接把这个决定钉死了：写连接用 `eventstore.OpenDB`（loc=Local），读连接
**故意只补 `parseTime=true`、不补 loc**（退回默认 UTC），两条连接错开 8 小时的情况下
断言读回来的墙钟逐字相同。

（顺带发现：`service/trade` 的信号回测读侧走的是 `time.Time`，在 loc 缺失的部署上
会有同样的 8 小时风险。不在本任务范围，记进 §7 遗留项。）

### 3.3 「一次触发」怎么归组（信号详情的核心）

`pkg/trade/manager.go:524 executeSignalTrades_From_WEB` 给每个账户开一个 goroutine，
各自 `eventlog.Log(...)`，而 `eventlog` 在写入时刻取 `Ts`。这意味着：

- 拦截类事件（gate_block / cap_skip / trend_skip）在毫秒内落地；
- 成交类事件（open）要等 `placeSignalWebOrderWithRetry` 的网络往返，可能晚数秒。

所以"同一次触发"**不能按 ts 相等归组**。考虑过：

| 方案 | 否决/选中理由 |
|---|---|
| A. ts 完全相等 | **否决**。会把同一次触发的成交行判成另一条信号，逐账户判定表永远少一行——正好丢掉最重要的那行 |
| B. ts ± N 秒的时间窗 | **否决**。相邻触发间隔中位只有 61 秒、48.7% 小于 60 秒（§3.3），窗口开到能覆盖下单往返（数秒）就已经有吃掉下一次触发的风险，而窗口本身没有任何语义来区分"同一次"和"下一次" |
| **C. 报价快照三元组（选中）** | `pkg/trade/signal_quote.go:38 applySignalQuote` 把同一个 `SignalQuote` 复制给这次触发的每一个账户事件，所以 `(sig_last, sig_mark, gap_bp)` 三元组相等 ⟺ 同源。这是**语义**判据不是**启发式**判据 |

最终实现是 C 为主、时间窗只做搜索范围收口（`signalGroupWindowSec = 30`）：
先按 (实例, 合约, 触发类事件, ±30s) 捞候选，再用三元组 + `side` 精确筛，最后按
账户去重（同账户多行取离锚点最近的）。老事件（报价不可算、三元组全空）退回
"同一秒 + 同方向"。

这个设计直接满足了任务说明的第一条硬约束：同一分钟内的第二次触发有**不同的**
报价三元组，天然是另一条信号。单测 `TestGroupSignalRowsSeparatesSecondTriggerInSameMinute`
和集成用例 `TestIntegrationSameMinuteTriggersStaySeparate` 都在钉这一点。

`signalId` 取组内最小的 `id`：点列表里同一次触发的哪一行进来，拿到的都是同一个
信号标识。

### 3.4 秒级切片：r3 没做，怎么办

| 方案 | 否决/选中理由 |
|---|---|
| A. 不提供这个接口 | **否决**。r12（行情主视图）依赖 r9，切片抽屉是它的一屏；接口缺席等于把 r12 也堵死 |
| B. 顺手把 r3 的采集做了 | **否决**。越界。r3 要改 `pkg/monitor` 的采样器、要设计切片表与 90 天滚动清理、要评估 0.44 GB/年的容量，是一条独立任务，塞进读服务里既做不干净也无法验收 |
| C. 从 1m K 线插值造点 | **否决**。K 线里根本没有 mark price，而信号源是 DeepCoin `last` 相对 `mark` 的偏离——需求大纲 §3.3 明确写了这个信息在 K 线中不存在。插出来的是假数据 |
| **D. 用现有秒级观测降级供数 + 自曝降级（选中）** | `strategy_event` 每行都带触发那一秒的 `(sig_last, sig_mark, gap_bp)`，是**真实的秒级观测**。窗口内把这些点按秒折叠返回，同时用 `tickSource` / `tickComplete` / `degradedReason` 三个字段说清楚"只有触发那一秒有点，别把它们连成连续曲线" |

选 D。契约按 r3 落地后的形态设计：届时只需把 `tickSource` 换成 `signal_slice`、
把 `points` 补满、`tickComplete` 置 true，前端不用改。切片里还附了窗口覆盖到的
`dev_sample`（无条件偏离，不受生产阈值截断）与 1m K 线上下文。

### 3.5 聚合放 SQL 还是放 Go

`GROUP BY` 下推更省内存，但口径（结果大类、强度分档、净仓推导）就要在 SQL 里
再写一遍 `CASE WHEN`，与 `catalog.go` 里的定义两处必然漂移。而这些口径恰恰是本
任务最容易被质疑的地方，纯函数能被单测钉死。

量级也撑得住：全库 16.6 万条事件、业务事件仅 9%，正常窗口在万级。

决定：**结果分布 / 门控聚合 / 强度分级 / 跨实例汇总 / 时间轴分桶都在 Go 侧做**，
统一走 `ListEvents(filter, 0, maxAggregateRows, true)`；超过 20 万行时返回体挂
`truncated: true`，不静默截断。

唯一下推 SQL 的是权益曲线的降采样——`balance_sample` 占全部事件 61%，30 天 × 2 账户
就是 8 万多行，全捞回来在 Go 里降采样不合算。桶键用
`FROM_UNIXTIME(FLOOR(UNIX_TIMESTAMP(ts)/N)*N, ...)`：两个函数走同一个会话时区，
来回抵消，桶边界落在**存储的墙钟**网格上，与连接 loc 无关（与 §3.2 的选择一致）。

### 3.6 默认时间窗口锚在哪

按 `now - 24h` 兜底是最常见的写法，但这个库的主力数据是 6–8 月的回灌历史
（r6 的巡检报告：58 个文件、16.6 万条，覆盖 6/28–8/21），今天是 9/2——按当前时间
兜底，四个页面打开全是空白。

改成：两端都没给时，先 `SELECT MIN(ts), MAX(ts)`（带上同一套筛选条件），把窗口锚在
**已入库数据的最新事件时刻**上回推 24 小时，并通过 `window.resolved`
（`explicit` / `latest-data` / `empty`）告诉前端这个窗口是怎么来的。多一次走索引的
聚合查询，换掉一个必然发生的"打开就是空页"。

### 3.7 跨实例：允许到什么程度

需求大纲 §4.3 说得很硬：参数分实例是 champion/challenger 实验体系的核心机制。
所以我按接口分了两类：

- **强制单实例**：`/timeline`（净持仓阶梯）、`/equity-curve`（账户权益）。
  缺 `instanceKey` 直接报错，不做任何跨实例兜底。
- **允许全部实例**：`/signals`（每行带 `instanceKey`）、`/gate-stats`
  （触发计数跨实例相加有意义，比率不可比 → 挂 `crossInstance` 标记与提示）、
  `/instance-summary`（**逐实例独立成行，服务端不做任何跨实例求和**）。

`/instance-summary` 上还有一条：事件里出现过但 `argus_instance` 没注册的实例照样
列出来，标 `registered: false`——那正是"实例键撞名 / 漏注册"要被看见的场景，
静默过滤掉等于把问题藏起来。

### 4.3 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/argus-event/filter-options` | 实例/账户/合约/变体/参数版本/事件类型/门控/强度档/来源 + 数据覆盖区间 |
| GET | `/argus-event/signals` | 分页信号列表，多维筛选 |
| GET | `/argus-event/signals/:id` | 信号详情 + 逐账户判定 + TG 明细行还原 |
| GET | `/argus-event/signals/:id/slice` | 触发瞬间 ±N 秒切片（默认 60，上限 300） |
| GET | `/argus-event/timeline` | 与 K 线对齐的桶聚合（**instanceKey 必填**） |
| GET | `/argus-event/equity-curve` | 按账户的权益曲线（**instanceKey 必填**） |
| GET | `/argus-event/gate-stats` | 拦截原因 + 结果分布 + 强度分级 |
| GET | `/argus-event/instance-summary` | 跨实例汇总对比 |

`/signals` 支持的筛选维度（对齐任务说明的"多维筛选"）：
`instanceKey|instanceKeys`、`start`/`end`、`instrument|instruments`、
`accountLabel|accountLabels`、`uid|uids`、`category`(trigger/exit/all)、`events`、
`result`(open/blocked/具体 gate_kind)、`strength`(weak/medium/strong) 或
`gapBpMin`/`gapBpMax`、`configVersions`、`variants`、`side`、`source`、
`pageIndex`/`pageSize`、`order`。

排序固定 `(ts, id)`：同秒多条是常态，只按 ts 排会让翻页结果抖动。

### 4.4 若干口径的落点

- **强度分档**只在 `catalog.go` 的 `strengthBands` 定义一次（弱 <7bp / 中 7–9 / 强 ≥9），
  筛选、聚合、前端下拉三处都从这里取，不让前端再写死 7 和 9。
- **`gap_bp` 为 NULL** 时不判档、不当成 0 混进"弱"档；给了强度条件时直接排除。
- **净持仓阶梯**是派生量：逐条事件维护每个账户的最近净仓快照（open 记的是成交后
  的 `postNet`，见 `manager.go`），五类平仓事件后该账户归零，桶末取各账户之和，
  空桶沿用上一桶。这一点在代码注释里明确标了"派生而非实测，精确生命周期是 r10"。
- **equity 只在 `equity_known = 1` 的样本上聚合**：0 与负权益是真实的极端回撤样本，
  不能用 `> 0` 过滤掉。
- **`registered = false`** 与 **`truncated = true`** 都是"让问题可见"的字段，
  不是装饰。

### 4.5 影响面与兼容性

- 纯新增：没有改任何既有接口、DTO、表结构或业务逻辑。既有 `trade-backtest-runs`
  等页面不受影响（需求大纲 §6.1 验收 9 的无回归要求）。
- `EnsureTable` 会 `AutoMigrate` 三张事件表。`strategy_event` / `dev_sample` 此前已
  由 `trade` 侧建过，`balance_sample` 是**第一次**在管理端侧被建出来（回测只用到前
  两张）——权益曲线依赖它，所以这里三张一起建。AutoMigrate 幂等，与写侧
  （argus_single）建同一组模型，不会冲突。
- 权限：新增 8 条 api 资源，全部走 `NOT EXISTS` 幂等插入。不建页面资源——
  页面属于 r12/r13/r15。
- 无数据迁移。

## 6. 被否决的想法一览（含理由）

1. **在 `service/trade` 上扩**——trade 已经太重，读写口径不同（§3.1）。
2. **用 `time.Time` 收发时间**——把正确性押在看不见的 DSN 上，错法最贵（§3.2）。
3. **启动时强制改写全局 `sqlconn` 的 loc**——会平移全仓所有 DATETIME 的解释，
   越界（§3.2）。
4. **按 ts 相等归组信号**——会丢掉成交行（§3.3）。
5. **按固定时间窗归组信号**——相邻触发中位间隔只有 61 秒，窗口没有语义（§3.3）。
6. **顺手把 r3 的秒级采集做了**——越界，且做不干净（§3.4）。
7. **从 1m K 线插值造秒级点**——K 线里没有 mark price，造出来是假数据（§3.4）。
8. **把聚合下推成 SQL GROUP BY**——口径两处漂移，且不可单测（§3.5）。
9. **默认窗口按 `now - 24h`**——回灌库里必然是空页（§3.6）。
10. **`/instance-summary` 直接给"合计"行**——需求大纲反复强调跨实例相加没有意义，
    服务端给了合计就等于替前端背书（§3.7）。
11. **把 `registered=false` 的实例过滤掉**——那正是实例键撞名要被看见的信号。
12. **支持 `1w` 周期的时间轴**——`time.Truncate` 的整除点落在周四，与交易所周线
    对不上，宁可明确拒绝也不给个错的桶。
13. **给成交价补 0 占位**——见 §7 的已知缺口，补 0 会让页面显示一个假价格。
