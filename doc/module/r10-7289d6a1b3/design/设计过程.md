## 1. 需求怎么理解

### 1.1 一句话

把 `strategy_event` 里的离散事件归集成"一次完整持仓"，并把每笔已实现盈亏
**平摊回各张仓位建仓时刻**的决策上。前者回答"这次扛单从哪开始、怎么结束"，
后者回答"在什么条件下做的决策更赚钱"——需求大纲 §3.5 明确这是**唯一正确**的
归因口径，按平仓时刻归集会系统性造出伪影。

### 1.2 从任务说明里读到的边界

| 要求 | 我的复述 |
|---|---|
| 实现设计文档 §6 已定稿的切分状态机 | `docs/argus_single/2026-07-28-事件数据持久化与可视化设计.md` §6.1~§6.6 逐条落地，不自创口径 |
| 六种出场方式 | trailing_close / reduce_to_zero / catastrophe_stop / fixed_close / external_close / manual_close |
| episode 归属 `(instance_key, account)` | 不是设计文档写的 `uid`——uid 靠 properties 映射补齐、可能为空；account_label 条条都有 |
| variant 取开仓时刻 | §6.3，跨越 variant 变更点的 episode 按决策时刻归属 |
| 深度按两档保真度 | §6.4 的 `minute` / `alert_sampled`，加跨界的 `mixed` |
| 仓位跳变记标记但不断开 | §6.5 / D6 |
| 派生表可从事件表纯函数重建 | 可整表 DROP 重跑，结果一致 |
| 决策归集口径 | 波动率研究 §10.3：平摊回**各张仓位建仓时**所处状态 |
| **不做**：external_close / manual_close 不计入策略胜率 | 交易所侧与人工操作，盈亏照记但胜率分母里剔除 |

### 1.3 与需求大纲的一处出入（已核对，按代码事实实现）

需求大纲 §6.2 写"8/18–8/21 区间……20 笔完整持仓（账户A 6 笔 / 账户B 14 笔）"。
本轮派生出来的实际数字（实例 `argus-single-roc`，按出场时刻落在该窗口）：

| 口径 | 账户A | 账户B | 合计 |
|---|---:|---:|---:|
| 只认平仓事件（大纲的口径） | 7 | 14 | **21** |
| 加上 `reduce_to_zero` | 13 | 16 | **29** |

大纲的 20 笔是"只认平仓事件"的口径，而设计文档 §6.2 明确点名这个口径会漏掉
`reduce_to_zero`（"**若前端只认 close 事件当出场点，这 17 个 episode 会显示成
永远没结束**"）。账户B 的 14 笔逐格吻合，账户A 差 1 笔——差在
`2026-08-18 00:11:23` 那笔 trailing_close，它的建仓发生在 8/18 之前，按"建仓与
出场都落在窗口内"数就是 6 笔。**不改需求，如实报数**，并把两种口径都写进报告，
让 r13 的复盘页自己选。

### 2.2 现场核对出来的、文档里没有的事实

动手前把 `argus_event_check` 库整个翻了一遍，六条与设计直接相关的发现：

1. **反向减仓在 JSONL 里就是 `open` 事件**，靠 `side` 与净仓快照区分，不是独立事件类型。
2. **`net_side` 不可靠**：2026-07-24 之前的减仓事件 `net_side` 为空、`pnl` 也为空
   （例：`2026-06-30 22:02:39 open short size=5`，其实是 6→5 的减仓）。
   之后的带 `net_side` 与 `reason='减仓锁利(pnl为估算)'`。
   ⇒ **只能靠 `size` 快照的增减判定加仓/减仓**，不能靠 `net_side`。
3. **`open` 事件的 `size` 为 NULL 就是 0**：JSONL 全字段 `omitempty`，减到 0 的那一笔
   `size` 被省掉了。全库 30 条，其中 16 条带 `减仓锁利` reason（新格式）、14 条不带（老格式）。
   加仓不可能落到 0，所以这个读法没有歧义。
4. **减仓事件带已实现盈亏**（2026-07-24 起）：`roi_pct` + `pnl` 都有。
   ⇒ `reduce_to_zero` 的 episode 不是"没有盈亏"，只是老数据段未知。
5. **日志窗口开头就扛着仓位**：`argus-single-roc` 的第一条事件
   （`2026-06-28 22:37:18 gate_block net_side=long size=14`）说明账户A 当时已经扛着
   14 张多单；头 30 条观测（10 条 gate_block + 20 条 loss_alert，最深 −170%）全落在
   任何 `open` 事件之前。账户B 的第一条是 `open size=6 / orderSize=1`，同样有 5 张存量。
6. **`balance_sample.upl` 的覆盖是断崖式的**：`argus-single-roc` 72,495 条心跳里只有
   40,101 条带 upl（2026-07-21 起 100%，之前 0%）。心跳周期实测约 **30 秒**一条，
   不是设计文档里写的一分钟。

### 3.1 代码放哪

| 方案 | 做法 | 取舍 |
|---|---|---|
| A（选中） | `argus_single/pkg/eventstore/episode/` 放模型 + 派生 + 重建；CLI 放 `manager-api/cmd/argus-episode-rebuild` | 与 r6 的 `eventstore/backfill` + `cmd/argus-event-import` 完全同构；r9 已经在 `service/argus_event` 里 `import "argus_single/pkg/eventstore"`，r13 照抄就能读 episode |
| B | `server/service/argus_episode/{dto,repository}` + Service，走 backend-development 的标准三层 | 派生是离线批处理、不是 HTTP 读路径；模型放 service 域会与 `eventstore.Models()` 分家，读侧要 import 两个不同模块的模型。**否决** |
| C | 塞进 `eventstore/backfill` | backfill 的语义是"JSONL ↔ MySQL"，episode 的输入是 MySQL、输出也是 MySQL，混进去两个 Job 结构会互相污染。**否决** |

选 A。backend-development 技能第一条就是"以仓库现状为准"，而仓库现状里
`argus_event` 读服务已经反向依赖 `eventstore` 模型了。

### 3.2 episode 的归属键

| 方案 | 取舍 |
|---|---|
| `(uid, instrument)`（设计文档 §4.3 原文） | uid 从来没进过事件，靠 properties 的 `trade.accountN.uid` 映射；配置没填时 `strategy_event.uid` 就是空串，全部账户会挤成一个账本。**否决** |
| **`(instance_key, account_label, instrument)`（选中）** | account_label 每条业务事件都有；instance_key 必须进键，因为两个实例里都存在叫"账户A-…"的标签却指向不同真实账户（r6 操作手册 §2 已经踩过） |

uid 仍然入表，只是不作为分组键。

### 3.3 唯一键的锚点

`opened_at` 会是 NULL（截断头），而 MySQL 唯一键里的 NULL 互不相等——拿它做键
等于没去重。改用 `first_event_at`（本 episode 观测到的第一条事件时刻，恒非空），
唯一键 `(instance_key, account_label, instrument, first_event_at)`。

### 3.4 决策归集怎么摊 —— 本任务的核心

先读了复现脚本 `docs/argus_single/vol_state_phase0.py:164`，它的口径是：

```python
if open_adds:
    share = cl["pnl"] / len(open_adds)   # open_adds 是"一张合约一个状态标签"的列表
    for s_add in open_adds:
        per[s_add]["pnl_add"] += share
open_adds = []
```

即**整仓平掉时，每张合约平分这笔盈亏**。但那个回测引擎只有整仓平仓，
真实事件流里还有**部分减仓**，脚本没有对应的先例。三个候选：

| 方案 | 做法 | 取舍 |
|---|---|---|
| FIFO | 减仓退掉最早的几张 | 实现直观，但会**系统性**让早期决策先退场、拿不到后续平仓的归因，凭空造出"越早建仓越不赚钱"的假结论。而且交易所是净额均价记账，根本不存在"减掉的是哪几张"。**否决** |
| LIFO | 退掉最新的几张 | 同上，方向相反的偏差。**否决** |
| **等比例（选中）** | 每笔实现盈亏按各笔决策**在场张数**摊；每次退场也按在场张数等比例退 | 与净额均价记账的经济含义一致：平掉 k/N 张实现的就是整仓浮盈的 k/N 切片，而这份浮盈是所有在场张数共同持有的。**整仓平掉时退化成"每张平分"，与 vol_state_phase0.py 逐字一致** |

代价：等比例退场会摊出小数张，所以 `episode_entry.closed_size` / `open_size` 是
`decimal(20,8)` 而不是 `int`。这个代价是值得的——整数化只能靠最大余数法，
而"哪一张被凑整"本身就是一个任意选择。

**归集的分母必须是真实净仓，不是可见决策数。** 截断头 episode 里有一部分张数的
建仓决策根本不在窗口内（例：账户B 首条事件就带着 5 张存量）。若把整笔盈亏摊给
看得见的那两笔，等于把看不见那 5 张的收益也算到它们头上——这正是决策归集要
消灭的那类假信号。所以账本额外记一个 `hidden`（在场但决策不可见的张数），
它进分母，落在它头上的那部分记进 `episode.unattributed_pnl`，不进任何决策行。

### 3.5 `external_close` / `manual_close` 怎么处理

任务说明只说"不计入策略胜率"，没说盈亏怎么办。三种理解：

| 理解 | 取舍 |
|---|---|
| 整条 episode 连同盈亏一起丢掉 | 那是真金白银，权益曲线会对不上。**否决** |
| 只在 episode 上打一个 `strategy_attributable=0` 标记 | 够用，但按决策分层统计时每次都要回 join episode 表。**部分采纳** |
| **（选中）** episode 上打标记 + 决策行上同时存 `attributed_pnl` 与 `attributed_pnl_strategy` | 盈亏如实记进 `pnl`，剔除交易所/人工出场后的那份单独存一列。下游要"策略自己的战绩"直接取 strategy 列，要"账户真实盈亏"取总列，不用各自记规则 |

### 3.6 深度保真度怎么判

| 方案 | 取舍 |
|---|---|
| 硬编码 2026-07-21 这个上线日期 | 设计文档 §5.2 已经因为同样的理由否决过一次（net_size 的已知性判定）。**否决** |
| 按绝对条数（"每分钟一条 ⇒ 期望 duration/60 条"） | 心跳实测是 30 秒一条、不是一分钟；周期改一次，全部历史 episode 的档位集体漂移。**否决** |
| **（选中）** 窗口内 `带 upl 的心跳 / 全部心跳` 的比值，≥0.9 记 `minute`、>0 记 `mixed`、=0 记 `alert_sampled` | 与采样周期无关。留 10% 余量是因为进程重启、心跳漏拍都会造成零星缺口，卡死 100% 会让绝大多数 7/21 之后的 episode 被误标成 mixed |

同时把 `balance_sample_count` 与 `upl_sample_count` 两个原始计数一起入表，
让这个判定可被复核，而不是只留一个结论字符串。

### 3.7 重建的范围：整实例 vs 按日期增量

否决按日期切片。episode 会跨天（设计文档实测最长 68.8 小时），
按日期截一段会把跨界持仓拦腰砍成两个假 episode。量级也不构成理由——
一个实例三个月的持仓相关事件不到 8 千条，全量派生耗时 < 1 秒。

因此 `Replace` 是**整实例先删后插、包在一个事务里**：派生表半旧半新的中间态
没有任何解释，比整段缺失更危险。

### 3.8 仓位跳变（|Δsize| != orderSize）的三种成因，分开处理

设计文档 §6.5 把它们归成一类，但实际处理需要区分：

| 现象 | 判据 | 处理 |
|---|---|---|
| 快照滞后 | Δsize = 0 | 记 `StaleSnapshot` + 跳变标记，**不动仓位**。实测正好 5 次（2026-07-07 05:10–05:11），与设计文档"A 3 处 + B 2 处"逐格吻合 |
| 信号突发累加 / 未记录的外部平仓 | Δsize ≠ 0 且 ≠ orderSize | 以快照为准调整仓位，记跳变标记，**episode 不断开**（D6） |
| 反向单反而做大仓位 | 反向事件的 Δ < 0 | 只记异常、不动仓位。全库实测 0 次（reverse_gate 拦掉了翻转单） |

### 3.9 截断头怎么识别 —— 一处刻意的不对称

三条入口：

1. **平仓/减到零事件落在空仓状态** ⇒ 建仓在窗口之前，`opened_at` 留 NULL。
2. **观测事件（gate_block / loss_alert / cap_skip / trend_skip）落在空仓状态**
   ⇒ 用它自带的净仓快照开一个截断头。roc 实例开头那 30 条就是这么救回来的；
   丢掉它们等于把一整段扛单过程从库里抹掉，而"扛住浮亏等价格回来"正是这个策略
   赖以为生的部分。
3. **账本的第一条 `open` 就报出比 orderSize 更大的净仓**（账户B 的 `size=6 / orderSize=1`）
   ⇒ 多出来的 5 张是存量，`opened_at` 留 NULL，只把 1 张记给这笔决策。

第 3 条有代价：§6.5 的"信号突发累加一次下单多张"（7/05 01:39 A 0→3，orderSize=1）
若恰好发生在账本第一条，会被误判成截断头。**所以这条规则只在账本的第一条事件上
生效**——之后我们已经亲眼看着仓位归零，净仓是可信的。两种误判里选这个方向：
少归因是缺数据（`opened_at IS NULL` 能被下游直接排除），多归因是假数据。

### 4.2 状态机（`derive.go`）

按 `(instance_key, account_label, instrument)` 分账本，事件按 `(ts, id)` 升序：
同一秒内可能有多条（实测 28.7% 的信号分钟内触发 ≥2 次），`id` 升序即 JSONL 落盘顺序。

```
open 事件
├─ 空仓
│   ├─ 结果净仓 = 0            → 截断头 + reduce_to_zero（只看到减到 0 的那一笔）
│   ├─ 账本首条且净仓 > 下单量 → 截断头（存量部分进 hidden）+ 记可见的那几张
│   └─ 否则                    → 新 episode，opened_at = 本事件时刻
└─ 持仓中
    ├─ side == episode 方向 → 加仓：Δ = 快照净仓 − 跟踪净仓
    │     Δ > 0  → 记一笔决策行
    │     Δ = 0  → 快照滞后，只记标记
    │     Δ < 0  → 反常缩仓，按未知盈亏的减仓处理 + 标记
    └─ side != episode 方向 → 反向减仓
          先 realize(pnl) 摊给全部在场张数，再 retire(Δ) 等比例退场
          退到 0 → exit_kind = reduce_to_zero

trailing_close / catastrophe_stop / fixed_close / external_close / manual_close
    → realize(pnl) + retire(全部) + 关 episode

loss_alert / gate_block / cap_skip / trend_skip
    → 计数 + 收 ROI 观测（空仓时用它的净仓快照开截断头）

流末仍持仓 → closed_at / exit_kind 留 NULL，在场张数落进 open_size
```

`realize` 与 `retire` 的**顺序不能反**：减掉的 k 张与留下的 N−k 张在净额均价账本里
是同一批浮盈，凭什么只算给 k 张。

### 4.3 已知性标记（沿用 §5.2 的口径）

三处"未知不等于 0"：

- `missing_pnl_events`：2026-07-24 之前的反向减仓只写 size 不写 pnl。
  当 0 会凭空造出"这次减仓不赚不亏"的假样本。
- `pnl_known`：决策行完全出场**且**在场期间没有未知盈亏才置 1。
- `min_roi_pct_observed` / `max_roi_pct_observed`：都带 `_observed` 后缀
  （设计文档 §4.3 原名是 `max_roi_pct`，看上去像精确值，是个陷阱）。
  loss_alert 是双重过滤的采样（ROI < −150% 才发 + 5 分钟冷却），实测最深 −362.2%
  而同一笔的真实最深是 −374.7%，差 12.5 个 ROI 点。

顺带一个对设计文档的**增强**：`gate_block` 的 `roi_pct` 是拦截当下整个净仓的 ROI，
与 loss_alert 同口径，一起收进深度观测能把 0 ~ −150% 那段空白补上一部分
（仍然只是下界）。

## 6. 还剩哪些风险与待确认项

| 项 | 说明 |
|---|---|
| **等比例退场是模型选择，不是观测事实** | 交易所净额均价记账下不存在"减掉的是哪几张"，等比例是最中性的选择，但它仍是一个假设。若将来接入逐笔成交明细，应改成真实的建仓价配对 |
| **`reduce_to_zero` 的 exit_roi_pct 是减仓那一笔的 ROI** | 不是整段持仓的收益率。前端展示时要标注，否则会被读成"这次持仓只赚了 13.9%" |
| **老数据段的减仓盈亏未知** | 2026-07-24 之前 92 次实现盈亏未知，波及 335 个决策行；再算上 24 个仍在场的，共 364 行 `pnl_known=0`（占 1501 行的 24%）。按状态分层统计时必须用 `pnl_known=1` 过滤，否则相当于把这些决策的收益当成 0 |
| **`unattributed_pnl` 只在截断头出现** | 实测 roc +1.6119U（占 153.8451U 的 1%）、ives −84.3049U（占 −1343.5805U 的 6.3%）。ives 的比例不小，因为它的日志只有 4 天、开头就扛着存量仓位 |
| **深度保真度的 0.9 阈值是拍的** | 有实测支撑（7/21 之后 upl 覆盖率 100%，之前 0%，没有中间态），但心跳策略改了要复核 |
| **重建不是自动的** | 目前只能手工跑 CLI。事件是持续写入的，episode 会滞后。建议 r13 落页面时一起决定：挂 cron 每日重建，还是在读服务里做增量触发 |
| **episode 的读 API 不在本任务范围** | r13（信号复盘与 episode 详情页）依赖 r9 + r10，读路径应该在 r13 那一刀里加，落在 `service/argus_event` 域内、复用 `episode.Models()` |
| **`argus_instance` 注册检查** | CLI 沿用 r6 的口径：注册表不存在或为空时放行，登记过但查不到这个键才拦。本地校验库里我补登了两个实例键 |

## 7. 被否决的想法一览（便于后来人不再重跑）

| 想法 | 否决理由 |
|---|---|
| 用 `balance_sample.net_size` 切 episode | 只有 2026-07-21 之后才有，且"空仓"与"字段缺失"编码相同（§6.1）。`open` 事件的 size 则条条都在 |
| 靠 `net_side` 判定加仓/减仓 | 2026-07-24 之前的减仓事件 `net_side` 为空 |
| 一张合约一行存决策归集 | 实例2 cap 246 / order_size 10，按张展开放大一到两个数量级；而决策的粒度本来就是"这一笔 open 事件" |
| FIFO / LIFO 配对 | 系统性偏差，且与净额均价记账的经济含义不符 |
| 仓位跳变时断开 episode | 会造出假 episode，比标记更糟（设计文档 D6 已定稿） |
| 按日期增量重建 | 会把跨天持仓砍成假 episode |
| 报告里保留完整账户邮箱 | 报告要提交进仓库；区分账户靠"账户A/账户B"前缀就够了，邮箱本地部分整段打码 |
| 打码后再分组统计 | 两个不同账户会被静默合并成一行，而"合并了"这件事本身看不出来。改成按原始标签分组、只在打印时打码 |
