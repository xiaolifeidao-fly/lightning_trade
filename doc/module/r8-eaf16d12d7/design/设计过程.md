### 1.2 目标复述

用**真实历史信号**跑参数回测，并让每组结果的**可信度显式可见**。

范围边界（逐条对照任务说明）：

1. 在 `strategy` 下新增信号驱动引擎，**不动**预测驱动的 `engine.go`；
2. **信号侧零推导**：触发时刻 / 方向 / gapBp / 拦截原因全部来自 `strategy_event` 按 `instance_key` 过滤的事件流，不从 K 线推信号；
3. **精度分层**：改仓位 / 止盈 / 止损 / 门控 / 趋势闸 ⇒ 事件级；改 `signal_threshold` ⇒ 频率级，用 `dev_sample.DevCross` 推 λ(θ)；
4. **出场保守假设**：同一根内可能同时触及止盈止损时按不利方向结算；`peakPct` 用 1m high 会偏高，须标注（实盘判定 5 秒、回测 60 秒）；
5. `params_snapshot` 冻结参数，`metric` 加 `fidelity` 字段；
6. 以 `backtest_dual_side.py` 作金标准对照；
7. 表骨架（`trade_backtest_*` 三张）可复用。

不做：不改实盘策略逻辑；独立执行路径；不触碰实盘进程。参数组批量扫描（r11）、自动寻优（r16）、可视化页（r14）都不在本轮。

### 1.3 与任务说明的一处事实修正

任务说明写「真实成交均价（open 事件 avgPx）全来自 strategy_event」。**核对真实数据后这一条不成立**：

```
{"ts":"2026-08-18 00:22:16","account":"账户A-...","event":"open","side":"long",
 "size":1,"orderSize":1,"sigLast":64080.6,"sigMark":64058,"gapBp":3.528052702238369}
```

`open` 事件**没有 avgPx / lastPx**。看 `pkg/trade/manager.go:620-637` 的 `openEv` 组装就清楚：只有"反向减仓锁利"那一支才会补 `AvgPx/LastPx/NetSide/Pnl/RoiPct`，普通开仓/加仓只带 `sigLast/sigMark/gapBp`（`applySignalQuote`）。真实的净仓均价只出现在**平仓类事件**上（`trailing_close` / `catastrophe_stop` 的 `avgPx`）。

处理方式（不擅自改需求方向，只按代码事实实现并记录）：

- 引擎**自己累积**净仓均价（与实盘 `Book` 语义一致，也与金标准脚本一致）；
- 成交价口径显式成参数 `EntryPx`：`bar_close`（金标准口径，默认）/ `sig_last`（事件自带的触发瞬间价）；
- 平仓事件上的真实 `avgPx` 定位为**校准对照数据**而不是回放输入——它是"模拟 vs 实盘"比对的锚点（金标准脚本的「校准」段就是干这个），本轮未做成接口，列为遗留项 R6。

## 2. 勘察到的现状事实

全部现场核对，附路径。

### 2.1 现有回测是 AI 预测驱动，不是盘口信号驱动

- `server/service/trade/strategy/engine.go`(842 行)：输入是 `Prediction{Trend, RefPrice, High, Low, Invalidation, Confidence, Efficiency, MovePct, KeyResistance, ...}`，判定是"入场分位 α / 止盈分位 γ / 挂单 TTL / 早段疲软离场"。整套语义与盘口信号策略（净仓累加 + 反向门控 + 分档移动止盈 + 兜底止损）没有任何交集。
- `server/service/trade/repository/model.go:344`：`trade_backtest_run` 的输入列是 `prediction_interval` / `prediction_variant` / `predicted_move_pct` / `confidence`。
- `server/service/trade/backtest.go:56 computeBacktest`：拉 `trade_ai_prediction` 逐条过引擎。

结论与需求大纲 §4.2 第 3 条一致：**必须新引擎**，表可复用。

### 2.3 信号流的真实形态

`logs/argus_single/8.18-8.21剧烈上涨/` 四天实测（本轮亲自统计）：

账户B 5766 | 账户A 5696 | (市场侧 dev_sample) 4966

### 2.6 时区：一个必须先钉住的坑

- `eventstore.ParseTs`（`pkg/eventstore/normalize.go:42`）用 `time.ParseInLocation(layout, ts, time.Local)`——`strategy_event.ts` 是 JSONL 那串无时区文本对应的**本地墙钟瞬时**；
- `trade_kline.open_time` 来自 `kline_backfill.go:337` 的 `time.UnixMilli(r.OpenTime)`，也是本地 Location 的瞬时；
- 但 `backtest.go:789 parseTimeFlexible` 把裸时间串按 **UTC** 解析。

预测驱动那条路自洽（人输 UTC、比较按瞬时）。信号驱动这条路**不能沿用**：本引擎的时间锚是事件 ts，而 Telegram 消息、`logs/` 全部文件、所有离线脚本都用本地墙钟。让人为了查"8/18 00:00 那批触发"先手工换算成 UTC，是必然出错的设计，而错 8 小时正是需求大纲反复强调的"数据全在、图能画、只是整段错位"那类隐蔽错误。**集成测试第一次跑就撞上了这个坑**（详见 §5.2）。

## 3. 考虑过哪些方案

### 3.1 引擎放哪

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| A. 扩展 `strategy` 包，在 `engine.go` 旁边加文件 | 同包新增 `signal_engine.go` 等 | 字面符合"strategy 下新增"。但同包内 `Direction`/`Order`/`Params`/`CloseReason`/`Book` 会大面积撞名，改名又污染预测引擎的既有 API；且任何编译错误都可能连带打断预测回测 | ❌ |
| **B. 子包 `strategy/signal`** | 新目录，纯领域逻辑、零 IO | 同样在 `strategy` 下；命名空间独立、`engine.go` 一行不动、可独立单测；代价是调用方多一个 import | ✅ **选中** |
| C. 独立域 `service/signal_backtest` | 新业务域 | 分层最"干净"。但它不是新业务域——共用 `trade_backtest_*` 三张表、共用 `TradeService`，拆出去要么复制仓储要么反向依赖 `service/trade` | ❌ |

### 3.2 判定逻辑：复用实盘函数 vs 在回测里重写

这是本任务最关键的一个决定。

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 在 `signal` 包里重写 trail / gate / cap 判定 | 零依赖、包很轻。但**两份实现必然漂移**：改一次分档比例、改一次门控口径，就多一个"回测有效、实盘不一致"的缺口。而需求大纲明写"回测与实盘共享参数定义" | ❌ |
| 把纯判定逻辑抽到 argus_single 的新 leaf 包，两侧共用 | 架构上最正。但要动 `pkg/monitor` 的 `TrailState`/`ExitConfig`/`Tier` 四个类型（`trail_persist.go` 在持久化 `TrailState`），得靠 type alias 兼容——改动面扩到实盘的持仓状态持久化路径 | ❌ 收益不抵风险，且"不改实盘策略逻辑" |
| **直接 import `pkg/monitor` 与 `pkg/trade`，复用导出的纯函数** | 回测与实盘共用同一份判定，物理上不可能漂移。代价：`service` / `manager-api` / `oracle` 三个模块的 go.sum 多两个间接依赖（`gorilla/websocket`、`telegram-bot-api`，因为 `pkg/monitor` 里有 WS 与 TG 客户端） | ✅ **选中** |

只有两处**没有**复用（都是不可导出的三行公式，已在代码注释里指回源头）：
- `netRoiPct`（`pkg/trade/reduce_pnl.go:7`）→ `book.roi()`
- `estimateReducePnl`（同文件:21）→ `book.pnlPerContract()`
- `isReduction`（`pkg/trade/reverse_gate.go:31`）→ 引擎里的 `nb.side != side` 分支

### 3.3 bar 内怎么评估出场（金标准的两套口径怎么复用同一个状态机）

这是实现上最细的一处。金标准脚本有两个分支：

```python
# non-pess:  pct = roi(c); rebase; activate; peak; trail 测试
# pess:      rebase 用 roi(c) → 不利极值测 trail → 有利极值 activate/抬峰
```

而 `monitor.EvaluateExit` 把"状态更新"和"决策"揉在一次调用里，pess 分支拆不出来。

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 只做 close 口径 | 能直接复用 `EvaluateExit`。但悲观口径是研究里的主口径之一（`FINE_PATHS` 一半的路径是 pess），少了它无法与 `study_fine.csv` 对齐 | ❌ |
| 两套口径各写一遍状态机 | 与金标准逐行对齐。但 trail 状态机就有了两份实现，回到 §3.2 已否决的问题 | ❌ |
| **`EvaluateExit` 当统一状态机 + 两个前置判定** | 见下 | ✅ **选中** |

选中方案的形状（`engine.go evalBook`）：

```
(1) 兜底止损前置：用一根内极值判断是否穿越触发线
    long: bar.Low <= avg·(1−S/(L·100))    short: bar.High >= ...
    成交价 = 触发线再过冲 overshoot 个 ROI 点；悲观口径取"极值与过冲价里更差的"
(2a) close 口径：EvaluateExit(size, roi(bar.Close), cfg, st)  ← 与金标准 non-pess 逐行等价
(2b) 悲观口径：
     · 加仓 rebase 用 roi(bar.Close) 先做掉（EvaluateExit 里的 rebase 分支就不会再用有利极值重算）
     · 不利极值 vs 上一根留下的 peak·(1−r) 前置判定，触发则按触发价成交
     · 再 EvaluateExit(size, roi(有利极值), cfg, st) 推进激活/峰值
```

**为什么 (2b) 里的 `EvaluateExit` 不会误触发**：前置判定已经挡掉能触发的情形，而 `roi(不利极值) ≤ roi(有利极值)`，所以若有利极值都跌到退出线以下、不利极值必然更低，前置判定早就返回了。兜底同理。也就是说 (2b) 的 `EvaluateExit` 只可能返回 `Hold`——它在这条路上纯粹充当"官方状态机"。这一点被 `TestTrailStateMachineMatchesLiveEvaluateExit` 与 6 个金标准口径共同钉住。

**为什么兜底要用一根内极值而不是收盘**：实盘 `position.monitor.interval_seconds = 5`，盘中插针必然被抓到；只看收盘会系统性漏掉插针，那是**高估**收益。这也是"按不利方向结算"的落点——兜底判定排在移动止盈之前。

### 3.4 `signal_threshold` 变更怎么处理

事实：`gapBp` 只在触发时落盘，被生产阈值结构性截断（实测 min = 5.01bp / 该实例 3bp）；`dev_sample.DevCross` 是不经阈值过滤的穿越计数，直接就是 λ(θ) 的测量。

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 一律拒绝阈值变更 | 最保守。但"阈值该不该从 3bp 调到 5bp"是真实存在的研究问题，直接堵死等于砍掉一半需求 | ❌ |
| 按 λ 比例缩放 PnL | 一行代码。但它假设"信号数翻倍 ⇒ 收益翻倍"，而净仓 + cap + 门控是强非线性系统（cap 打满后新增触发一律 cap_skip），这个假设明显错，还会给出一个看起来很精确的数字 | ❌ 比不给结果更有害 |
| **λ + 按 \|gapBp\| 门限筛的近似回放，全程标频率级** | 抬高阈值：`\|gapBp\| ≥ θ` 的筛选在**门限上是精确的**，只是 edge-trigger 的 in-band re-arm 动态没有重推（θ0 下被"同向抑制"的偏离在更高 θ 下可能变成新的首次触发），所以仍是近似；降低阈值：无法从事件流补出新触发点，只给 λ、不产 PnL | ✅ **选中** |

落地：`fidelity.go Classify()` 判等级并生成警示，`replay.go` 在降阈值时直接返回"只有 λ 的结果"，`lambda.go` 算 λ 曲线 + 插值 + **自检**。

**自检这一项是主动加的**：`dev_sampler` 与生产判定共用 `EvaluateDeviationSignal`（`deviation_rule.go:44`），所以 λ(θ0) 应当与真实事件流的触发密度一致。`LambdaSelfTest = 真实触发/天 ÷ λ(θ0)`，偏离 [0.5, 2] 就直接把结论标成"λ 推断不可信"。这正是"可信度显式可见"要暴露的东西——比给一个没人知道该不该信的比值有用得多。

### 3.5 一行逐笔明细代表什么

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 一行 = 一次触发 | 与预测驱动的"一行 = 一个信号"对称。但净仓模式下一次触发只是加一张仓，没有独立的开平价与盈亏，绝大多数行的结算列会全空 | ❌ |
| **一行 = 一个持仓生命周期**（某一侧从 0 张累积到平仓/削零） | 结算列都有意义（均价/平仓价/张数/ROI/PnL/峰值/加仓次数），与实盘 `trailing_close` 事件一一对应，也正是 r10 要派生的 episode 单位 | ✅ **选中** |

出场归因四类：`trailing` / `catastrophe` / `reduce`（反向减仓削零）/ `eod`（窗口结束仍持仓）。
`reduce` 与 `eod` 都是金标准脚本里"藏在汇总数字里"的东西（脚本只打 `盈利减仓 18` 与 `期末持仓`），拆成明细行才能在页面上点开看。

### 3.6 表：复用 vs 新建

任务说明明写"表骨架可复用"。核对三张表后确认可行：

- `trade_backtest_run`：加 `engine_kind`（`default:'prediction'`，既有行自动归到预测驱动）+ `instance_key` / `account_label` / `signal_source` / `fidelity` / `fidelity_note` / `signal_count`；
- `trade_backtest_trade`：`direction` / `open_price` / `close_price` / `close_reason` / `pnl` / `fee` / `net_pnl` / `leverage` / `opened_at` / `closed_at` 全部可直接用；缺的是净仓口径的四个字段，加 `contracts` / `max_contracts` / `add_count` / `peak_pct` / `reduced_pnl`；
- `trade_backtest_metric`：`trade_count` / `win_rate` / `gross_pnl` / `fee_total` / `net_pnl` / `expectancy` / `profit_factor` / `max_drawdown` / `sharpe` / `avg_hold_secs` / `trail_count` / `sl_count` 直接复用（`sl_count` 承载兜底止损笔数，与"止损笔数"语义一致）；加 `fidelity` + 信号侧计数 + λ 三列。

**`fidelity` 为什么同时落在 run 和 metric 上**：横向对比页是按 metric 行排序的，精度等级必须跟着每一行走，否则事件级与频率级会被排进同一张榜——那正是需求大纲 §6.1 第 7 条"寻优不误导"要防的事。

**为什么不新建 `signal_backtest_*` 三张表**：`GetBacktestRunDetail` / `GetBacktestMetrics` / K 线详情弹窗 / 逐笔分页这些读侧能力全部现成，新建表要把它们复制一遍；而两套引擎的输出维度重合度超过 70%。

### 3.8 种子仓怎么推

回放窗口的左端几乎总是切在持仓中间，不灌种子仓会让第一批信号在空仓上重新起步——前若干笔的分档、门控、cap 判定全错。

金标准脚本的规则是"第一条同时带 `avgPx + size + netSide` 的事件"。核对真实数据，`logs/argus_single/events-0702` 里账户A 的第一条业务事件正是：

```
2026-06-28 22:37:18 gate_block short net=long 14 avg=60258.105
```

`gate_block` 携带净仓快照（`manager.go:568` 组装时带了 `NetSide/Size/AvgPx/LastPx`），而 `open` 不带 —— 所以拦截事件是窗口起点唯一可信的旧仓来源。

**比脚本多加了一道护栏**：脚本的窗口是人挑的、必然切在持仓中间；本引擎的窗口由使用者任选。如果窗口起点本来就是空仓，第一条带快照的 `gate_block` 可能出现在若干次 `open` 之后——那时的持仓是回放自己建起来的，再灌一次种子等于把同一批仓位开两次。于是规则改成：**只认出现在第一条 `open` 之前的快照**。两个方向都有单测（`TestSeedFromSignalsIgnoresSnapshotAfterFirstOpen` / `...AcceptsSnapshotBeforeAnyOpen`）。

### 3.9 仓位上限：公式 vs 固定值

实盘的 `PositionCapGuard.EnsureInit`（`position_cap.go:83`）语义是"**第一个算得出来的 `N_max` 缓存到进程结束**"，之后价格再变也不重算。金标准脚本用的是固定 cap。

两者都要支持，且实盘那条必须照抄懒冻结语义——否则上限会随价格漂移，同一组参数在不同窗口给出不同 cap，寻优结果不可比。`CapOverride > 0` 走固定值（金标准口径），否则走 `ComputeMaxContracts` 并在第一个可用价格上冻结（`TestCapFromLiveFormulaFrozenOnce` 钉住：价格腰斩后 cap 不变）。

### 3.10 趋势闸的动量从哪来

实盘的动量来自 tick 流（`TrendTracker` 内部按分钟去重成 close 语义）。回测只有 1m 收盘，喂进同一个 `TrendTracker` 即可——语义天然对齐。

但**动量要读在哪个时刻**上，第一版写错了：读 `Momentum(signal.Ts)`。`TrendTracker.prune` 以"最新样本时刻"为基准裁剪（只留窗口边界前最后一点），用落在上一根之内的信号 ts 去问 `Momentum`，参考点会落进窗口内、恒返回 `ok=false`——趋势闸形同关闭。单测（`TestTrendGateBlocksCounterTrendAndWarmupPasses`）直接把这个 bug 打红了。改成读"最后一个喂进 tracker 的样本时刻"。1m 数据下两者最多差一根，是 60 秒粒度的固有对齐误差，已写进 fidelity 注记（`NoteTrendGateBar`）。

`momOK=false`（覆盖不足一个窗口）时放行，与实盘重启后未回填的语义一致。

### 3.11 被否决的其他想法

- **从 1m K 线推信号**：需求大纲 §3.3 已用实测否决（K 线无 mark price；28.7% 的信号分钟内触发 ≥2 次、承载 48.6% 全部触发、单分钟最多 5 次）。代码里写成包头第一条硬约束 + `NoteNoMarkInKline` 注记。
- **按 λ 比例缩放 PnL**：见 §3.4。
- **对信号流去重**：同秒多条触发是常态，去重会直接丢真实触发。`SortSignals` 用 `SliceStable` 保序、`ListEvents` 按 `(ts, id)` 排序，都刻意不去重。
- **回测窗口右侧加 pad 让持仓走完**（预测驱动的 `backtestRightPad` 那套）：净仓策略的持仓中位约 2 小时、最长 24.9 小时，pad 多少都可能不够；而且 pad 出来的区间里还有真实触发却不回放，会造出一段"只平不开"的假行情。改成明确记 `eod` 并按最后一根收盘标记浮动。
- **给回测加"最优参数"式的单一结论**：需求大纲 §2.2 明确不做，且 §3.5 指出现行 champion 的符号一致率只有 0.56。引擎只产指标不产结论。

- **集成（真库）**：新增列真的被 AutoMigrate 建出来（27 列逐个查）且既有列没丢、整条链路写出一致的 run/metric/trade、按 `instance_key + account_label` 过滤确实只取本实验体的触发流（账户B 的触发不得混入）、区间内没有事件时明确 failed 且带原因。

### 5.3 验证过程中发现并修掉的三个真问题

1. **趋势闸形同关闭**（§3.10）。`Momentum(signal.Ts)` 与 `TrendTracker.prune` 的基准不一致，恒返回 `ok=false`。单测直接打红，改成读"最后一个样本时刻"，并把这个 60 秒粒度的对齐误差写进 fidelity 注记。
2. **回测窗口错 8 小时**（§2.6）。集成用例第一次跑就报"区间内没有触发事件"——`parseTimeFlexible` 按 UTC 解析，而 `strategy_event.ts` 是本地墙钟瞬时。新增 `parseSignalWindowTime` 按 `time.Local` 解析并加单测锁死。**这个错误如果只跑单测是发现不了的**：单测里事件与窗口用同一个 `time.Time` 构造，天然自洽；只有过一遍真库、走完"字符串 → time.Time → DSN loc → DATETIME 列"这条链路才会暴露。
3. **种子仓可能把同一批仓位开两次**（§3.8）。金标准脚本的窗口是人挑的，规则直接照抄会在"窗口起点是空仓"时出错。加了"只认第一条 open 之前的快照"护栏 + 双向单测。

另外两处是自查时改的：`recordEpisode` 在削零场景下 `bk.size` 已减到 0，`Contracts` 会记成 0（改成显式传 `contracts`/`pnl`）；`gorm.Migrator().HasColumn` 传表名字符串会 panic（改传模型指针）。

### 5.4 待测试阶段验证（本轮无法覆盖）

- **真实事件数据上的端到端**：需要 argus_single 的事件双写（r4）实际跑起来并覆盖 8/18–8/21，或先做 r6 的历史 JSONL 回灌。本轮的集成用例用的是构造事件。
- **验收 §6.1 第 6 条的"触发次数与真实触发数完全一致"**：口径说明见 §6 遗留项 R3（有种子仓时 `signal_count + signal_dropped = 区间内事件总数`，不是 `signal_count = 总数`）。
- **验收 §6.1 第 7 条（寻优复跑 `study_fine.csv` 10 个精算格）**：那是 r16 的范围。本引擎已备好它需要的三样东西——`CatastropheOvershootRoiPts`（+5）、`TakerFee`（0.00012）、`DailyMTM`（熊市月 bootstrap 输入），但多路径降噪协议（8 个 offset × 2 个 drop seed × 2 个评估口径）与三关判定不在本轮。
- **频率级路径的真实 λ**：需要 `dev_sample` 表有实际数据；r3 落地后 λ 估计会更细。
- **性能**：单窗口 4 天 / 5383 根 / 334 触发的回放在本机 < 5ms。长窗口（23 天以上）与 r11 的批量扫描并发未压测。

| # | 风险 / 待确认 | 说明与建议 |
| --- | --- | --- |
| R1 | 两个新接口缺权限资源 | `POST /backtest/signal-runs`、`GET /backtest/signal-sources` 需要往 `resource_new` / `role_resource_new` 补行。生成幂等 SQL 需要 `role_id`，请测试或运维提供后用 `add-permission-resources` 技能出 SQL |
