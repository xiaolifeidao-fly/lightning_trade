## 1. 需求怎么理解

需求级文档 §3.1 给了容量结论，任务说明给了范围。我把它拆成三件互相独立的事：

1. **秒级切片采集（写侧）**：在 argus_single 已有的双 WS 流（币安 `fstream` + DeepCoin `stream`）上挂一个按秒聚合的环形缓冲；每次盘口信号触发时，把触发前后各 60 秒的逐秒行情 flush 成**一条记录 + 三条 JSON 序列**（DC last / DC mark / 币安 last，各 121 点），带 `instance_key`，90 天滚动保留。
2. **dev_sample 粒度提升**：`devSampleInterval` 从 `time.Minute` 改成 10 秒，并落库。`DevSampleThresholdsBp` 的九个阈值与 `DevCross`/`DevOver` 的结构**不动**——它是频率级回测（λ(θ)）的唯一数据源。
3. **不做**：不落全时段秒级 K 线（单币双源约 18GB/年，需求大纲已否决）。

两个必须先想清楚的隐含约束：

- **"±1min" 里的 "+1min" 是未来**。触发那一刻右半窗还没发生，所以"触发时 flush"在物理上不可能一步完成——必须有一个延迟落盘机制。这是本任务最重要的一条设计约束，任务说明的"触发时 flush"只能理解为"触发时定格窗口、到期落盘"。
- **"不引入新锁序"是硬约束**。`price_monitor.go` 已有 `mu`（价格读写锁）与 `signalMu`（信号派发锁）两把锁，交易路径穿过它们。新增缓冲不能嵌进这两把锁的临界区里，否则凭空多出一条锁序，将来任何一处反向加锁就是死锁。

范围边界上我额外确认了一件事：**读侧必须一起改**。因为 `server/service/argus_event/slice.go` 的包注释里明写着"r3 尚未实现，本接口先用 strategy_event 的稀疏观测点降级供数，r3 落地后只需把 tickSource 换成 signal_slice 并补满 points"。写侧建了表而读侧不接，等于交付了一张没人读的表，验收标准里"触发瞬间可下钻"仍然不成立。

### 2.3 λ(θ) 读侧对粒度变化的既有准备

`server/service/trade/strategy/signal/lambda.go:141 windowStep` 已经写着"r3 把粒度从 1min 提到 10s 后，同一张表里可能并存两种步长，用中位数比用首个间隔稳"，取相邻窗口间隔的**中位数**作为步长。也就是说读侧已经为本次改动做过准备，改 `devSampleInterval` 不需要改 λ 推断代码。这是勘察阶段最有价值的一条发现——它把"改粒度会不会破坏频率级回测口径"这个最大风险直接消掉了一半。

另一半风险（穿越计数会不会因为窗口变小而变化）由 `DevSampler` 自身的注释回答：`lastDerived` 跨窗口保留，"若随窗口清零，跨窗口边界的同向持续偏离会被重复计成新穿越"。所以同一段行情切成 6 份小窗与 1 份大窗，穿越总数**完全相同**，λ 只是分摊得更细。

## 3. 考虑过哪些方案

### 3.1 秒级点位怎么存

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A 按行存秒级点位 | 每秒一行 `(instance, instrument, ts, dc_last, dc_mark, bin_last)` | 查询最自然、可按时间范围任意裁；但需求大纲 §3.1 已实测：±3min 窗口 worst case 5256 万行/年，与"全时段秒级"同量级（信号成簇，窗口互相覆盖） | ❌ 否决，与已否决的全量秒级同量级 |
| B 一行 + JSON 序列 | 一次触发一行，三条等长 JSON 数组 | 7 万行/年 ≈ 0.44GB/年；代价是不能按秒做 SQL 过滤（必须整条取回在应用层展开） | ✅ 采用，任务说明也是这个口径 |
| C 一行 + 二进制 blob | 同 B，但用定长 float64 数组压成 binary | 体积再小约 3 倍；但完全不可读、DBA 排查时看不见内容、且没有任何现有代码路径处理 blob | ❌ 否决，省的那点空间买不到 0.44GB/年 已经能接受的现状 |

B 的"不能按秒 SQL 过滤"不是真损失：切片的唯一用途是**按一次触发下钻**，永远是整条取回。

### 3.2 右半窗怎么等

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A 触发时开一个 goroutine `time.Sleep(60s)` | 直观 | 信号成簇时会同时挂几十个 goroutine；且每个都要独立持有缓冲引用，收尾语义混乱 | ❌ |
| B 挂在行情 tick 上顺便检查到期 | 零额外 goroutine，与 `observeDeviationLocked` 的窗口推进同风格 | **行情断流时永远不落盘**——而"WS 断了那一分钟"恰恰是最该看的切片；`dev_sampler` 有同样的性质（"窗口内全是坏 tick，不推进窗口"），但它丢的是采样、这里丢的是整条切片 | ❌ |
| C 一个 1s ticker 的独立 flusher goroutine | 到期即落盘，与行情是否还在完全解耦；收尾时可以把手上未满窗的切片一次交出去 | 多一个 goroutine + 每秒一次 map 遍历（当前 1 个币种、待办通常 0~2 条） | ✅ 采用 |

### 3.3 锁怎么放

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A 复用 `signalMu`（照抄 `observeDeviationLocked`） | 与 dev 采样接线完全同构 | 币安流也要写缓冲，那就要在币安 handler 里也拿 `signalMu`——币安 aggTrade 是高频流，会与信号判定争锁，直接压到交易热路径上 | ❌ |
| B 新加一把 `sliceMu`，但在 `signalMu` 内调用 | 只需改一处接线 | 制造出 `signalMu → sliceMu` 这条**新锁序**，违反任务说明的硬约束 | ❌ |
| C 新加一把 `sliceMu` 作为**叶子锁**：唯一获取点在 `slice_buffer.go`，获取时绝不持有 `mu`/`signalMu` | 无任何锁嵌套 ⇒ 结构上不可能死锁；临界区只有几十纳秒的数组写 | 需要把 DC 侧的 observe 挪到 `signalMu.Lock()` **之前**（而不是像 dev 采样那样在临界区内） | ✅ 采用 |

C 还顺带解决了另一个问题：`handleBinanceMessage` 里 `pm.mu` 已经解锁之后才调 observe，所以币安侧同样零嵌套。

### 3.4 币安 last 从哪来

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A 在 DC tick 时刻顺手读 `pm.binancePrices` 缓存 | 改动最小，只碰一个函数 | DC 流断掉的那几秒币安侧会**跟着变空**——而"只有一边断流"正是要看清的场景；且 `pm.mu.RLock` 要么嵌进 `signalMu`（新锁序），要么再多一次锁 | ❌ 否决 |
| B 币安流自己落槽（在 `handleBinanceMessage` 里 observe） | 两条流真正独立可见，任务说明"在双 WS 流上挂"也是这个字面意思 | 高频流上多一次叶子锁获取 | ✅ 采用 |

### 3.5 切片走不走 JSONL

需求大纲的硬不变量之一是"JSONL 不立刻废弃，双写保留 3 个月，它是回测平台和全部历史分析脚本的输入格式"。那切片要不要也双写 JSONL？**否决**，三条理由：

1. 它在触发那一刻**不完整**（右半窗还没发生），写不进"触发时刻"那一行；
2. 单条载荷约 4KB，JSONL 每天要被导出/解析，塞进去纯粹是膨胀，而且**没有任何现存脚本读它**；
3. 它有 90 天滚动保留的生命周期，JSONL 根本没有这个概念。

代价必须写明：**切片丢了就是永久缺失，没有 JSONL 兜底可以回灌**。所以 `EmitSlice` 的丢弃告警文案与事件侧刻意不同，明确写"无 JSONL 兜底"。

### 3.6 包放哪（避免依赖倒挂）

`pkg/eventlog` 是 leaf 包，给它加 gorm 会造成 `trade → eventlog → gorm` 的循环——这条教训 r4 已经踩过并写进了 `pkg/eventstore` 的包头。切片有同样的形状：产出方是 `pkg/monitor`，落库方是 `pkg/eventstore`。

| 方案 | 取舍 | 结论 |
|---|---|---|
| A `monitor` 直接 import `eventstore` | 改动最少；但把 gorm 拖进交易 goroutine 所在的包，monitor 的单测从此要拉 gorm，而且 `eventstore` 永远不能反向引用 monitor | ❌ |
| B `eventstore` import `monitor` | 把整条 trade 栈拖进写库包 | ❌ |
| C 载荷 + Sink 接口放新 leaf 包 `pkg/marketslice`，两侧各自 import 它，由 `initialization`（其实是 `eventstore.Setup`）组装时注册 | 与 `eventlog.Sink` 完全同构；`marketslice` 只依赖 `logrus` | ✅ 采用 |

环形缓冲本身放在 `pkg/monitor/slice_buffer.go`，而不是塞进 `marketslice`——它是 monitor 的采集实现，和 `DevSampler` 同层，也照 `DevSampler` 的纯累加器写法（不持有时间、不持有锁）。

### 3.7 读侧的时间原点（本轮最容易做错的一处）

一开始我打算按 `strategy_event.ts` 精确等值去取切片。写完才意识到不成立：`trade.signal.delay_seconds` 默认 5 秒，`SignalScheduler` 延迟派发，成交类还要再加一次下单往返——`service.go` 的 `signalGroupWindowSec = 30` 注释里就写着"成交类实测可比拦截晚数秒"。按等值取永远取不到切片。

于是有了第二个问题：取到之后，points 的 `offsetSec` 以谁为原点？

| 方案 | 取舍 | 结论 |
|---|---|---|
| A 以事件 ts 为原点（沿用降级路径的写法） | 契约不变；但切片窗口是 `[锚点-60, 锚点+60]`，重新对齐到事件 ts 后**右半窗凭空缺掉 lag 秒**，默认 ±60 的请求永远 `tickComplete=false`，读起来像"还是降级态" | ❌ |
| B 以切片锚点（偏离穿越时刻）为原点，事件 ts 通过 `IsTriggerTs` 标在它自己那一秒 | 121 点完整、语义也更对——切片本来就是围绕穿越瞬间采的；代价是返回体多两个字段（`sliceAnchorTs` / `anchorLagSec`）说明这件事 | ✅ 采用 |

B 附带一个好处：`anchorLagSec` 本身就是可观测量，"从偏离穿越到成交落地花了几秒"以前只能靠人读日志比时间戳。

## 4. 方案怎么落到改动

### 4.1 新增 leaf 包 `server/argus_single/pkg/marketslice/marketslice.go`

- `HalfWindowSeconds = 60`、`SeriesPoints = 2*Half+1 = 121`（两个常量的关系有单测钉死，读侧按 `offset+half` 定位下标，改一个不改另一个会让整条曲线错位）。
- `Slice`：`Anchor / InstIdRaw / StartAt / EndAt / HalfWindow` + 三条 `[]*float64` + `DcPoints/BinPoints` 覆盖率。
- `Sink` 接口 + `RegisterSink/ResetSinks/SinkCount/Emit`，逐字照 `pkg/eventlog/sink.go` 的形状，含单 sink panic 隔离。
- **`nil` 元素的含义写进包注释**：该秒没有行情，不是 0，不许插值。这是全链路唯一一次机会把这条口径写在数据结构上。

### 4.2 新增 `server/argus_single/pkg/monitor/slice_buffer.go`

- `SliceBuffer`：`slots []sliceSlot`，按 `epochSec mod cap` 定位，槽位上是别的秒就整体清零（环形覆盖不需要显式淘汰）。
  - `slot(sec)` 写路径（会清零）与 `at(sec)` 只读路径（不清零）**必须分开**——`Snapshot` 用 `slot` 会把缓冲擦掉一半，这一点有单测 `TestSliceBufferSnapshotIsReadOnly` 钉住。
  - 取模用 `((sec%n)+n)%n`，负 epoch 秒不会算出负索引。
  - `ObserveQuote` 的 `mark<=0 || last<=0` 忽略，与 `DevSampler.Observe` 同口径。
  - 秒内多 tick **取最后一个**（秒收盘口径）：切片要回答"这一秒行情走到哪"，均值会抹平瞬时极值，恰好抹掉触发瞬间最该看的东西。
- `sliceBufferSeconds = 240`：下界是 121，取 2 倍留裕度——右半窗要等 60 秒，期间新 tick 继续覆写，容量恰好 121 时最老那一秒会被 `anchor+61` 顶掉。240 秒 ≈ 12KB/币种。
- `PriceMonitor` 接线：`observeSliceQuote` / `observeSliceBinance` / `armSlice` / `takeDueSlices(now, force)` / `runSliceFlusher`。
  - `armSlice` 同一秒去重（同秒多账户各自判定会调进来多次，重复登记只会产出完全相同的行）。
  - `takeDueSlices` 锁内只做内存快照，投递在锁外——与 dev_sample 的落盘时机同规矩。
  - `force=true` 用于收尾：`ReloadMonitor` 会 `Stop()` 旧 monitor，手上的切片如果直接丢掉，一次配置热更新就会吃掉一整批触发。改成如实交出去，覆盖率字段会暴露右半窗没凑满。
  - map 为 `nil`（部分单测直接构造 `PriceMonitor`）时整条链路静默关闭，不 panic。

### 4.3 `server/argus_single/pkg/monitor/price_monitor.go`

- 结构体加 `sliceMu / sliceBuffers / slicePendings` 三个字段 + 注释说明 `sliceMu` 是叶子锁。
- `NewPriceMonitor` 初始化两个 map。
- `Start()` 起 `runSliceFlusher`（挂 `pm.wg`，`Stop()` 的 `wg.Wait()` 会等它收尾）。
- `handleBinanceMessage`：`pm.mu.Unlock()` **之后**调 `observeSliceBinance`。
- `handleOrderBookSignal`：`pm.signalMu.Lock()` **之前**调 `observeSliceQuote`；`fire` 之后（`signalMu` 已解锁）调 `armSlice`。

### 4.4 `server/argus_single/pkg/monitor/dev_sampler.go`

`devSampleInterval` 由 `time.Minute` 改成 `10 * time.Second`，并把三件事写进注释：为什么缩窗不改变 λ 口径（`lastDerived` 跨窗口保留）、读侧步长自适应在哪（`lambda.go windowStep`）、阈值列表与 `DevCross/DevOver` 结构为什么不动。

### 4.5 `server/argus_single/pkg/eventstore`

- `model.go`：新增 `SignalSlice`（表 `signal_slice`），唯一键 `uk_signal_slice_anchor(instance_key, instrument, ts)` + `idx_signal_slice_ts`；加进 `Models()`。
  - **不另算哈希**：三列全 `NOT NULL`，没有事件表那个"NULL 互不相等"的问题；且一次触发在一个实例上就该只有一条切片，重放必须落在同一行，不能因为载荷差一个点就插新行。
  - 包内明确标注它**不是 append-only 真源**，是 90 天滚动的派生观测品。
- `convert.go`：`Envelope` 加 `Slice *marketslice.Slice`，`Rows` 加 `Slice []*SignalSlice`，`Convert` 在最前面分流；新增 `ConvertSlice` + `marshalSeries`。锚点 `Truncate(time.Second)`——必须能与秒精度的 `strategy_event.ts` 对上。
- `store.go`：`EmitSlice` 实现 `marketslice.Sink`（复用同一条队列与背压）；`flush` 增加 `signal_slice` 的插入，但用**独立的 `sliceBatchSize = 20`**——单行约 4KB，按 200 行分批会攒出 800KB 的 SQL 撞 `max_allowed_packet`。
- `retention.go`（新增）：`SliceRetention = 90 天`，6 小时一轮、每批 `LIMIT 500`、单轮最多 200 批的分批 DELETE；独立 goroutine，退出条件是 `ctx.Done()` 或 writer 收尾（`s.done`）。**只清 `signal_slice`**，三张事件表一行不碰。
- `runtime.go`：`Setup` 里 `marketslice.RegisterSink(store)` + `StartSlicePurge(ctx)`；`Shutdown` 里 `marketslice.ResetSinks()`。

复用 `Store` 的队列而不是另开一条 writer：切片与事件共享"非阻塞入队 + 批量 INSERT + 失败只计数"这套背压策略，另开一套只会多一份需要同步维护的丢弃口径；频率上也不需要（每次触发一条）。

### 4.6 读侧 `server/service/argus_event`

## 7. 剩余风险与待确认项

1. **切片与事件的关联是启发式的**。事件行里没有"锚点"字段，只能按"不晚于事件 ts 的最近一条锚点、回看 30 秒"去找。同一簇里 20 秒内连着两次触发时，晚到的成交事件可能被归到后一个锚点上。两条切片窗口高度重叠，图形结论不受影响；要精确关联得在埋点上给事件带一个锚点时间戳（本任务范围外，建议记进 r13 的复盘页需求）。
2. **切片没有兜底真源**。队列满被丢或写库失败即永久缺失，JSONL 补不回来。已在 `EmitSlice` 的告警文案里点明，`Stats().Dropped/Failed` 是唯一线索。
3. **配置热替换会产出未满窗切片**。`ReloadMonitor` 停旧 monitor 时按 `force` 把手上的切片交出去，右半窗不完整，由 `dc_points/bin_points` 如实反映。这比整批丢掉好，但前端画图时要看覆盖率而不是假定 121 点都有值。
4. **`dc_points` 的正常值不是 121**。行情安静的那几秒 DeepCoin 可能没有 `PO` 推送，覆盖率天然低于满值；"覆盖率低"不等于"采集有问题"。基线需要上线后实测一段再定告警阈值。
5. **90 天清理由每个实例各自跑**。三实例会重复删同一批行（DELETE 幂等，无害），但三份 6 小时 tick 会有轻微重叠。如果将来实例更多，值得挪到 manager-api 侧单点执行。
6. **r12 的切片抽屉还没建**。本轮只同步了前端数据模型，页面组件属于 r12；读侧契约已经就位，r12 可以直接消费。
7. **`server/oracle` 模块 `go build` 报 `missing go.sum entry for github.com/go-redis/redis`**。本轮未改动 `server/oracle` 与 `server/common`（两者在本轮开始前的 `git status` 里就已是 modified），属于先行任务遗留的依赖状态，不在本任务范围内，但需要有人补一次 `go mod tidy`。
