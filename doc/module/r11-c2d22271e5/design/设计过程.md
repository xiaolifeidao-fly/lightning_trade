### 1.2 目标复述

一次提交多组参数，跑出**可横向对比**的指标矩阵，并且让"可比性"本身显式可见。

逐条对照任务说明：

| 任务说明 | 我的理解与落点 |
| --- | --- |
| 批量创建 run + 并发执行 + 汇总 | 新增 `trade_backtest_batch`（批次）+ run 上加批次三列；有界并发 worker 池；批次进度原子累加 |
| 复用 r8 的回测引擎 | 一行引擎代码都不新写；把 r8 的 `computeSignalBacktest` 拆成「取数」与「回放」两段，批量复用同一份 |
| 复用 `trade_backtest_metric` 的胜率/盈亏比/最大回撤/夏普/出场分布字段 | 指标 diff 只读既有列（`win_rate` / `profit_factor` / `max_drawdown` / `sharpe` / `trail_count` / `sl_count` / `reduce_close_count` / `eod_open_count`），未新增任何指标列 |
| 提供与基线差异计算，基线默认取所选实例当前生产参数 | `signal_baseline.go` 读 `argus_config` 已发布快照映射成 `signal.Params`；批次冻结基线快照；参数 diff + 指标 diff |
| 对比结果按 fidelity 分组呈现 | 详情接口返回 `groups[]`，每组一个精度等级、组内独立排序；**接口层从不返回跨精度的全局榜** |
| 【不做】禁止把频率级与事件级结果放在同一排序里比大小 | 结构上就做不到混排：不同精度进不同 group；跨精度行的 `metricDiff=nil` 且带 `diffBlockedReason` |
| 【不做】不在本任务实现自动搜索与统计判定（属 r16） | 组必须由调用方显式给出；单批 ≤64 组并在超限错误里明确指向 r16；不输出任何"最优参数"结论、不做符号一致率/分位判定 |

**范围边界**：本任务是后端能力。可视化页面属 r14（`盘口信号回测与寻优可视化页`，执行层第 6 层，依赖 r16），所以"分组呈现"在本轮落成**接口层的分组结构 + 中文精度标签 + 警示文案**，而不是页面。这个边界写在这里是为了避免后续误判本任务漏交付前端。

### 2.2 `signal.Replay` 的一个关键行为（决定了排序逻辑）

`strategy/signal/replay.go` 里，**降低**阈值的频率级组直接早返回：

```go
if p.SignalThresholdBp < p.BaselineThresholdBp {
    res.Fidelity = fid; res.SignalReplayed = 0
    res.SignalDropped = len(signals); return res, nil
}
```

也就是这类组**只有 λ(θ)、没有 PnL**，落库后 `net_pnl = 0`。这个 0 不是"不赚不亏"，是"没算"。如果对比矩阵一律按净利排序，它会显示成"最差的一组"——这是一个必须专门处理的误读源（见 §4.3）。

### 2.3 配置面的真实缺口（决定"基线"能取到什么）

按需求大纲 §3.2 逐项核对 `service/argus_config/repository` 与 `dto`：

| 基线字段 | DB 来源 | 现状 |
| --- | --- | --- |
| `budget_pct` | `argus_account_risk.risk_budget` | ✅ 有列有值 |
| `catastrophe_stop_pct` | `argus_account_risk.catastrophic_stop_loss` | ✅ |
| `max_contracts_ceiling` | `argus_account_risk.max_contracts` | ✅ |
| trail 8 项 | `argus_account_risk.trailing_stop_tiers_json` | ✅（`importer.go:331` 已写入；键名 = properties 去前缀） |
| `signal_threshold` | `argus_monitor_symbol.signal_threshold`（小数） | ✅，需 ×10000 转 bp |
| `order_size` | 只有全局 `argus_config.default_order_size` | ⚠️ 账户级无列（§3.2 C） |
| `risk_equity` | 无列 | ⚠️ 按实盘 `ResolveRiskEquity` 回落 `argus_account.initial_balance` |

| `trend_gate.window_hours` / `threshold_pct` | 无列 | ⚠️ 只能按关闭处理，而实例2/3 生产上是 24h/5% |

这张表是本轮**最重要的现状事实**：基线里有 5 类字段是兜底来的。如果不把兜底说清楚，页面上"基线趋势闸 = 关闭"会被当成生产事实读，而实例2/3 明明开着——这正是需求大纲反复强调的那类隐蔽错误（数据全在、页面能画、只是整段错位）。

另一个事实：`runtimeconfig.runtimeAccount()` 目前**不读** `extra_risk_json` / `trailing_stop_tiers_json`（r5 未做），所以严格说 DB 里这些值现在还到不了运行时。但本任务的基线口径应当是"DB 里记录的生产参数"，而不是"运行时实际生效的值"——后者的收敛正是 r5 的交付物。这一点在基线说明里以"r5 待收敛"标注。

### 2.4 `account_label` 与 `account_name` 同源（基线能定位到账户的依据）

- `pkg/eventstore/convert.go:77` → `AccountLabel: e.Account`（JSONL 的 `account`）
- `argus_config/importer.go:273` → `AccountName: properties[prefix+"name"]`
- 两者都是 properties 的 `trade.accountN.name`

所以基线可以用 `accountLabel` 精确匹配 `argus_account.account_name`。这很重要：实例2 有 champion(cap26) 与 challenger(cap8) 两个账户，猜错账户 = 整批基线错一倍仓位，而且**没有任何外部现象会提示这件事**。

## 3. 考虑过哪些方案

### 3.1 批次与组的存储形态

| 方案 | 做法 | 代价 / 风险 | 结论 |
| --- | --- | --- | --- |
| **A. 一组 = 一条完整 run + 批次表只做归组**（选中） | 新增 `trade_backtest_batch`；`trade_backtest_run` 加 `batch_id` / `group_label` / `is_baseline` 三列 | 给既有大表加 3 列（`batch_id=0` 表示单跑），需要一个索引 | ✅ 组自带 `params_snapshot`/`fidelity`/`metric`/逐笔，**任一组都能在既有 run 详情页直接打开、单独重跑**；r14 不需要为"看某一组"再造读接口 |
| B. 新建 `trade_backtest_batch_item` 关联表 | 批次 → item → run | 多一张表、多一次 join，且 item 上没有任何 run 上没有的信息 | ❌ 纯粹的冗余层 |
| C. 批次表内嵌 N 组的 JSON，不建 run | 一次批量只落一行 | 组的逐笔明细无处安放；无法复用 run 详情页；无法单独重跑某组；`metric` 表的 `run_id` 外键失去意义 | ❌ 与"复用 r8 三张表"直接冲突 |
| D. 把指标冗余到批次行上（方便排序） | batch 上存一份 best/worst 指标 | 会出现"批次上的净利与组详情里的净利不一致"，且无法排查 | ❌ 明确否决，指标唯一来源是 `trade_backtest_metric` |

### 3.2 数据取几次

| 方案 | 做法 | 风险 | 结论 |
| --- | --- | --- | --- |
| **A. 批次取一次，全组共享**（选中） | 把 `computeSignalBacktest` 拆成 `loadSignalDataset` + `replaySignalDataset` | 需要改 r8 的既有函数（回归面） | ✅ 两个理由：① **正确性**——事件双写是持续在写的，各组各取一次会让先跑的组和后跑的组吃到不同触发集，组间差异里就混进了数据差异；② 性能——4 天窗口 ≈1.6 万事件 + 5760 根 1m，省掉 N−1 次全表扫 |
| B. 每组各自调 `RunSignalBacktest` | 零改动，直接 N 次调用 | 上面①的正确性问题；N=20 时 20 次全表扫 | ❌ 正确性问题是决定性的 |
| C. 批次开事务/快照隔离读一次 | 用 REPEATABLE READ 保证一致 | 长事务跨整个回放期（可能几十秒），会拖住 DB | ❌ 得不偿失，方案 A 已经解决了一致性 |

### 3.3 组参数以什么为基底

| 方案 | 做法 | 后果 | 结论 |
| --- | --- | --- | --- |
| **A. 组参数叠加在基线上**（选中） | 没给的旋钮沿用基线（= 实例当前生产参数） | 需要在建组前先解析基线 | ✅ "cap 15/26/40 三组"的 diff 里只有 cap 一行 |
| B. 组参数叠加在 `signal.DefaultParams()` 上（沿用 r8 单次回测的口径） | 未给的旋钮回落代码缺省 | 实例2 的生产参数是 cap26/S400/budget13.3/3bp，代码缺省是 ceiling20/S300/budget20；每组都会在**十几个字段**上同时偏离生产，与基线的 diff 完全失去意义 | ❌ 与"基线取生产参数"这条要求自相矛盾 |

单次回测（r8 的 `CreateSignalBacktestRun`）仍保持 B 的口径不变——那是既有行为，改它是无谓的回归风险。

### 3.4 基线从哪来

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| **A. `service/trade` 调 `service/argus_config` 的 `GetPublished`**（选中） | 跨域读，方向是"回测（下游）→ 配置（上游）"，无环 | ✅ 复用了已发布版本的解析、实例键解析与凭证脱敏；`service/trade` 已有跨域引用先例（`service/pressure/repository`） |
| B. 在 `service/argus_config` 里做映射并暴露 | 会让配置域反向依赖回测引擎的 `signal.Params` | ❌ 依赖方向错，且 argus_config 不该知道回测的存在 |
| C. `service/trade` 直接用 `argus_config/repository` 自己查已发布版本 | 要重抄一遍"找 published 版本 + 装载子表"的逻辑 | ❌ 必然与 argus_config 漂移 |
| D. 读 properties 文件 | 管理端读不到部署机上的文件，且 r5/r7 已确定 DB 是唯一来源 | ❌ |

**基线快照要冻结**：diff 一律按批次创建时冻结的 `baseline_snapshot` 算，不在查详情时重新读一次生产配置。理由是参数热更新（r5/r7 的整条链路就是为热更做的）会让同一个批次今天和明天算出不同的差异。

### 3.5 跨精度怎么防混排

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| **A. 结构上分组，接口不返回全局榜**（选中） | 详情返回 `groups[]`，每组一个精度等级，排序只在组内 | ✅ 前端拿不到混排数据，也就无从误排；符合"禁止把频率级与事件级结果放在同一排序里"的字面要求 |
| B. 返回一张全局榜 + 每行带 `fidelity` 字段，让前端自己分组 | 排序权在前端，任何一次疏忽（默认按净利排列）就把两级混排了 | ❌ 把护栏交给调用方 = 没有护栏 |
| C. 只允许同精度的组进同一个批次（创建时拒绝混合） | 简单，但"看看抬高阈值会怎样"是真实需求，混合提交本身没错 | ❌ 过度限制；错的是混排比较，不是混合提交 |

### 3.6 组内排序的口径

发现 §2.2 那个行为后，排序必须再分一层：

- 组内有任何组产出了 PnL → 按 `netPnl` 降序，`sortedBy="netPnl"`；
- 整组都不产 PnL（典型是降阈值的频率级组）→ 按 `lambdaPerDay` 降序，`sortedBy="lambdaPerDay"`——那才是这类组唯一有信息量的输出；
- 基线行恒置顶（它是参照物，不参与"谁更好"的排名）；
- 未完成/失败的行沉到组内末尾，避免空指标混在有效结果中间。

`sortedBy` 回给前端而不是内部消化：让页面能显式标出"这一列是按什么排的"。

### 3.7 被否决的其他想法

- **让批次自动生成网格（如 cap ∈ [15,40] 步长 5）**：属 r16 的搜索空间，且 r16 带降噪协议与三关判定。本任务放开就等于给了一条绕过统计护栏的路。单批上限 64 组，超限错误里直接指向 r16。
- **在对比结果里给出"推荐参数"或高亮"最优组"**：需求大纲 §3.5 明确"单路径混沌 ±70U，点估计不可信"、现行 champion 的符号一致率只有 0.56；§2.2 还明确"自动寻优不输出最优参数"。本任务只排序 + 给差异，不下结论。
- **按 `net_pnl` 在 SQL 里 ORDER BY**：排序必须在分组之后做，SQL 层排序无法表达"组内排序"，而且会让"跨精度不比大小"这条规则漏到数据库层去。仓储层 `FindRunsByBatch` 刻意按 `id ASC`（提交顺序）返回。
- **对失败组自动重跑**：静默重跑会掩盖"K 线缺口""事件没覆盖"这类必须让人看到的数据问题。失败组保留 `error_msg`，批次状态标 `partial` 并明说"缺失的组不代表结果差"。
- **不匹配 accountLabel 时退到第一个账户**：见 §2.4，直接报错并列出候选账户名。

### 4.2 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/backtest/signal-batches` | 提交一批参数组，立即返回 `batchId`（异步并发回放） |
| GET | `/backtest/signal-batches` | 批次列表（可按实例/账户过滤） |
| GET | `/backtest/signal-batches/:id` | 批次详情 = 批次头 + 基线 + **按 fidelity 分组**的对比矩阵 + 警示 |
| GET | `/backtest/signal-baseline` | 基线预览：提交前先看清"与什么比"、哪些字段是兜底 |

单组详情仍走既有 `GET /backtest/runs/:id`，不另造读接口。

### 4.3 执行流

```
POST /backtest/signal-batches
  ├─ 校验窗口 / 实例 / 账户 / 组数(≤64)
  ├─ 定基线：baselineParams 显式给 → source=request
  │           否则 argus_config.GetPublished(instanceKey) → 映射 → source=instance_published
  ├─ 基线自身过 Validate（口径同实盘启动校验），不合法整批拒绝
  ├─ 先把**全部**组的参数算出来并逐组 Validate —— 全通过才落库
  │   （否则第 20 组写错会留下 19 条 run + 一个半残批次）
  ├─ 建 batch(pending) → 建 N 条 run(pending，含 baseline 组) → 回填 baseline_run_id
  └─ 立即返回 batchId，异步 goroutine 起 RunSignalBacktestBatch

RunSignalBacktestBatch
  ├─ batch → running
  ├─ needDev = 任一组 fidelity=frequency（fidelity 建组时已算好落库，直接读）
  ├─ loadSignalDataset(window, needDev)  ← **只取一次，全组共享**
  │   └─ 失败 = 批次级失败：逐组也标 failed（不留永远 pending 的组），batch → failed
  ├─ 有界并发（默认 3，上限 8）：每组 replaySignalDataset → 落 metric/逐笔 → run→done
  │   └─ 单组 panic 只失败该组，不带走整批
  └─ 汇总：全失败 → failed；部分失败 → partial（明说"缺失的组不代表结果差"）；否则 done
```

### 4.4 对比矩阵的构造（`buildComparison`）

1. 基线精度等级取自基线 run 的 `fidelity`（回放实测值），缺失时回落 `Classify(baselineParams)`；
2. 每组：解析 `params_snapshot` → 参数 diff（对基线）→ 组标签（缺省按 diff 自动生成）→ 指标 → 指标 diff 或拒绝理由；
3. 按 `fidelity` 装桶，事件级组恒排在频率级组之前；
4. 组内排序（§3.6）；
5. 组内精度警示取并集去重（`fidelity_note` 按 `" | "` 拆）；
6. 批次含多个精度等级时追加混排警示。

**指标 diff 的四道拒绝理由**（顺序即优先级）：本行即基线 → 本组尚未产出指标 → 基线无指标 → 跨精度不得比大小 → 本组只产 λ 不产 PnL。每一条都作为 `diffBlockedReason` 回给前端，而不是静默给个空对象。

### 4.5 影响面与兼容性

| 关注点 | 处理 |
| --- | --- |
| `CreateSignalBacktestRunDTO` 的参数字段被抽进匿名嵌入结构 | Go 的 `encoding/json`（Gin 的 JSON 绑定就走它）会把无 tag 的匿名嵌入字段**扁平化**，请求体 JSON 键与嵌入前逐字一致 → 对前端零影响。已改的两处测试构造是 Go 侧的复合字面量语法要求，不是接口变更 |
| 给 `trade_backtest_run` 加 3 列 | AutoMigrate 走加列路径；`batch_id` 默认 0、`is_baseline` 默认 0，既有单跑 run 语义不变。集成用例断言"新列存在且既有列一个不少" |
| `computeSignalBacktest` 被拆开 | 行为逐字保持：同样的过滤条件、同样的对账（COUNT vs 行数）、同样的错误文案、`run.KlineCount/Start/End` 同样回填。r8 的 3 个集成用例全部原样通过（见 §5） |
| `GetBacktestMetrics` / `ListBacktestRuns` 等既有读接口 | 未改。批量产生的 run 会出现在 `engineKind=signal` 的列表里——这是有意的（每组本来就是一条完整回测），并且带 `groupLabel` 可辨识 |
| 预测驱动回测（`backtest.go`） | 一行未动 |
| 数据迁移 | 无需人工脚本：新表与新列都由 `EnsureTable`（`TradeService.EnsureTable` 已加入批次仓储）在 handler 构造时 AutoMigrate |

### 5.2 单测覆盖的行为（13 条）

基线：
1. 已发布快照 → 参数逐项映射（cap26/S400/budget13.3、trail 8 项、`0.0003 → 3bp`），且基线自身必须是**事件级**精度、必须通过实盘校验；
2. r5 未收敛的 5 类字段（`risk_equity`/`trend_gate`/`reverse_gate_min_profit_pct`/`contract_face`/`order_size`）必须在说明里逐条交代，且说明要带版本号；
3. `accountLabel` 未命中 → 报错并列出候选账户，绝不退到第一个账户。

参数 diff：
4. 组参数叠加基线而非代码缺省（未给的旋钮仍是 400/13.3/8/375.73），"只改 cap"的 diff 只有一行；
5. 显式传入与基线相同的值不算差异；
6. 组标签自动生成（单差异 / 折叠 `+N项` / 全同基线 → `same_as_baseline`）；
7. 组标签的数值只剪小数末尾 0（**这条是测试先发现的真 bug**：原实现 `TrimRight(v,"0")` 把 `40` 剪成了 `4`，已修为只对含小数点的串生效，并补了 `trimTrailingZeros` 回归用例）；
8. 并发数归一（0/负 → 3，超限 → 8）。

横向对比：
9. 事件级与频率级分成两组、事件级在前；频率级组不标可比；**故意把频率级组的净利设成全场最高（900）**，断言它不会出现在事件级组里——这正是需求大纲 §3.3 禁止的误读；跨精度行 `metricDiff=nil` 且理由含"跨精度"；批次给出混排警示；
10. 组内按净利降序、基线置顶、同精度组的 `metricDiff` 数值正确（净利差 68、变化 68%）、参数 diff 只有 cap；
11. 只产 λ 的组：`sortedBy=lambdaPerDay`、`pnlAvailable=false`、无 `metricDiff`；
12. 基线未跑完：警示 + 不给指标差异 + 参数差异仍可用；
13. 失败/未完成的组沉到组内末尾并带上失败原因。

### 5.3 集成用例覆盖的行为（4 条）

1. `trade_backtest_batch` 16 列 + run 的批次三列真的被 AutoMigrate 建出来，且 r8 的既有列一个不少；
2. 端到端：提交 2 组 + 基线 → 并发跑完 → `group_count/done_count/failed_count = 3/3/0`、`baseline_run_id` 已回填；**三组的 `signal_count` 与 `kline_count` 逐一相等（=3/60）**，这是"共享同一份输入"的验收口径；每组都有自己的逐笔；未给 label 的组被自动命名 `ceiling=40`；详情里只有一个精度组、基线置顶、精度警示非空、非基线行都有 `metricDiff` 且参数 diff 只有 cap；
3. 事件级 + 频率级混批 → 详情分成两组、事件级在前、频率级组不可比且无 `metricDiff`、警示含"不得比大小"；
4. 任一组参数非法（S=100 违反 ≥250）→ 整批拒绝，错误指出是哪一组哪个参数，且**批次表行数前后不变**（不留半残批次）。

## 6. 还剩哪些风险与待确认项

| # | 项 | 说明 | 影响 |
| --- | --- | --- | --- |
| 1 | **基线有 5 类字段是兜底的** | r5（配置面收敛）未完成，`risk_equity`/账户级 `order_size`/`reverse_gate_min_profit_pct`/`trend_gate.*`/`contract_face` DB 无列。已逐条写进 `baseline_note` 并随接口返回，但**读的人必须真的看** | 与基线的 diff 在这些维度上不代表"与生产的差异"。r5 落地后应回来把兜底改成真实读取 |
| 2 | **趋势闸基线按关闭处理** | 实例2/3 生产上是 24h/5%。要对齐生产必须在组参数里显式给 `trendGateWindowHours`/`trendGateThresholdPct` | 否则基线组会比生产更宽松（少一道逆势拦截） |
| 3 | **回测的净仓形态恒带反向门控** | r8 的 `ModeNet` 里 `EvaluateReverseGate` 是无条件调用的，没有 on/off。账户生产上 `reverse_gate=off` 时已在基线说明里给出 ⚠️ 提示 | 反向减仓类差异不可直接外推到实盘。是否给引擎加"门控开关"属 r8 的口径问题，本轮不擅自改引擎 |
| 4 | **抬高阈值组是近似** | 沿用 r8 的 `FilterByGapBp`（θ0 流上的门限筛），edge-trigger 的 in-band re-arm 动态未重推。这已由 r8 落在 `fidelity_note` 里 | 频率级组内的排序仍是近似排序，不可当作精确结论 |
| 5 | **`is_baseline` 列目前是冗余的** | 判定基线用的是 `batch.baseline_run_id`，`is_baseline` 只是让单看 run 行时也能认出来 | 无功能风险；若后续要支持"一个批次多基线"（不建议），需要重新设计 |
| 6 | **并发上限是进程内的** | 每个批次各自限 ≤8，多个批次同时跑会叠加。管理端是单进程，理论上可能被并行批次吃满 CPU | 建议成品测试观察一下同时跑 2~3 个批次时在线接口的响应；必要时改成全局信号量 |
| 7 | **新接口没配权限资源** | 本仓库没有路由级权限中间件，权限是菜单/资源驱动的，页面属 r14 | r14 建页面时用 `add-permission-resources` 一并补 `resource_new` / `role_resource_new` |
| 8 | **单批 64 组上限是拍的** | 依据是"手工对比十几组是常态，上百组就是网格搜索" | 若 r16 想复用批量执行器，应由 r16 显式提高上限并带上它的降噪协议 |

- `server/service/trade/repository/position_repository.go` 与 `strategy/engine_test.go` 未通过 `gofmt`（本轮之前就如此）。属无关文件，未动。
