### 1.2 目标复述

argus_single 现在把 12 类策略事件只写进本地 JSONL（`logs/argus_single/`，565 个文件 / 44 MB）。复盘靠每周导出 Telegram 历史消息交给 AI 读。本任务要让这 12 类事件同时落进共享 MySQL，**带实例维度**，从而让后续的事件查询接口（r9）、episode 派生（r10）、事件级回测（r8）有一个统一的数据源。

范围边界（逐条对照任务说明）：

1. 新增 `pkg/eventstore`，**不污染** leaf 包 `pkg/eventlog`（给它加 DB 依赖会造成循环）；
2. 按设计文档 §4 分表（稀疏业务事件 + balance 心跳；实测心跳 61%、dev_sample 30%、业务事件 9%）；
3. 每条带 `instance_key` 与 `config_version`；账户唯一性用 `(instance_key, account)` 或 `uid`；
4. Go 侧算 `event_hash`；
5. 保留 `equity_known`；
6. `DATETIME` 不用 `TIMESTAMP`、DSN 显式设 `loc`；
7. `ts` 精度到秒；
8. 门控 reason 结构化为 `gate_kind` + `threshold` + `actual`；
9. JSONL 双写保留至 2026-12-01。

不做：不改策略判定逻辑；不引入 ClickHouse 等新存储。

## 3. 考虑过哪些方案

### 3.1 事件怎么从 eventlog 流到 DB

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| **A. 在 eventlog 里直接写库** | `Logger.Log` 里加 gorm 调用 | 最少的代码。但 eventlog 是 leaf 包，`trade` 与 `monitor` 共同引用，加 DB 依赖必然循环，且 `backtest/` 与全部离线分析脚本对它的零依赖假设被打破 | ❌ 需求 §3.6 明令禁止 |
| **B. 改 12 个埋点，双调用** | 每处 `eventlog.Log(e)` 后面再加一句 `eventstore.Write(e)` | 不动 leaf 包。但要改 12 处交易/监控代码，漏一处就静默丢一类事件，且以后新增埋点必须记得写两遍 | ❌ 违背"不改策略判定逻辑"的精神，长期必然漂移 |
| **C. eventlog 定义 Sink 接口，eventstore 实现** | leaf 包只加一个 `Emit(Event)` 接口 + 注册函数；`Log` 落盘后旁路投递 | leaf 包只多一个接口和一个 `sync.RWMutex`，零外部依赖；12 个埋点一行不改；以后新增埋点自动进 DB | ✅ **选中** |

**选 C 的判断依据**：它是唯一同时满足"leaf 包不被污染"和"埋点零改动"的方案，而这两条恰是需求大纲和任务说明各自最硬的约束。代价只是 leaf 包多了 40 行接口代码，且这段代码不引任何新依赖（`logrus` 本来就在）。

### 3.2 用哪条数据库连接

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 复用 `common/middleware/db.Db` | 零成本。但 loc 是否正确完全取决于 properties 写没写对——设计文档 §5.3 把"DSN 没设 loc 导致整体偏移 8 小时"列为**极隐蔽错误**（数据全在、图能画、只是全错）。而且事件写入是持续的小批量写，和配置查询共用 500 连接的大池会互相排队，也没法给它单独设超时 | ❌ |
| **专属连接 + DSN 归一化** | 多一条连接（4 个连接的小池）。换来的是：loc/parseTime/charset 由代码强制而非配置；超时可控（DB 卡住时 writer 自己失败退出，不牵连交易路径的配置查询） | ✅ **选中** |

### 3.3 分几张表

任务说明写的是"稀疏业务事件 + balance 心跳"，同时给出实测占比"心跳 61%、dev_sample 30%、业务事件 9%"。设计文档 §4 写于 `dev_sample` 上线之前，只有两张业务表。

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 两张表（dev_sample 塞进 strategy_event） | 与设计文档 §4 字面一致。但 dev_sample 是**市场侧**事件，无 account/uid/side/pnl，载荷是两个 `map[string]int`；塞进去以后 strategy_event 里 77% 的行账户列全空，每个业务查询都得带 `event != 'dev_sample'` 才不被污染 | ❌ |
| **三张表**：`strategy_event` + `balance_sample` + `dev_sample` | 多一张表。但这正是设计文档分表的原始理由（把高频、列集不重叠的那一类拆出去）在 dev_sample 上线后的自然延伸，任务说明给出 30% 这个占比本身就是在提示它 | ✅ **选中** |

`episode` 表**不建**：它是 r10 的范围（"episode 持仓生命周期派生与出场归因"），且设计文档 §4.3 明确它是可从前两张表纯函数重建的派生物化表。本任务提前建一张空表只会给 r10 添乱。

### 3.4 表名与实体放哪

- **表名**：需求大纲 §4.2 与设计文档 §4 都写死了 `strategy_event` / `balance_sample`，验收也会照这个名字找。虽然共享库 `lightning_trade` 里其他域都带 `argus_` / `trade_` / `coin_` 前缀，但改名的风险（验收对不上、下游任务文档全要改）大于命名一致性的收益。**按文档原名建。**
- **实体位置**：考虑过放 `server/service/argus_event/repository/model.go`（符合 backend-development 技能的 Entity 归属约定，r9 的读侧可以直接复用）。核对后发现 `server/manager-api/go.mod:68` 已有 `replace argus_single => ../argus_single`，manager-api 完全可以 import argus_single 的包，所以放在 `pkg/eventstore` 不会挡住 r9。**按任务说明放 `pkg/eventstore`，保持本任务自包含**，并导出 `Models()` 供读侧共用表清单。
- **不嵌 `db.BaseEntity`**：这三张是 append-only 的事实表，不需要 `active` 逻辑删除、`created_by`/`updated_by`；而且 BaseEntity 的部分 tag 是 `orm:"column(id)"` 这种非法写法，靠默认蛇形名兜底，用在需要精确控制列类型（`binary(16)`、`datetime` vs `datetime(3)`）的表上不合适。

### 3.5 event_hash 怎么算

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| `UNIQUE(ts, uid, event, size, roi_pct)` | 不用算哈希。但 MySQL 里 NULL 互不相等，可空列进唯一键**等于不去重** | ❌ 设计文档 §5.1 已否 |
| MySQL 生成列拼字符串 | 表自洽。但 Go 的浮点格式化与 DECIMAL 渲染不一致，同一条事件在直写与回灌两条路径上会算出两个哈希、插出两行 | ❌ 同上 |
| Go 侧**逐字段枚举**拼串后哈希 | 可控。但要随 `eventlog.Event` 加字段同步维护，漏一个就静默插重复行；`DevCross`/`DevOver` 是 map，还得自己排序 | ❌ 维护成本会随字段增长 |
| **Go 侧哈希整行规范 JSON**：`md5(instanceKey + "\n" + eventlog.Marshal(e))` | 直写路径拿到的是 `eventlog.Event`，回灌路径拿到的是 `ParseFile` 反序列化出的**同一个结构体**，两边都过 `eventlog.Marshal` ⇒ 字节级同源；`encoding/json` 对 map 按 key 排序，`DevCross`/`DevOver` 天然确定；加字段不需要维护 | ✅ **选中** |

`instanceKey` 必须进哈希：实例1 与实例3 各有一个 `account1`，是两个不同的真实账户，同秒同内容的事件是两条真事件而不是重复行。

**已知取舍（写进代码注释与测试）**：内容完全相同且落在同一秒的两条真事件会被判成重复。逐类核对过实测数据后认为不可达——`loss_alert` 有 5 分钟冷却、`balance` 每分钟一条、`dev_sample` 带逐窗变化的 `devTicks`、`open` 的 `size` 是递增净仓、信号类事件带逐 tick 变化的 `sigLast/gapBp`。

**不进哈希的字段**：`uid`、`config_version`、`source`、`ingested_at`。理由是回灌路径拿不到（或拿到的不是同一份）`config_version`，若进哈希则同一条事件在两条路径上必然算出不同哈希，回灌立刻插出重复行。

### 3.6 门控 reason 怎么结构化

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 在埋点处新增 `GateKind`/`GateThreshold`/`GateActual` 字段 | 无解析、最准。但 r6 要回灌 44 MB 历史 JSONL，历史行里**只有 reason 串**——历史数据的 `gate_kind` 会全为空，"按 gate_kind 聚合统计今天最常被什么条件挡住"只能覆盖上线之后。那正是本任务要消灭的断层。而且要动 `pkg/trade` 的三个判定函数签名 | ❌ |
| **纯函数解析 reason 文本** | 文案漂移会失效。但直写与回灌**共用一条代码路径**，历史数据同样能结构化；解析器是纯函数，用 `pkg/trade` 里同样的 `Sprintf` 格式串写单测，埋点侧改格式会被测试直接打红 | ✅ **选中** |

为文案漂移加了兜底：解析不出具体形态时，仍按事件类型给出可聚合的 kind（`cap` / `reverse_gate` / `trend_gate`），阈值与实际值留空。这样一句文案改动最多让阈值统计失真，不会让"按 gate_kind 聚合"整段失效。

### 3.7 可空列的空值口径

`eventlog.Event` 全字段 `omitempty`，实测业务事件里**没有任何字段出现过真零值**——零值都被 omitempty 省掉了，"真零"与"缺失"在 JSON 里编码完全相同。

选定口径：**可空列一律"零值 ⇒ NULL"**，让 DB 与 JSONL 的可判定信息完全等价。否则 r6 的一致性校验会逐行报差异（DB 说 0，JSONL 说没有）。

两个例外走独立的已知性标记列：

- `equity` / `equity_known`：口径与 `pkg/eventlog/report.go:133` 一致（`e.EquityKnown || e.Equity > 0`）。老日志（2026-07-21 前）无 `equityKnown` 字段只能回退正数判断；新日志读显式标记，于是 `equity=0`（浮亏恰抵平余额）与负权益——**恰恰是最极端的回撤样本**——不会丢。
- `net_size` / `net_size_known`：直写路径 `Size` 是 Go 的 int 真值（0 就是已知空仓），恒为已知；回灌路径按天自适应判定（r6 的事）。

## 4. 方案怎么落到改动

### 4.1 新增 `server/argus_single/pkg/eventlog/sink.go`

leaf 包里只加：`Sink` 接口（`Emit(Event)`）、`RegisterSink` / `ResetSinks` / `SinkCount`、内部 `emitToSinks`。**零新依赖**（`logrus` 本来就在）。单个 sink 的 panic 被 `recover` 吃掉，只记 error——旁路投递永远不能把 JSONL 落盘或交易主流程带崩。

### 4.2 改 `pkg/eventlog/eventlog.go`

把 `Logger.Log` 的文件写入抽成 `writeLine`，`Log` 变成"补 Ts → 落 JSONL → 投递 sink"。两条路拿到的是**同一个 Ts 已补齐的 Event**，这是哈希在直写与回灌两条路径上一致的前提。JSONL 的行为一字未变。

### 4.3 新增 `server/argus_single/pkg/eventstore/`

| 文件 | 职责 |
| --- | --- |
| `model.go` | 三张表的 gorm 模型 + `Models()`；`SourceLive/SourceBackfill`；`JSONLDualWriteUntil = "2026-12-01"` |
| `hash.go` | `EventHash`（纯函数） |
| `normalize.go` | `NormalizeInstrument`、`ParseTs`、`NormalizeDSN`（均纯函数） |
| `gate.go` | `ParseGate` + 7 个 `gate_kind` 常量（纯函数） |
| `convert.go` | `Envelope` → `Rows`（纯函数），`EquityKnown` |
| `store.go` | `Store`：专属连接、`EnsureTable`、非阻塞 `Emit`、批量 flush、`Stats`、`Close` |
| `runtime.go` | 包级默认 store：`Setup` / `Default` / `SetConfigVersion` / `SetAccounts` / `Shutdown` / `IsDisabled` |

写入路径的形状：

```
交易 goroutine                      writer goroutine
  eventlog.Log(e)
    ├─ 写 JSONL（真源）
    └─ Store.Emit(e)
         ├─ 原子读 state → 取 config_version 与 uid
         └─ 非阻塞入队 ──────────►  攒批（200 条 / 2 秒）
                                     ├─ Convert（算哈希、归一化、结构化门控）
                                     └─ 按表 CreateInBatches
                                          + ON DUPLICATE KEY UPDATE id=id
```

几个刻意的决定：

- **uid 与 config_version 在 Emit 时刻取好**，不留到 writer goroutine。否则一次配置热更新会把队列里积压的旧事件标成新版本号，归因口径立刻失真。
- **队列满直接丢并计数**（每 200 条打一次告警）。这是"绝不阻断交易路径"的落点；丢掉的事件仍在 JSONL 真源里，可由 r6 回灌补齐。
- **写库失败不重试**，只记 error 并计入 `Failed`。重试会把队列堵死，把 DB 故障传导成交易延迟。
- `SkipDefaultTransaction: true`：批量 INSERT 不需要外层事务，幂等哈希已经保证可重放。（这条不是可选优化——验证时发现 gorm 的默认事务会在 DryRun 之前先真的 `BeginTx`。）

### 4.4 改 `initialization/initialization.go`

- 在 `eventlog.Init` 之后、任何交易/监控启动之前 `eventstore.Setup`，实例键取 `runtimeManager.InstanceID()`、DSN 取 `sqlconn`；
- **失败不算启动失败**：`sqlconn` 为空打一行 info（完全退化成今天的行为），其他错误打 error 后继续。DB 问题绝不能让实盘进程起不来；
- 成功后写入初始 `config_version` 与账户映射；
- 把 reload observer 从 `heartbeat.RecordReload` 换成一个同时通知 heartbeat 与 eventstore 的闭包（只在 `err == nil && version > 0` 时更新）；
- 新增 `accountIdentities(*trade.TradingSystemConfig) []eventstore.Identity`，避免 eventstore 反向依赖 `pkg/trade`。

### 4.5 改 `routers/routers.go`

在既有的 SIGTERM 优雅关闭里、`runtimehealth.StopDefaultReporter()` 之后加 `eventstore.Shutdown(3 * time.Second)`——和旁边"停账户监控并 flush trail 状态"同一个理由：正常部署重启不该丢掉队列里积压的事件。超时即放弃，绝不为此拖住进程退出。

### 4.6 表结构（AutoMigrate 实际产出，已在 MySQL 8.0.28 上核对）

三张表都带 `event_hash binary(16)` 唯一键、`ts datetime`（秒精度）、`instance_key varchar(64)`、`config_version bigint unsigned`、`source tinyint`、`ingested_at datetime(3)`。

- `strategy_event`：10 类业务事件。业务列 + `gate_kind`/`gate_threshold`/`gate_actual` + `trend_mom_pct` + `ext json`（预留，新字段不改表）。索引 `(instance_key, ts)`、`(instance_key, uid, ts)`、`(instance_key, event, ts)`、`(gate_kind, ts)`、`(ts)`。
- `balance_sample`：`balance` 非空 + `equity`/`upl`/`equity_known` + `net_size`/`net_size_known`。索引 `(instance_key, uid, ts)`、`(ts)`。
- `dev_sample`：`dev_ticks` + `dev_max_bp`/`dev_mean_bp` + `dev_cross_json`/`dev_over_json`。索引 `(instance_key, instrument, ts)`、`(ts)`。

### 5.2 集成校验发现并修掉的真问题

第一次跑集成用例时 `equity` 读回是 NULL 而 `equity_known=1`——`Convert` 走的是"零值 ⇒ NULL"的统一口径，把"已知的零权益"这个**最极端的回撤样本**吃掉了，写出了自相矛盾的行。改成 `equity` 已知时原值入库（含 0 与负值），`upl` 同理，并把单测断言从"只查 known 标记"补强到"查值本身"。这正是设计文档 §5.2 反复强调的那个坑，单测口径太松没能拦住，靠真库回读才暴露。

第二处：gorm 把 Go 的 `int` 一律映射成 `bigint`（`type:int` 标签不生效，要给 `size:32`），已修正为 `int`。

### 5.3 待测试阶段验证（本轮无法覆盖）

- 三实例并发写同一张表的隔离性（需要至少两套真实实例配置 + 共享库）；
- 配置热更新后新事件的 `config_version` 递增（需要跑通 r5 的发布链路）；
- 长时间运行下的容量与索引表现；
- `fixed_close` / `manual_close` 两类事件（设计文档 §2.1：历史 30 天从未触发过，无金标准数据可验），本轮只有构造数据的单测覆盖。

## 6. 还剩什么风险与待确认项

| # | 风险 / 待确认 | 说明与建议 |
| --- | --- | --- |
| R1 | 同秒同内容事件被判重 | 逐类核对后认为不可达（见 §3.5），但这是设计上的取舍而非证明。建议 r6 回灌时把"JSONL 行数 vs DB 行数"的差额按事件类型分组打出来，一旦某类持续有差额就是这里被触发了 |
| R2 | 门控 reason 文案漂移 | 已用同样的 `Sprintf` 格式串写了单测，改格式会被打红；文案改了但没跑测试的情况下会退化成"只有 kind 没有阈值"，不会整段失效 |
| R3 | 队列满丢事件 | 8192 的队列 + 2 秒 flush，按实测 9.6 万条/天（约 1.1 条/秒）有几个数量级的余量。真被打满说明 DB 长时间不可用，`Stats().Dropped` 会持续增长——建议 r9 把这个计数暴露到健康检查里 |
| R4 | `net_size_known` 直写恒为 true | 沿用设计文档 §5.2 的决定。但 `accountNetSize` 在持仓快照尚未建立时也返回 0，此时的"已知空仓"其实是"还没查过"。影响窗口只有进程启动后的第一个轮询周期（≤5s），且 balance 事件本身每分钟才一条。留作 r10 派生 episode 时的注意事项 |
| R5 | `episode` 表没建 | 属 r10 范围。若 r10 决定改用别的切分口径，本任务的两张事实表都不需要改 |
| R6 | 表名无 `argus_` 前缀 | 按需求大纲与设计文档原名建（见 §3.4）。若后续决定统一前缀，需同步改 r6/r9/r10 三个下游任务的文档 |
| R7 | 实例与机器的映射 | 需求大纲 §9.1 的待确认项，属 r1 范围；本任务只消费 `argus.instance.id`，映射关系变化不影响本任务的代码 |
