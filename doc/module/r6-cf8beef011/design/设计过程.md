### 1.2 目标复述

r4 让**上线之后**的事件进了库，但 2026-06-28 ~ 2026-08-21 这段历史仍然只在 JSONL 里。

2. **对账**：在 3 个月双写期（至 2026-12-01）里，每天能回答"JSONL 有的，库里是不是都有"，
   并且发现缺口后能用同一个工具补上。

范围边界（逐条对照任务说明）：

- 照 `cmd/argus-config-import` 先例新增 `cmd/argus-event-import`；

  事件无 uid 需账户名映射；
- 历史数据**按来源目录归属实例**；
- 去重靠 r4 的 `event_hash`；
- 产出每日一致性巡检报告；
- **不修改历史 JSONL 原文件。**

## 2. 勘察到的现状事实

全部现场核对，附路径与实测数字。

### 2.1 数据资产的真实规模

任务说明写的「565 文件 / 44MB」是整个 `logs/argus_single/` 目录的规模，其中绝大部分是
Telegram 导出（`ChatExport_*`：html + css + images）与 `dc_files`。真正的事件 JSONL：

| 项 | 实测 |
| --- | --- |
| `events-<date>.jsonl` 文件数 | **62** |

### 2.4 r4 已经建好、本任务直接复用的东西

### 2.5 r4 留给本任务的两个缺口

1. `Convert` 对 `source=backfill` 的 balance 行一律写 `net_size=0 / net_size_known=0`。
   这是自相矛盾的行（值 0 却标未知）。r4 的设计过程 §3.7 明确写了"回灌路径按天自适应判定
   （r6 的事）"，所以这是有意留的口子，不是 bug。
2. `eventstore.Open()` 里 gorm 连接的建立是私有的，`Store` 的 `db` 字段不导出。回灌工具
   需要一条同口径的连接但不需要 writer goroutine。

## 3. 考虑过哪些方案

### 3.1 回灌代码放哪

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| A. 直接写进 `pkg/eventstore` | 与 `Convert`/`EventHash` 同包 | 最省事，共用私有函数。但 `pkg/eventstore` 被实盘进程链进去，塞进文件扫描、报告渲染这些离线代码会让这个包的职责糊掉——它的包头写着三条交易路径的硬不变量，不该再管 Markdown 渲染 | ❌ |
| B. 独立顶层包 `pkg/eventbackfill` | 与 eventstore 平级 | 平级会给人"两套写入路径"的错觉，实际它必须严格从属于 eventstore 的口径 | ❌ |
| **C. 子包 `pkg/eventstore/backfill`** | 反向依赖 eventstore | 目录层级即表达了"我是 eventstore 的离线入口，口径以它为准"；实盘二进制不 import 它就不会链进去 | ✅ **选中** |
| D. `service/argus_event/...` | 走 backend-development 的分层 | 那是 r9（读侧 API）的域。回灌是离线批处理工具，不是 HTTP 业务域，硬套 Handler/Service/Repository 三层只会多两层空壳 | ❌ |

### 3.2 CLI 放哪、长什么样

任务说明写的是"照 `cmd/argus-config-import` 先例"，而那个 cmd 在 `server/manager-api/cmd/`。
核对过 `server/manager-api/go.mod:68` 有 `replace argus_single => ../argus_single`，manager-api
可以直接 import `argus_single/pkg/eventstore/backfill`。**放 `server/manager-api/cmd/argus-event-import`**，
和先例同目录，也顺带能用 `service/argus_config` 校验实例注册表。

| 参数形态 | 取舍 | 结论 |
| --- | --- | --- |
| 一次跑全部目录，映射写死在代码里 | 最省事。但"哪个目录属于哪个实例"是**人的判断**，写死在代码里以后新增快照目录就要改代码重新编译 | ❌ |
| `--manifest manifest.json` | 表达力最强。但要先造一个文件才能跑，第一次用的人会卡在"manifest 长什么样" | ❌ |
| **`--instance` + `--config` + 可重复的 `--source`** | 一次跑一个实例，与 config-import 的"一次一个实例"完全一致；目录归属在命令行里一眼可见 | ✅ **选中** |

`--source` 可重复是关键：实例1 的七个快照目录必须在**同一次**运行里一起喂进去，否则跨目录
的重复行会分成七次插入，虽然 `event_hash` 仍能兜住，但报告里就看不到"重复了多少"这个数。

### 3.3 回灌与对账是两个工具还是一个

设计文档 §7.1 已经给了答案（"回灌工具与它是同一份代码，只是入口不同"），本轮复核后同意：
两者的前半段完全相同（扫 JSONL → 转行 → 算哈希），只有后半段分叉（写 vs 比对）。
拆成两个二进制必然出现"回灌改了转换口径、对账没跟上"的漂移，而这种漂移的表现是
**对账每天报缺口但补不上**，极难定位。

落成三个模式：

| 模式 | 命令 | 行为 |
| --- | --- | --- |
| dry run（默认） | 不加 flag | 扫描 + 出报告，不连库 |
| 回灌 | `--apply` | 建表 + 写入 + 写完立刻对账 |
| 巡检 | `--audit` | 只比对，一行不写 |

`--apply` 之后自动跑一次对账，是刻意的：回灌完立刻用独立路径（DB 查询）验证写进去的东西，
而不是拿写入侧自己的计数当证据。

### 3.4 `net_size_known` 的判定放哪

设计文档 §5.2 给的规则是"某 uid 在某天的 balance 事件里出现过至少一条带 `size` 的
⇒ 该字段那天已上线，同日缺失即已知空仓；一条都没有 ⇒ 全天未知"。

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 硬编码 2026-07-21 上线日 | 一行代码。但设计文档明确写了"不硬编码这个日期"——三个实例的部署时点不同，某个实例晚几天升级就会被判错，而且判错的方向是"把未知当成已知的 0"，会造出假的空仓样本 | ❌ |
| 放进 `eventstore.Convert` | 口径集中。但 `Convert` 是逐条纯函数，看不到"当天这个账户还有没有别的 balance"，要传这个上下文就得给纯函数加一个只有回灌用得上的参数 | ❌ |
| **在 `backfill` 里按天成批后覆盖 Convert 的保守默认值** | 判定发生在唯一拥有"整天上下文"的地方；`Convert` 保持纯函数不变；覆盖方向是"从保守的未知放宽到已知"，即使 backfill 忘了调用，结果也只是偏保守而不是造假 | ✅ **选中** |

判定单位为什么是"天 × 账户"而不是"天"：实测 2026-07-21 当天账户A 有带 `size` 的样本而
账户B 一条都没有。按天判会把账户B 全天的缺失也当成"已知空仓"。单测 `TestBuildNetSizeKnownIsAdaptivePerDayPerAccount`
钉的就是这一点。

### 3.5 未知 account 标签怎么处理

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 从标签里解析数字（`账户A-9564268` 里有 uid） | 实例2 的标签恰好含 uid。但实例1 的 `账户A-<QQ号>@qq.com` 里那串数字是 QQ 号、不是 uid，真 uid 是另一串完全不同的数字——**解析出来的会是个看似合理的错值**。这是最坏的一类 bug：不报错、数据全在、归因全错 | ❌ |
| 留空 uid，回退 `(instance_key, account_label)` | 不会出错值。但下游 r10 的 episode 派生要按 uid 归集，留空等于把问题推给下游 | ❌ |
| **拒绝导入并报错，列出标签** | 与设计文档 §9 一致。代价是新增账户时要先补 properties，但这本来就是必须做的事 | ✅ **选中** |

`dev_sample` 是市场侧事件、`account` 本就为空，不受此限——单测
`TestBuildAcceptsAccountlessDevSample` 钉住。

### 3.6 一致性比对比什么

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 只比行数 | 一条 SQL 就够。但行数相等不代表内容相同：丢了一条 `open`、多插一条重复 `balance`，行数照样对上 | ❌ |
| 逐行拉出业务列做字段级 diff | 最彻底。但 16 万行 × 30 列的比对既慢又会被 DECIMAL 渲染差异刷屏，而这些差异恰恰不是问题（哈希已经覆盖了内容） | ❌ |
| **按 `event_hash` 做集合差** | `event_hash` 是整行规范 JSON 的哈希，哈希对上就等于内容逐字对上。只拉两列（hash + source），16 万行秒级 | ✅ **选中** |

比对口径按 `ts` 的自然日过滤而不是 `ingested_at`：JSONL 按事件时刻分文件，只有同一个口径
才能逐行对上。

**补了一个 §7.1 没提的检查**：逐日比对只能覆盖"JSONL 有的天"，覆盖不到"库里有整天数据、
JSONL 整天都没有"这种情况——双写期里这意味着 JSONL 落盘失败，而它会被静默读成"这几天没交易"。
加了 `FindOrphanDays`，并计入退出码。

### 3.7 每日报告长什么样

考虑过输出 JSON 给别的程序消费，否决了：这份报告的读者是人（每天早上扫一眼），
JSON 还得再配一个渲染器。选 Markdown，并且**保证同一批数据两次渲染逐字一致**
（表格行序全部显式排序），这样两天的报告可以直接 `diff`。单测
`TestReportRenderCoversEverySection` 钉住确定性。

对机器消费的需求用**退出码**满足：一致 = 0，发现缺失行或缺整天 = 2。cron 直接用退出码告警，
不用解析报告。

### 3.8 要不要写一个 shell 包装脚本

`server/argus_single/script/` 下有 `deploy*.sh` / `control.sh` 这一套。考虑过加一个
`event_audit.sh` 把"目录 → 实例"的映射写进去。否决：那个目录里的脚本全是**进程生命周期**
脚本，会被打包同步到运行机；回灌是一次性的、跑在有全部历史快照的地方，两者的部署位置都不同。
映射关系写进操作手册（`doc/module/r6-cf8beef011/回灌与双写巡检操作手册.md`），
每日巡检用 cron 直接调二进制 + 退出码告警。

## 4. 方案怎么落到改动

### 4.1 新增 `server/argus_single/pkg/eventstore/backfill/`

| 文件 | 职责 |
| --- | --- |
| `scan.go` | `ListEventFiles`（只认 `events-<date>.jsonl`）、`ScanFile`（逐行解析 + 行级统计） |
| `matrix.go` | 设计文档 §6.6 的字段适用性矩阵 + `missingRequired` |
| `build.go` | `Job` / `Build`：多目录扫描、uid 映射、按天分组、`Convert`、哈希去重、`net_size_known` 自适应、覆盖率统计 |
| `import.go` | `EnsureTables`、`WriteDay`（`ON DUPLICATE KEY UPDATE id=id`） |
| `audit.go` | `AuditDay`（按 `event_hash` 集合差）、`FindOrphanDays` |
| `report.go` | `Report.Render` / `Write`：六节 Markdown |

`ScanFile` 为什么不直接用 `eventlog.ParseFile`：后者静默跳过坏行。回灌报告必须说清
"这个文件有几行、解析出几条、丢了几行"，静默跳过等于把缺口藏起来。解析用的是同一个
`json.Unmarshal` 到同一个 `eventlog.Event`，所以后续 `eventlog.Marshal` 出来的规范行
与直写路径**字节级同源**，哈希必然一致。

事件按**自身 `ts` 的日期**归日，不按文件名——按天的判定（`net_size_known`）必须落在真实
日期上；文件名日期与 `ts` 日期不一致的条数单独计入 `FileStat.OffDate` 并在报告里报出来。

### 4.2 改 `server/argus_single/pkg/eventstore/store.go`

把 `Open()` 里建 gorm 连接的那段抽成导出的 `OpenDB(rawDSN)`，`Open` 改为调用它。
回灌工具用同一条 DSN 口径（强制 `loc=Local` / `parseTime` / `utf8mb4` / 超时）但不需要
writer goroutine。`Open` 的行为一字未变。

### 4.3 改 `server/service/argus_config/importer.go`

新增 `LoadInstanceAccounts(propertiesPath)`：只读 `argus.instance.id` 与
`trade.accountN.name/uid/variant`，**不碰 `session.json`、不解析任何凭证字段**。
复用已有的 `validateInstancePropertiesFile` 与 `readProperties`。

放在配置域而不是 backfill 包里，是为了让 `pkg/eventstore/backfill` 不反向依赖 `service`
模块——和 r4 让 `initialization` 构建 `[]eventstore.Identity` 再传进去是同一个模式。

### 4.4 新增 `server/manager-api/cmd/argus-event-import/main.go`

flag：`--source`（可重复）、`--config`、`--instance`、`--dsn`、`--since`/`--until`、
`--apply`、`--audit`、`--report`、`--batch-size`。

几个刻意的决定：

- **默认 dry run**，与 config-import 一致；
- `--instance` 与 properties 的 `argus.instance.id` 不一致时**只告警不拦**：历史目录可能
  来自改名之前的部署，归属由人按目录判断，工具不替他决定；
- 实例注册表校验用 `Migrator().HasTable` 先探再查，避免 gorm 打一行红色的
  `Table doesn't exist` 错误日志；注册表**不存在或为空时放行**，与
  `argus_config.assertInstanceUsable` 的自举口径一致；
- `--dsn` 缺省时才 `vipper.Init()` 读 `sqlconn`——给了显式 DSN 就不需要 configs 目录，
  一次性回灌可以从任意目录跑。

### 4.5 顺带修掉的一个数据安全隐患

r4 的 `pkg/eventstore/store_integration_test.go` 用**真实部署的实例键** `argus-single-roc`
作测试实例，并在用例开头 `DELETE FROM strategy_event/balance_sample/dev_sample
WHERE instance_key = 'argus-single-roc'`。

本轮实跑时被真实触发了：全量回灌完 166,662 行之后跑一遍 r4 的集成用例，roc 的
strategy_event 从 7348 掉到 5、balance_sample 从 144,989 掉到 1。在一次性 schema 上
只是要重跑一次；如果哪天有人把 `EVENTSTORE_TEST_DSN` 指向共享库，这就是一条**直接
删掉线上实例全部历史事件**的路径，而且删得静悄悄。

改动很小：把测试实例键换成 `it-eventstore-main` / `it-eventstore-alt` 两个常量，并把
那条按 `account_label` 的全局 DELETE 也收窄到这两个键。本包的新增集成用例从一开始
就用 `it-backfill-*` 前缀，同一个理由。测试断言逻辑一行未改。

## 6. 还剩什么风险与待确认项

| # | 风险 / 待确认 | 说明与建议 |
| --- | --- | --- |
| **R1** | **8/18–8/21 兜底止损次数对不上** | 任务说明与需求大纲 §6.1.2 写"6 次兜底止损"，原始 JSONL 实测是实例1 **5 次** + 实例2 **2 次** = 7 次，逐条核对过 ts/账户/ROI，没有重复行也没有被去重掉的。**"6" 在原始数据里找不到对应口径**——可能是当时按单账户或按某个时间子区间数的。建议验收时以本轮报告的实测数为准，或由需求方确认 6 的口径 |
| R2 | 同秒同内容事件被判重 | 沿用 r4 的取舍。全量 62 个文件回灌后，去重条数与"重叠快照的行数差"完全能对上（例如 7/10 的 2212 = 被截断快照的全部行数），没有出现无法解释的额外去重。但这是观测证据不是证明 |
| R3 | `--dsn` 会进 shell history 与进程列表 | 生产回灌请从 `server/manager-api` 跑、用 `configs/application.properties` 的 `sqlconn`，不要在命令行贴 DSN。已写进操作手册 §7 |
| R4 | 巡检跑"今天"会假报缺失 | 今天的 JSONL 还在追加、库里也还在写，两边取快照的时刻不同必然有差。操作手册 §4 要求只跑昨天 |
| R5 | `open` 缺 `size` 的 30 条异常 | 全量里 `open`/`size` 异常 28 条（roc）+ 2 条（ives）。`size` 是开仓后的结果净仓，为 0 说明这一单把净仓打平了（reduce-to-zero）。按 §6.6 矩阵它算"应有而缺"，但很可能是正常语义。**建议 r10 派生 episode 时确认这一点**，如果确认正常就把 `open` 的 `size` 从必需集里去掉 |
| R6 | `config_version=0` 的历史行 | 回灌行没有可考的配置版本。下游若按 `config_version` 分组做归因，历史段会全落进 0 这一组。r9/r10 需要知道这个口径 |
| R7 | 巡检覆盖不到"两边都没有"的事件 | 如果某条事件既没落 JSONL 也没落 DB（例如进程在写 JSONL 之前就崩了），任何对账都发现不了。这是 JSONL 作为真源这个前提本身的边界，不是本工具能解决的 |
| R8 | `application.properties`（`argus-single-1`）没有历史数据 | 该实例的 uid 与实例1 不同但账户标签形态相似。操作手册 §2 已明确警告不要拿它回灌 roc 的目录 |
