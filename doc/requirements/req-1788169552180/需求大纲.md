## 1. 需求背景与目标

`server/argus_single` 是 DeepCoin BTC-USDT-SWAP 上的盘口信号跟随累加器（125x 杠杆，均值回归机理，靠扛住浮亏等价格回来）。目前它已在三台部署单元上运行 champion/challenger 实验体系，但**运维与研究完全依赖人工**：

- 复盘靠每周导出 Telegram 历史消息交给 AI 读，历史数据散落在 `logs/argus_single/`（565 个文件 / 44 MB JSONL）；
- 参数散落在三份 properties 文件里，管理端已有的配置页只覆盖一小部分字段，且改动无法确认是否真的生效；
- 回测能力只有一堆离线 Python 脚本，无法在管理端提交与对比；
- 8/21 那次剧烈上涨中策略表现很差，事后只能靠人读日志定位原因。

**目标**：把 argus_single 的行情、触发信号、持仓生命周期全部落库，在既有管理端（`client/manager` + `server/manager-api`）上重建四类能力——历史行情与触发点可视化、信号复盘、参数回测与自动寻优、参数按实例热更新——让策略决策从"人读日志"变成"数据驱动"。

## 2. 范围与不做的事

### 2.1 范围

| 能力 | 内容 |
|---|---|
| 历史行情 | DeepCoin 与币安双源，1m/5m/1h/1d 四周期落库；触发瞬间 ±1min 秒级切片 |
| 触发信号 | 12 类策略事件落 MySQL，含成功开仓与被拦截（反向门控 / 上限跳过 / 趋势闸），拦截原因结构化 |
| 持仓归集 | episode 生命周期派生 + 六种出场归因 + 决策时刻归集口径 |
| 回测 | 事件驱动的盘口信号回测引擎，精度分层；参数组批量对比；后台自动寻优 |
| 参数热更 | 配置面完整收敛到 DB，按实例分域发布，生效状态以心跳回报为准 |
| 前端 | 总览、实例对比、行情触发点、信号复盘、回测、寻优、参数共 7 个页面 |
| 研究 | 行情状态依赖性 Phase 0 复现（判定"自动按行情路由参数"这个方向是否成立） |

### 2.2 明确不做

- **不做实时行情推送**（需求明确只要历史行情）。
- **不落全时段秒级 K 线**：单币双源按行存 1s 约 6300 万行/年 ≈ 18 GB/年，已否决。
- **不做管理端的 start / stop / restart 远程控制**，不引入控制 agent，不改进程启停方式（保持 SSH + `script/control.sh`）。进程启停属于发版与故障处置；停进程后持仓仍挂在交易所但移动止盈、兜底止损、平仓监控全部失效，比不停更危险。真正的紧急刹车是 `order_size = 0`（暂停新开仓、继续看管已有持仓），走参数热更新链路。
- **不把 cookie / token / sentry 放进参数编辑表单**：它们是程序登录后自己刷新的运行时状态，由 `InstallSessionWriteBack()` 自动回写，不属于配置版本快照（`argus_runtime_session` 与 `argus_account` 分表正是这个原因）。实测 cookie 约 950 字符，手工编辑无实际意义且扩大泄露面。只做只读巡检。
- **不实现自动参数路由器**（原因见 §3.4），不引入外生数据源（宏观日历 / 新闻 / LLM 判断）。
- **不改任何策略判定逻辑**。回测与实盘共享参数定义，但走独立执行路径，不触碰实盘进程。
- **自动寻优不输出"最优参数"**，不自动修改线上参数，不做贝叶斯优化 / 遗传算法（搜索空间只有几十格，网格足够且可解释性更重要）。
- **不引入新的时序数据库**（ClickHouse 等），量级不需要。
- 既有模块（真实交易、模拟盘分析、平台/币种管理、用户/角色管理）不在本次重构范围。

## 3. 关键约束

### 3.1 容量结论（BTCUSDT 单币，DC + 币安双源）

| 方案 | 行数/年 | 磁盘/年 | 结论 |
|---|---|---|---|
| 全时段 1s | 6,307 万 | ≈ 18 GB | ❌ 否决 |
| 1m | 105 万 | ≈ 315 MB | ✅ 采用 |
| 5m + 1h + 1d | 22.8 万 | ≈ 70 MB | ✅ 采用 |
| 触发瞬间 ±1min 秒级切片（一条信号一行 + JSON 序列） | ≈ 7 万 | ≈ 0.44 GB | ✅ 采用，保留 90 天滚动 |
| dev_sample 采样从 1min 提到 10s | 8,640 条/天 | < 100 MB | ✅ 采用 |

秒级不按行存——按行存 ±3min 窗口 worst case 达 5,256 万行/年，与全量秒级相当（信号成簇，窗口互相覆盖）。

### 3.2 配置面收敛的三类缺口（properties 共 63 个键，已逐项核对）

**A. 必须留在 properties 的 4 个**（连库前置，鸡生蛋）：`sqlconn`、`redis.addr`、`redis.password`、`argus.instance.id`。

**B. DB 有列但值到不了运行时的 13 项**：
- `position.monitor.interval_seconds` / `profit_threshold` / `loss_threshold` → `argus_config` 有列，但 `RuntimeConfig` 结构体没有对应字段，`pkg/monitor/account_monitor.go:106/110/114` 仍读 vipper；
- `position.monitor.trail.*` 共 8 个 → `argus_account_risk.trailing_stop_tiers_json`，`importer.go:236` 已写入，`runtimeAccount()` 不读；
- `trade.accountN.trade_logic` / `variant` / `trade_direction` → `extra_risk_json` 有值但 `runtimeAccount` 不读；`argus_account_risk.stop_loss_mode` 同类。

> ⚠️ **`trade_logic` 是功能性故障，不只是"字段没读"**：`runtimeAccount` 不设 `TradeLogic` → 空字符串 → 被 `config.go:196 normalizeTradeLogic` 归一化成 `spread`（老价差逻辑）→ `manager.go:286` 的 `IsSignalLogic()` 分支不会走。**切到 DB 配置驱动后整套盘口信号策略会静默失效且不报任何错。**
> `variant` 为空会让所有事件的 variant 字段为空，champion/challenger 归因彻底失灵。

**C. DB 完全没有列的 9 个**：`trade.accountN.order_size`（账户级，现只有全局 `argus_config.default_order_size`）、`risk_equity`、`reverse_gate_min_profit_pct`（账户级 + 全局）、`position.risk.contract_face`、`trade.signal.delay_seconds`、`monitor.spread.max_price_age_ms`、`trade.trend_gate.window_hours`、`trade.trend_gate.threshold_pct`、`trade.accountN.trend_gate_threshold_pct`（`trend_gate.go:58` 存在但 properties 未配）。

`argus.build.version` 与 `argus.heartbeat.*` 可进 DB 但价值低，本次不收敛。

### 3.3 回测精度分层（必须显式标注，不得混排比较）

| 改动的参数 | 回测方式 | 精度等级 |
|---|---|---|
| 仓位上限 / 风险预算 / 止损 / 移动止盈分档 / 反向门控 / 趋势闸 | 信号序列不变，直接回放 `strategy_event` 真实触发点 | **事件级**（触发点精确到秒） |
| `signal_threshold` | 必须重新推导信号；历史事件被生产阈值结构性截断（实测 min = 5.01bp），改用 `dev_sample.DevCross` 推 λ(θ) | **频率级**（只能推频率，推不出每次时刻） |

**为什么不从 1m K 线推信号**：① K 线里没有 mark price，而信号源是 DeepCoin `last` 相对 `mark` 的偏离，该信息在 K 线中不存在；② 实测（8.18–8.21，4 天，去重后）**28.7% 的信号分钟内触发 ≥2 次，承载 48.6% 的全部触发，单分钟最多 5 次，相邻触发间隔中位 61 秒、48.7% 小于 60 秒**——按 1m 推导会丢掉约一半触发。

**1m K 线只用于持仓期间的路径回放**。实盘判定频率是 `position.monitor.interval_seconds = 5` 秒，回测是 60 秒，因此 `peakPct` 会偏高；同一根内可能同时触及止盈与止损时**按不利方向结算（先止损）**，宁可低估。实测持仓中位约 2 小时（≈120 根 1m）、最长 24.9 小时，出场时点 ±1 分钟对最终 ROI 影响很小。

### 3.4 已被实证否定的方向（不得重跑）

来自 `docs/argus_single/2026-07-27-波动率状态自适应研究设计.md` §1：

| 已否定 | 实测证据 |
|---|---|
| 跳过高波动期加仓（burst throttle） | T1 **+61U** vs 基线 **+168.7U**（5.5 周库） |
| 紧止损 / 提前割肉 | −150% 会杀死全部 22 个反转获利 episode；−350% 杀死 0 个 |
| 时间衰减激活 / 年龄退出 | D1/D2/D3 全部更差（−8~−29%，回撤最高翻倍），持仓时长不变 |

**共同母题：所有"聪明地提前退出 / 优化入场"的尝试都在削减系统赖以为生的部分。** 因此**任何"高波动 → 降低暴露"的规则都是 burst throttle 的变体，直接排除**。

Phase 0 已执行（2072 信号 / 38 天 / 16 路径 × 4 格）：H1 被**反方向**否定——高波动期打满 cap 的时长占比更低（rv 口径 7.8% vs 12.7%，88–94% 同号），受 cap 约束更紧的是低波动期；主口径 ρ（滚动信号密度）关键指标不显著，H0 成立，未进 Phase 1。

**仍开放的**：λ（兜底频率）的状态依赖、gate 与 trail 档位的状态依赖。已上线的 `trend_gate`（24h 窗口动量 ±5%）是被接受的 regime 门控，区别在于它是**方向性**门控（只拦逆势加仓），不是波动率性降暴露。

### 3.5 统计口径护栏

- **决策时刻归集**：按状态/条件分层的收益归因必须把每笔 PnL 平摊回其各张仓位**建仓时**所处的状态。设计文档 §10.3 记录了反例：按平仓时刻归集得出"高波动期收益是低波动期 8–11 倍、16/16 路径同号"的极强信号，**实为伪影**；改决策归集后差异塌缩到 0.001–0.065，信号基本消失。
- **rv 是比信号密度更强的状态代理**：两口径一致率仅 57.6%（W=1h）/ 70.9%（W=4h），且在关键指标上给出不同判定。
- **单路径混沌 ±70U，点估计不可信**：现行 champion `net(15,300)` 的符号一致率只有 **0.56（等于掷硬币）**。决策只依据「符号一致率 ≥ 80% 且中位数达标」。
- **OOS 纪律**：参数锁定后用锁定之后新进的信号流每周复算，不重新调参。扫描窗口内的收益必然高估（in-sample）。
- **规模不变性破缺**：cap 的摊平动态依赖**绝对张数**，小额账户按公式实例化后动态不同，challenger 只能验证单一效应的方向性。

### 3.6 其他不变量

- **写库失败只告警、绝不阻断交易路径**。DB 挂掉或慢查询不得让下单或平仓卡住。
- **`pkg/eventlog` 是 leaf 包**（被 trade 与 monitor 共同引用），引入 DB 驱动必须放独立包 `pkg/eventstore`，加依赖会造成循环。
- **JSONL 不立刻废弃**，双写保留 3 个月（至 2026-12-01），它是回测平台和全部历史分析脚本的输入格式。
- **`risk_equity` 只能来自配置**，禁止任何"运行时余额 → cap"的自动路径（制度性护栏）。
- 前端图表库采用 **lightweight-charts**（现有依赖只有 `@antv/g2 5.1.15-beta.4`，无蜡烛图组件）。
- 表结构与页面按**多币种**设计，当前只接入 BTCUSDT。

### 4.2 真实缺口

1. `trade_kline` **没有平台维度**（`service/trade/repository/model.go:66` 唯一键只有 `symbol+interval+open_time`）→ 物理上存不下双源。
2. **事件只落 JSONL 没进库**：全仓库无 `strategy_event` / `balance_sample` / `episode` 任何一张表。
3. **现有回测是 AI 预测驱动，不是盘口信号驱动**：`trade_backtest_run` 字段为 `prediction_interval` / `prediction_variant` / `confidence` / `predicted_move_pct`，`service/trade/strategy/engine.go` 也是喂预测。
4. **配置系统按单实例写死**：`argus_config_version.published_slot` 的唯一索引 `idx_argus_single_published` 只允许全表一个 published 版本；Redis `argus:config:snapshot` / `argus:config:version` 是全局单键；`ConfigVersionMessage` 无 `instanceId`，`runtime.go:161 handleVersionMessage` 不做实例过滤。
5. **配置面 22 项未打通**（详见 §3.2），其中 `trade_logic` 是功能性故障。
6. **跨机器运行控制不可达**：`service/argus_runtime` 的 `Control()` 是 `exec.CommandContext(control.sh)` 本地脚本，而 `deploy_2.sh` 指向另一台服务器；只有 `Reload()` 走 Redis 能跨机器。

## 6. 验收标准

### 6.1 需求级验收

1. **告别 TG 导出**：复盘页能完整还原一条真实 Telegram 信号消息的全部信息（含门控跳过行的 ROI 与阈值），且可按 `gate_kind` 聚合统计"今天最常被什么条件挡住"。
2. **数据完整性**：8/18–8/21 区间的 613 次信号触发时刻可完整查出，20 笔完整持仓（账户A 6 笔 / 账户B 14 笔）与 6 次兜底止损可完整还原，实例归属正确。
3. **参数真生效**：以 DB 为唯一来源启动（properties 只留 4 个基础设施键），三实例的 `RiskParamsView` 打印值与各自 properties 原值逐项一致；`manager.go:286` 的 `IsSignalLogic()` 为 true 且能看到盘口信号开仓。
4. **实例隔离**：给某个实例发布参数后，只有该实例的心跳 version 变化，其余实例参数与版本不变。
5. **生效可确认**：改参数发布后页面 15 秒内显示"已生效 vN"；发布成功但程序未确认时明确显示仍在用旧版本；发布瞬间断开 Redis 订阅，30 秒内参数仍能自行补上。
6. **回测可信**：事件级回测的触发次数与该区间 `strategy_event` 的真实触发数完全一致（零丢失零重复）；每条 run 带 `fidelity` 标记；改阈值的组自动标为频率级精度。
7. **寻优不误导**：用 `signals_canonical.csv`（1459 信号 / 23 天）复跑，10 个精算格的中位 PnL / 符号一致率 / λ_bear / 熊市分位 / p90DD 与 `study_fine.csv` 逐格吻合；三关判定结果与设计文档 §10.2 一致（0 格通过，走无解分支）；输出中不出现"最优参数"这类单一结论。
8. **安全护栏**：页面上不存在任何能停掉实盘进程的入口；会话卡片只读且不回显明文凭证；关键参数改动必须二次确认。
9. **无回归**：改造后现有 `trade-backtest-runs` 等既有页面结果与改造前一致。
10. **容量达标**：切片日增 ≤ 1.5 MB 且 90 天外自动清理；1m/5m/1h/1d 双源年增约 0.4 GB/币种。

## 9. 待确认问题

1. **实例与机器的映射关系**：`deploy.sh` 与 `deploy_1.sh` 共用环境变量 `argus_single_remote_server`，远程路径都是 `/data/program/app/argus_single`。实例1 与实例2 是靠部署时改环境变量区分，还是实际在不同机器上？这个对应关系要在 r1 落进 `argus_instance` 表。不影响拆解，实施 r1 时确认即可。
2. **自动寻优三关阈值的最终取值**：熊市月净 p10 的下限与 `DD_max` 需要人拍板。上一轮研究用的是 p10 ≥ −56U / p90DD ≤ 94U，按此标准 0 格通过。

4. **JSONL 双写的最终切换时点**：当前定为保留 3 个月至 2026-12-01，届时依据一致性巡检结果再决定是否停写。
