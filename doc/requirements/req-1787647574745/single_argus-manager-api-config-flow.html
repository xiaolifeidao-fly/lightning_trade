01 / EXECUTIVE READ

先把调用关系说清楚

在已合入远端主干的最新实现中，配置管理链与行情监控链是两条不同的数据流。Manager API 负责版本化与发布；Argus 负责订阅、转换、热替换和执行。行情价格不会经过 Manager API。

HTTP

管理页面调用 Manager API

读取已发布配置、保存草稿、发布版本、查看运行状态，以及发起启动/停止/重启/重载。

LATEST MAIN

Argus 与 Manager API 共享基础设施

MySQL 是版本化事实源，Redis 保存 24 小时快照、发布版本消息、传递 reload 控制并承载心跳。

WEBSOCKET

Argus 分别订阅 Binance Futures 与 DeepCoin 行情，用发布配置中的币种和价差阈值进行判断，再决定告警和交易。

02 / SYSTEM MAP

不是服务对服务 HTTP

以下为提交 6bf4f73（已合入远端主干）的架构。真正的中间层是数据存储和消息通道。Manager API 不把配置直接 POST 给 Argus；Argus 也不定时请求 Manager API。

Control plane

Manager Web + manager-api

  • HTTP 配置编辑与发布
  • 字段校验、敏感值掩码
  • 版本状态与回滚保护
⇄
Shared state

MySQL + Redis

  • MySQL：不可变版本及子表
  • Redis：快照、版本广播、控制
  • Redis：实例心跳与加载结果
⇄
Data plane

argus_single

  • 启动恢复已发布快照
  • 订阅版本变更并热替换
  • 独立接收行情、比较差价、交易

因此“Argus 调 manager-api 配置”的准确表述应是：Manager API 发布配置，Argus 从共享快照消费配置。

03 / SEQUENCES

四条关键交互时序

点击切换不同链路。发布与 reload 是两次消息：发布本身已经广播版本；当前前端仍会紧接着再发送一次显式 reload，作为主动确认。

保存草稿

管理端调用 POST /api/argus-config/drafts。Manager API 校验字段，把敏感信息加密写入 MySQL，生成新的 draft 版本。

发布版本

管理端调用 POST /api/argus-config/versions/:id/publish。Service 加载完整子表，写 Redis 快照并生成 SHA-256 checksum，再把数据库中的唯一 published 槽切到新版本。

广播变化

Manager API 向 argus:config:changed 发布 {version, checksum}。发布失败时尝试回滚数据库发布状态并恢复旧 Redis 快照。

校验并热替换

Argus 读取 argus:config:snapshot，校验 checksum 和版本一致性，转换配置，然后执行 trade.ReplaceManager 与 monitor.ReloadMonitor。失败则保留旧运行配置。

显式 reload

前端随后调用 POST /api/argus/runtime/reload，Manager API 再向 argus:control 发布定向 reload。Argus 重新读取当前快照；这是一次额外确认，并非 HTTP 直推。

加载本地引导配置

vipper.Init() 仍读取 ./configs/application.properties，用于数据库、Redis、实例 ID、心跳周期以及少量尚未迁移的运行参数。

要求 DB 与 Redis 可用

Argus 初始化数据库和 Redis。当前实现把两者都视为启动必需依赖；任一关键初始化失败会终止启动。

优先读取 Redis

读取 argus:config:snapshot 并校验 SHA-256。若 Redis 没有快照，则直接查询 MySQL 唯一 published 版本及全部子表，再把快照回填 Redis。

初始化运行组件

把账户、币种和通知配置转成运行时结构，初始化交易管理器、PriceMonitor、AccountMonitor 与 Telegram。

订阅与心跳

订阅配置及控制频道；每 5 秒向 argus:heartbeat:<instanceId> 写心跳，默认 TTL 15 秒。

Argus 写状态

心跳包含 PID、启动时间、构建版本、当前配置版本、最近 reload 结果、健康状态和更新时间。

Manager API 读 Redis

GET /api/argus/runtime/status 读取实例心跳。Key 已过期或不存在即返回 online=false。

管理页轮询

页面可见且自动刷新开启时，每 10 秒请求一次运行状态；首次加载同时读取已发布配置和运行状态。

Start / Stop / Restart

Manager API 在同机执行受限的 control.sh，脚本只接受固定动作并委托 start.sh/stop.sh。这条链不经过 Redis。

Reload

Manager API 不执行脚本，而是向 argus:control 发布 reload，可按 instanceId 定向。

跨机限制

源码注释明确说明控制脚本适合同机部署；分离部署应使用受限控制代理，不能直接复用本地脚本路径。

04 / SPREAD ENGINE

差价如何真正触发

阈值不是“只要绝对差价大于阈值就不断触发”。实现记录上一次有方向价差，只在从阈值区间内向外穿越时触发一次。

signedSpread =
(Binance − DeepCoin)
÷ DeepCoin

正值表示 Binance 价格更高，负值表示 DeepCoin 价格更高。比较配置项为 monitorSymbols[].spreadThreshold。

G1

两边价格都必须有效

任一价格为 0，直接跳过。

G2

必须存在 spread 逻辑账户

hasSpreadTradeAccounts() 为 false 时不比较差价。

G3

行情必须足够新

Binance 与 DeepCoin 的价格年龄均不得超过 monitor.spread.max_price_age_ms，默认 500ms。该值目前仍来自本地 properties。

G4

需要发生阈值穿越

prev < threshold && current ≥ threshold，或负方向对称条件。第一次样本只建立基线，不触发。

G5

余额检查与 2 秒交易冷却

余额不足只告警不交易；成功进入交易路径后，同币种 2 秒内的重复触发会被抑制。

OUT

告警 + 执行套利交易

并发发送 Telegram 告警，并调用 trade.ExecuteArbitrage。实际开仓方向由账户配置决定。

06 / FINDINGS

当前最值得注意的缺口

这些不是架构设想，而是配置模型、运行时转换和消费者代码之间的实际断点。它们会直接影响“管理端改了配置是否真的生效”的判断。

HIGH

交易总开关未被执行链消费

tradeEnabled 能保存、能展示，但 runtimeFromSnapshot 没有映射，价差触发后仍可能进入下单路径。UI 承诺与后端行为不一致。

HIGH

账户交易逻辑在管理模型中丢失

DB/DTO 没有 tradeLogic。运行时构造账户时该字段为空，而空值会被当成 spread，因此管理配置天然偏向差价逻辑，无法可靠配置 signal 模式。

MEDIUM

部分“全局配置”仍由本地文件决定

价差行情最大年龄、信号延迟，以及 AccountMonitor 的间隔和盈亏阈值没有统一进入发布快照。Manager 与 Argus 可能展示两套不一致的值。

MEDIUM

订阅恢复缺少显式重连循环

Manager.subscribe 建立一次 Pub/Sub；订阅通道关闭后函数返回。虽然启动恢复和手动 reload 可补救，但长时间运行中的消息恢复策略不够明确。

MEDIUM

启动依赖 MySQL 与 Redis 同时可用

即使 Redis 已有快照，初始化仍要求 DB 可用；Redis 初始化失败也会终止。控制面故障会扩大到 Argus 冷启动可用性。

BOUNDARY

同机与跨机控制需明确区分

start/stop/restart 依赖本地可执行 control.sh。只有 reload 是 Redis 消息。跨机部署需要受限代理，否则 Manager API 无法控制远端进程。
